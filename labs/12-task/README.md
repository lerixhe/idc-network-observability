# 12-task · 任务管控：拉取还是推送

第 30–32 课配套实验。控制面只回答两个问题：变更多久到得了探针，到不了的时候长什么样。

这个实验把探针、任务、变更全部虚拟化。不发一个真实包，不碰外网，全程虚拟时钟。变更延迟、请求数、控制面峰值、连接内存都是算出来的，参数都在命令行上，读完能自己代入一遍。

产物 `out/batches.jsonl` 按第 33 课的数据契约落盘，`13-pipeline` 直接拿它当输入。

## 跑起来

```bash

make run     # 拉取 vs 推送 + 四个失败模式 + 对账，产物落 out/

make flap    # 只看坏点替换震荡：抑制开与抑制关的对比
```

## 数据契约：13-pipeline 直接吃 out/batches.jsonl

字段名与第 33 课一字不差，`13-pipeline` 不需要转换。

```text
上报批次：probe_id, batch_seq(uint64), produced_at(RFC3339), points[]
点位：   probe_id, acked_batch_seq, acked_ts
幂等键：  (probe_id, batch_seq, metric_id)
最大补报延迟：15 分钟（-max-report-delay 可配）
```

一行一个批次，按**到达顺序**写，不是按生产顺序：

```json
{"probe_id":"probe-a-01","batch_seq":4,"produced_at":"2024-03-01T00:06:00Z","points":[{"probe_id":"probe-a-01","metric_id":"if_err_rate.leaf-a1f-02.eth1-2","acked_batch_seq":1,"acked_ts":"2024-03-01T00:03:00Z"},{"probe_id":"probe-a-01","metric_id":"if_pkt_loss.leaf-a1f-05.eth1-2","acked_batch_seq":4,"acked_ts":"2024-03-01T00:06:00Z"}]}
```

两个 `batch_seq` 不是一回事，这是接管道时最容易踩的一处：

| 字段 | 在哪 | 含义 | 管道拿它干什么 |
|---|---|---|---|
| `batch_seq` | 批次信封 | 这台探针的第几个批次，从 1 开始递增 | 进幂等键，压整批重放 |
| `acked_batch_seq` | 点位 | 这条确认第一次被上报时所在批次的序号 | 同一个值会在后面每一批里重复出现，按它压周期重复上报 |

`acked_ts` 也随之固定：它是这条确认第一次被上报的时刻，不随后面的批次漂移。

`metric_id` 必须是**时序的唯一标识**，所以样本里写成 `if_err_rate.leaf-a1f-02.eth1-2`（指标名 + 设备 + 端口）。只写 `if_err_rate` 会在同一台探针上撞键，幂等键一压就丢一条——`samples/tasks.json` 里撞键会被 `LoadTasks` 直接拒绝。

样本里刻意留了四样素材，`13-pipeline` 的窗口、水位线、去重逻辑都要对付它们：

| 素材 | 在哪看得出来 | 对应第 33 课 |
|---|---|---|
| 迟到批次 | `produced_at` 早于前一行的批次，最大迟到 2m0s（probe-a-02 离线 3m–5m 期间的缓冲） | 迟到数据、水位线宽度 |
| 周期重复确认 | 同一 `probe_id`、同一 `metric_id` 在连续多批里带同一个 `acked_batch_seq` | 幂等键去重 |
| 跨探针重复 | `t-err-a1f-02` 的 `if_err_rate` 同时被 probe-a-01 与 probe-a-02 上报（重复下发） | 幂等键管不了，只能控制面拦 |
| 永久缺口 | probe-c-03 在 5m0s 退役，之后没有它的批次；`if_pkt_loss.leaf-c3f-01` 就此断掉 | 缺口标记与任务回收 |

`make tail` 把补报上限压到 1 分钟后，同样是这批数据会有 2 条变更的延迟超窗（拉取侧 p95 仍是 1m30s，但已经进不了窗口）。超窗的那批数据不是迟到，是缺口——这个分支在 33 课里必须分开处理。

## 拉取 5 秒 vs 长连接：差在三个数

| | 拉取 5s | 长连接 20ms | 怎么算出来的 |
|---|---|---|---|
| 变更到生效 p50 | 2.7s | 27ms | 拉取 = 均匀落在 (0, P]；推送 = 单程延迟 + 抖动 |
| 变更到生效 max | 1m30s | 1m33s | 两条路的尾巴都是**离线时长**，不是分发模式 |
| 请求数（12 台 / 10 分钟） | 1,363 | 258 | 拉取 = 探针数 × 时长/P；推送 = 探针数 × 时长/心跳 + 变更数 + 建连 |
| 请求数比 | 5.3 倍 | 1 | 理论值 240/40 = 6，样本 12 台、在线率 92% 拉低到 5.3 |

三条能自己复核的数：

1. **轮询上限就是轮询周期**。`-poll 5s` 时一条变更最晚等 5 秒；`-poll 30s` 时最晚 30 秒，请求数掉到 1/6。`make modes` 三行就是这个换法。
2. **推送的在线延迟 = 单程延迟 + 处理抖动**，默认 20ms 抖动不超过本身，所以落 (20ms, 40ms)。测试 `TestPushLatencyBeatsPull` 逐条断言这一点。
3. **尾巴不由模式决定**。probe-a-02 在 3m0s–5m0s 离线，落在这段的变更只能等它回来：拉取 1m30s、推送 1m33s，差的是 `-poll 5s` 的相位余量 vs `-reconnect 3s` 的重连退避。谁更好取决于这两个数的比值，不是取决于「推送更实时」这句话。

轮询时刻按 64 个相位打散（`pollPhase`）。不打散的话，十万探针在整秒上同时醒，峰值 QPS 等于平均值；打散之后峰值是 1/64。这一行在报告里固定打印。

## 十万探针的账

```bash
make scale    # -n 100000 -out ""
```

按默认参数（5s 轮询、30s 心跳、每台探针一条任务）算：

| 项 | 拉取 5s | 长连接 | 算式 |
|---|---|---|---|
| 每小时请求 | 68,150,000 | 12,900,000 | 100000 × 720 = 72M（样本在线率 94.6% 折下来 68.15M）；100000 × 120 = 12M 心跳 |
| 平均 QPS | 18,931 | 3,583 | 除以 3600 |
| 控制面长连接 | 0 | 100,000 | 每条连接一份状态 |
| 连接内存 | — | 1.3 GiB | 14 KiB × 100000 = 1.4 GB |

一条连接的 14 KiB 拆开：连接状态（位点、任务表、租约）2 KiB + 收发缓冲 4 KiB + 协程栈 8 KiB。十万条约 1.3 GiB 常驻，还没算探针表与路由索引。这是第 30 课那个判断的来源：小规模上连接池与对象池都是过度设计，到这个量级不做就是 OOM。

`make scale` 实跑 100000 台探针、100002 条任务、125003 条变更，耗时 311ms，只算量不落批次——落批次是几百万行 JSONL，不是这个实验要量的事。探针数超过 2000 台还带 `-out` 会被直接拒绝：

```text
$ go run . -n 5000
失败: 探针 5000 台超过落批次的护栏 2000：十万探针只用 -out "" 算量，不落 JSONL
```

## 四个失败模式

每个模式都是「注入 + 检测 + 一条可观测信号」，信号进 `out/events.jsonl`。

**1. 重复下发**。`KindMove` 的撤销消息丢了，旧探针和新探针同时接活。检测靠分组：同一个 `(task_id, revision)` 出现在两台探针上就是重复。

- 信号 `duplicate-dispatch`，evidence 里有 `probes`、`overlap_s`、`duplicated_points`。
- 代价是数据翻倍：`t-err-a1f-02` 重叠 434.9s，重复 7 个点位。
- 关键一句：幂等键是 `(probe_id, batch_seq, metric_id)`，按探针去重，**跨探针的这份重复它压不住**。数据面没有办法，只有控制面自己报。

**2. 全量重推**。一条全局变更（换版本、改 schema）把全部任务重发一遍。

- 信号 `full-repush`，evidence 里同时给本样本与十万探针两组数。
- 十万探针：稳态 34.72 QPS（125000 条变更 / 3600 秒），限流 500 条/秒之后峰值 500 QPS，放大 14.4 倍，排空 100000 / 500 = 200 秒。
- 真正的代价不是那 200 秒的带宽，是**排空期间所有增量变更排在队尾**：这段时间下发的变更，延迟统一加 3m20s。

**3. 坏点替换震荡**。目标设备整段不应答，换哪台探针都失败，任务就在几百台机器之间迁移，每跳一次断一段数据。

- 抑制策略：连续换 `-flap-limit`（默认 2）次之后不再换，转成一条 `task-fault`——「目标设备坏了，不是探针点位的问题」。
- 抑制开：迁移 2 次，断档 2 段 2m5s。抑制关：迁移 7 次，断档 7 段 7m17s，仿真结束时还在转。
- 差 10m25s 的数据。抑制的价值不在少发几条指令，在这 10 分钟的指标曲线是连续的。
- 测试 `TestFlapSuppressionStopsOscillation` 同时断言两侧：抑制开时迁移次数不超过阈值、`task-fault` 条数等于坏点任务数；抑制关时迁移次数必须超过阈值、且不许有 `task-fault`。

**4. 过期任务不回收**。探针下线了，任务还挂在它名下。判据只有一条：最后一次心跳距今超过 `-stale-ttl`（默认 2m）。

- 信号 `stale-assignment`，一条任务一条。
- probe-c-03 在 5m0s 退役，名下 2 条任务。不回收：静默 5m0s，缺口到仿真结束，也没人知道该去找哪台探针。
- 回收：TTL 到点（7m0s）改派，加半个轮询周期，7m2s 恢复出数，缺口 2m2s。
- 注意这两个数的差别不是「2m 和 5m」，是**有恢复时刻和没有恢复时刻**。

## 留的坑

**1. 幂等键里的 `batch_seq` 是信封上的那个，不是点位上的。** 两个字段名字像，作用完全不同。用 `acked_batch_seq` 进键，整批重放就压不住了；用信封的 `batch_seq` 压周期重复上报又压不掉，两件事分开做。

**2. `metric_id` 只写指标名会在同一台探针上撞键。** 一台探针跑 5 条任务，其中两条都是 `if_err_rate`，幂等键 `(probe_id, batch_seq, metric_id)` 当场把两条并成一条。样本里写成 `if_err_rate.leaf-a1f-02.eth1-2`，`LoadTasks` 会拒绝重复的 `metric_id`。

**3. 尾延迟两条路差不多，别拿 p50 的差距去选型。** 拉取 2.7s 对推送 27ms，差了 100 倍；但 p95 是 1m30s 对 1m33s。真正决定选型的是「你能接受多少条连接、多少内存、多少请求」，以及数据面要不要批次边界——拉取式天然带批次号，推送式没有，推送式只能用 `(probe_id, metric_id, ts)` 去重，碰到补报与乱序就容易误杀。

**4. 震荡的抑制阈值是个经验值，不是定理。** `-flap-limit 1` 会让偶发一次失败就报故障，`-flap-limit 5` 会多丢 5 段数据。取 2 的理由是「一次失败是噪音，两次连续失败是目标侧问题」——按你自己环境的失败率重算，别照抄。

**5. 探针离线 ≠ 数据不产生。** 离线期间任务照跑、确认照记，批次堆在本地缓冲里等重连补报；超过最大补报延迟的那部分直接丢。所以「迟到」和「缺口」是两件事：迟到的数据放宽窗口就能收，缺的数据只能打标记。本实验两条路都注入了，看 `make tail` 与 `out/batches.jsonl` 的对比。

**6. `capacity` 只做校验，换点时不看容量。** 真实控制器挑接活探针要算配额，本实验只按同机房轮转。加上容量约束只会让换点更难，震荡的结论不变；要真算配额，把 `nextFlapProbe` 里的候选过滤补上就行。

**7. 全量重推在本样本上的放大倍数是 467 倍，这个数没有意义。** 样本稳态只有 0.03 QPS，任何重推都是几百倍。要用的数是十万探针那一行：14.4 倍、排空 200 秒。
