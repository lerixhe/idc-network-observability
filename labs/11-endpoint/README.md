# 11-endpoint · 终端定位联查

第 27 课的配套实验。运维问得最多的一句话是「10.32.7.18 现在在哪个机柜的哪个口」，答案要靠三张表接力：

```text
IP ──ARP 表──► MAC ──MAC 表（FDB）──► 交换机端口 ──台账──► 机柜 / U 位
```

样本给了两台网关的 ARP 表、四台二层交换机的 FDB、一份 DHCP 租约日志，外加一份最小台账（端口 → 机柜 / U 位）。程序把这四份拼起来，输出每个 IP 的位置、判断依据、命中了哪个陷阱、下一步做什么。

三个陷阱是重点：**同一个 MAC 在两个端口**、**聚合口只报逻辑口**、**ARP 已老化但 DHCP 租约还在**。

## 跑起来

```bash
cd labs/11-endpoint
make run                       # 批量查 samples/queries.txt 里的 7 个 IP
make query IP=10.32.7.18       # 单查一个，竖排输出全部证据
make test                      # vet + 单元测试
make demo                      # 批量 + 结论分布 + 陷阱命中 + 三表规模
make clean                     # 删 out/
```

零外部依赖，不连网、不连设备。

## 三张表的采集频率差三个数量级

| 数据源 | 在哪采 | 采集频率 | 表项老化 | 断了之后的表现 |
|---|---|---|---|---|
| ARP | **所有**三层设备：网关、三层交换机、防火墙、负载均衡 | 60s | Linux 60s，交换机 240–1200s | IP 有、MAC 断 |
| FDB（MAC 表） | **所有**二层设备 | 300s，核心交换机分片错开 | 300s（默认 `aging-time`） | MAC 有、端口断 |
| DHCP 租约 | DHCP 服务器事件流，或中继日志 | 实时推，或 30s 拉 | 由 `lease time` 决定，常见 6h / 24h | 只剩主机名 |
| 端口台账 | CMDB，变更驱动 | 变更即写，日对账 | 不老化，靠对账纠 | 端口有、机柜断 |

一句话记住这个表：**ARP 一分钟就老，FDB 五分钟，租约几小时**。老得快的表决定了采集频率，老得慢的表决定了历史能追多久。

联查的正确性卡在两头：采 ARP 慢一拍，答案就变成「查不到」；台账漏一个端口，最后一公里就走不完。

## 联查算法

```text
1. ARP：这个 IP 的 MAC 是什么？表项多老？
   ├─ state=incomplete        → 网关在问、没人答，ARP 不可用
   ├─ age ≤ 老化门限          → 可用，拿它的 MAC
   └─ age > 老化门限          → 不可用，只当历史线索
2. 租约：这个 IP 分给过谁？
   └─ 日志最后一行是 ack 且未到期 → 有有效租约，拿到 MAC 与主机名
3. FDB：这个 MAC 在哪个交换机的哪个口？
   └─ 同 VLAN 内按 age 升序取最新，其余标 stale
4. 台账：这个口在哪个机柜的哪个 U 位？
   └─ 逻辑口按 members 展开到成员口
```

四个结论，各对应一处断点：

| verdict | 含义 | 断在哪 | 样本里的 IP |
|---|---|---|---|
| `located` | 三张表接力走通 | — | 10.32.7.31、10.32.8.44、10.20.4.51、10.33.1.12 |
| `arp_only` | ARP 有、二层表没有 | MAC 表覆盖不全 | 10.20.4.60 |
| `lease_only` | 租约在、现网未见 | ARP 老化 + 二层表没有 | 10.32.7.18 |
| `not_found` | 三张表都没有 | 第一跳就断 | 10.32.7.99 |

`arp_only` 和 `lease_only` 长得像，处置完全不同：前者是采集覆盖问题，去补采；后者是终端不在了，去按主机名找。混成一个「查不到」，值班的人只能重启一遍设备试试。

老化门限是策略不是常量。`-aging` 调到 1 小时，10.32.7.18 的结论就从 `lease_only` 翻成 `arp_only`——同一条数据，门限一动，答案就变。

```bash
go run . -query 10.32.7.18 -aging 1h
```

## 三个陷阱

**陷阱 a：同一个 MAC 在两个端口。** 虚拟机从 `leaf-b1f-01` 迁到 `leaf-b1f-02`，新交换机立刻学到 MAC，旧交换机那条表项要等 300 秒老化完才消失。样本里 `00:50:56:aa:00:44` 在 `leaf-b1f-01 Ethernet1/5`（age 780s）和 `leaf-b1f-02 Ethernet1/12`（age 96s）各有一条。取 age 最小的，旧的进 `stale` 字段。按旧表项派人，到 `B-01/U09` 只能看着一台空机柜。

**陷阱 b：聚合口只报逻辑口。** 服务器双网卡 bond 上联，交换机 FDB 学到的是 `Port-Channel10`。逻辑口没有物理对端，台账里也不该有机柜 U 位。程序按台账的 `members` 展开到 `Ethernet1/1`、`Ethernet1/2`，两个成员口报的位置一致才敢落答案。不一致就只给候选，让现场核——猜一个等于埋一颗雷。

**陷阱 c：ARP 已老化但 DHCP 租约还在。** `10.32.7.18` 的 ARP 表项 12 分钟没刷新，过了 5 分钟门限，四台交换机的 FDB 里也没有它的 MAC。这时候回「查不到」是错的：租约还有 6 小时，主机名 `pi-sensor-07` 就在日志里。正确答案是「租约在、现网未见」——终端关机或网线拔了，位置要按上次上线记录核。

## 样本格式

### `samples/arp.jsonl`

两台网关的 ARP 表，10 条。华为与思科的 `show arp` 字段差不多，这里统一成一套。

| 字段 | 含义 |
|---|---|
| `ts` | 本台设备的快照时刻 |
| `gateway` / `vlan` / `if_name` | 哪台三层设备的哪个三层接口 |
| `ip` / `mac` | 表项本体 |
| `state` | `reachable` / `stale` / `incomplete` |
| `last_seen` | 表项最后一次被确认的时刻，从表项 age 反推 |

`last_seen` 不是设备报的字段。不给它就算不出「老化了多久」，只能看到 state 猜——这是这个实验要求显式带上它的原因。

### `samples/fdb.jsonl`

四台二层交换机，17 条。MAC 写法故意两种混着来：华为风格 `3c52-8211-0731`、思科风格 `0050.56aa.0044`，网关 ARP 里那份还用冒号 `00:1b:21:04:00:77`。三张表三种写法，代码先归一成 `aa:bb:cc:dd:ee:ff` 再比。

| 字段 | 含义 |
|---|---|
| `ts` | 快照时刻 |
| `switch` / `vlan` / `port` | 学到这个 MAC 的设备和端口 |
| `mac` | MAC，写法因厂商而异 |
| `age_s` | 表项已经存在的秒数，越小越新 |
| `type` | `dynamic` / `static` |

交换机不报「学到时刻」，只报 age。跨设备比新旧全靠它，所以快照时刻必须对齐，否则 300 秒的误差能把漂移方向判反。

### `samples/dhcp-leases.jsonl`

一份事件流，10 行，同一个 IP 会有多行。最后一行才算数：`ack` 且未到期才有效，`release` / `expire` / `decline` 一律作废。

```json
{"ts":"2026-05-12T10:05:33Z","server":"dhcp-02","event":"release","ip":"10.32.8.90","mac":"00:25:90:08:00:90","hostname":"srv-b1f-t90","vlan":30,"start":"2026-05-12T02:05:00Z","expire":"2026-05-12T14:05:00Z"}
```

`10.32.8.90` 就是这种：ARP 表里还有它、FDB 里也还有它，租约已被客户端释放。ARP 和 FDB 都没错，只是慢了。

### `samples/ports.json`

最小台账。`devices` 给设备清单，`ports` 给「设备 + 端口 → 机柜 / U 位」。

| 字段 | 含义 |
|---|---|
| `device` / `port` | 端口主键。不用 `ifIndex`，换块业务板它会重排 |
| `rack` / `u` | 机柜号与 U 位 |
| `desc` | 端口描述，写清接的是谁 |
| `members` | 只有聚合逻辑口才有，列出物理成员口 |

台账里 `leaf-b1f-01 Ethernet1/40` 故意没登记。FDB 说这个口学到过 MAC，台账说不出它在哪个机柜——**定位的最后一公里断在台账上，比断在采集上更难发现**，因为前三张表看起来全是通的。

### `samples/queries.txt`

一行一个 IP，`#` 后面是给人看的注释，代码只取第一个字段。

## 这个实验故意留的坑

1. **MAC 有三种写法。** 华为 `0050-56aa-0044`、思科 `0050.56aa.0044`、Linux `00:50:56:aa:00:44`。不归一，同一个 MAC 在三张表里就是三个东西，联查必断在第一步。`normalizeMAC` 只认十六进制字符，长度不对就原样返回——把异常值吞成空串，日志里再也看不出输入有问题。
2. **三张表的快照时刻不同，时间没对齐。** 样本里都是 `2026-05-12T10:12:00Z`，真实环境 ARP 与 FDB 差几十秒是常态。年龄差到分钟级，漂移方向就可能判反。代码只取最晚那个时刻当「现在」，没做插值也没做外推。
3. **ARP 只在网关上有。** 样本两台网关覆盖 VLAN 10/20/30/40。只采到 `gw-core-01` 的话，`10.32.8.44`、`10.33.1.12` 这批 IP 永远定位不到，而且报出来的错是「查不到」，看着像终端不在。
4. **FDB 要采全部二层设备，还要采全 VLAN。** `10.20.4.60` 的 ARP 与租约都新鲜，四台交换机的 FDB 里都没有它的 MAC。最可能的原因是它的接入设备不在采集清单里，或者落在没采的 VLAN——代码只能指出断在 MAC 表，指不出具体是哪台设备漏了。
5. **同 MAC 跨 VLAN 不算漂移。** 代码先按 ARP 里的 VLAN 过滤 FDB。一条都没有时才放宽到全部 VLAN，并在证据里写「广播域对不上」。私有 VLAN 与 MUX VLAN 的业务口翻译没做，真机上这一层会把端口名再拧一次。
6. **聚合口的成员关系来自台账，不来自设备。** FDB 只说「学在 Port-Channel10」，成员口的机柜 U 位全靠 `members` 展开。台账把成员口写错，答案就错得理直气壮——这是第 23 课「台账错了后面全错」的最小复现。
7. **IPv6 完全没做。** NDP 表与 ARP 表是两张表。样本只有 IPv4，真机上线两年才发现 IPv6 终端定位不了，就是从这行缺口开始的。
8. **漂移靠 age 猜，猜的是「谁更新」。** 两台交换机的时钟差 30 秒、FDB 采集时刻差 30 秒，`age_s` 的比较就开始飘。老化的边界上（比如两条都 290s），代码会给出一个确定的答案，而正确的答案可能是「pending，再采一次」。
9. **随机 MAC 让租约主机名对不上。** 手机开随机化 MAC，同一个 IP 每天换一个 MAC，DHCP 租约里每次都是新行。`lease_only` 的结论照样成立，但主机名那条线索基本没用。
10. **`type` 字段只当标记，代码不区分 static 与 dynamic。** 真机上 static 表项不老化，`age_s` 永远是 0，按 age 升序排它永远排第一个。样本里全是 dynamic 绕过了这个坑，真环境中一条 IP-MAC 绑定就能把定位结果带到另一台设备上。
11. **查到宿主机就到头了。** 容器里的服务，FDB 只能告诉你是哪台物理机。再往下走 `ip netns`、`veth`、`conntrack`、CNI 都不在这个实验里，那是第 44 课的活。
