# 04-ecmp-hash · 哈希与路径覆盖

第 12 课的配套实验。给一组等价路径和一种哈希函数，算出**探测覆盖率**：打多少包，能覆盖几条 member，剩下几条是盲区。

核心结论一句话：你以为在测一条链路，其实在测一条哈希路径。同一批五元组在按五元组哈希的设备上永远落在同一条 ECMP 分支，另一条坏了毫无察觉。

## 跑起来

```bash
cd labs/04-ecmp-hash
make run     # 覆盖率曲线 + 预算表 + 故障可见性
make test    # vet + 单元测试
make demo    # 再多打 member 负载、期望探测次数、一段演示
make try     # 换 crc32c-pow2 落桶，看负载怎么歪成 2:1
make clean   # 删 out/
```

零外部依赖，不发一个真实数据包，不碰外网。

## 哈希口径

哈希输入是五项，按下面的顺序拍成 13 字节，全部大端：

| 顺序 | 字段 | 字节 | 来源 |
|---|---|---|---|
| 1 | 源 IP | 4 | 探针自己的地址，固定 |
| 2 | 目的 IP | 4 | 目标地址，固定 |
| 3 | 协议号 | 1 | 6=TCP，17=UDP，1=ICMP |
| 4 | 源端口 | 2 | **唯一可变的字段** |
| 5 | 目的端口 | 2 | 探测协议定的，固定 |

编码顺序是哈希口径的一部分：调一行顺序，全部落桶结果就变，而且不会报错。`TestEncodeTupleLayout` 把 13 个字节逐个钉住。

三个落桶函数，用 `-hash` 选：

| 名字 | 算法 | 落桶 | 用来说明 |
|---|---|---|---|
| `fnv1a-mod` | FNV-1a 32，手写 10 行 | `h % n` | 最短的可复现实现，能一行一行对着算 |
| `crc32c-mod` | CRC-32C（Castagnoli），默认 | `h % n` | 多数交换 ASIC 的哈希用它，硬件里有专用指令 |
| `crc32c-pow2` | CRC-32C | 成员表填充到 2 的幂，低位掩码取下标 | 负载不均的来源 |

盐（`hash_salt`）当哈希的初始值用，等价于设备上的 `hash seed` 配置。同一批五元组，盐一换落桶全变——这是「换一台设备就得重测」的物理原因。样本里两组路径的盐故意不同（`0x12345678` 与 `0xdeadbeef`）。

`crc32c-pow2` 的填充规则：成员表补齐到 2 的幂，多出来的槽位重复填前面的成员。n=6 填成 8 格，槽位顺序 `[m0,m1,m2,m3,m4,m5,m0,m1]`，于是 m0、m1 各占 25%，其余各 12.5%。覆盖率照样 100%，流量从第一步就不均。

比对照着实算一遍 n=4：8 个槽位里 `h & 7` 均匀取 8 个值，落到 m0 的槽位是 0 和 4 两个，所以 m0 拿 25%，m1、m2、m3 各 25%。成员数是 2 的幂时填充不改变任何东西。

## 三种探测方式

五元组里只有源端口能自由改，所以「换五元组」在探测里就等于「换源端口」。

| 方式 | 源端口 | 等价于现场什么做法 |
|---|---|---|
| `fixed` | 固定 40001 | 固定配置的探针、一条 `ping` 脚本、写死的健康检查 |
| `random` | 每次从 1024–65535 均匀随机 | 每次新建连接的客户端、随机端口的合成探针 |
| `budget` | 第 k 个取 `1024 + (k × 4099) mod 64512` | 「这一轮允许多打 B 个包，把端口铺开」 |

`budget` 的步长 4099 是质数，与 64512（可分配端口数）互质，所以前 64512 个预算端口互不重复；同时它和 2 的幂不对齐，避免「端口号低位全 0」这种自欺欺人的均匀。

## 覆盖率怎么算

覆盖率 = 累计探测过的不同 member 数 ÷ member 总数。累计是关键：曲线只升不降，降了说明代码在数「这一轮打到了几条」。

随机源端口覆盖满全部 n 条，是标准的优惠券收集器问题：

```text
E[T] = n · H_n = n · (1 + 1/2 + 1/3 + … + 1/n)

n = 4：4 × (1 + 0.5 + 0.3333 + 0.25) = 4 × 2.08333 = 8.33 次
n = 6：6 × 2.45 = 14.7 次
```

实测（2000 次试验，`make demo`）：

| member 数 | 理论期望 | p50 | p90 | p99 |
|---|---|---|---|---|
| 4 | 8.3 | 7 | 13 | 22 |
| 6 | 14.7 | 13 | 24 | 35 |

p50 比期望小是因为期望被长尾拉高：一半的试验在期望值之前就打完了。定预算看 p99，不看 p50——4 条 member 想「几乎必然」覆盖满，得按 22 个包准备，不是 8 个。

`budget` 模式没有运气成分，三个分位数相等（4 条 member 是 7，6 条是 15）。这不是 bug，是「预算固定就没有方差」的意思。

## 故障可见性

一行一条 member，假定它坏掉，看探测侧观测到的丢包率。0.0% 就是「坏了，但探测没给它发过包」：面板全绿、告警不响。

`fixed` 列里是 0.0% 的那些行，就是这个实验要说的事。4 条 member 里 3 条是 0.0%，概率 75%——所以 `-broken auto` 默认挑的就是这种 member，不是故意挑一个极端例子。

反过来那两个非 0 的列证明了一件事：问题不在「测不了」，在「没换五元组」。改一行代码换成随机端口，同一批故障立刻可见。

`-broken` 可以指定 member id 看「运气好的那次」：

```bash
go run . -broken m2    # m2 是固定五元组打到的那条，观测丢包率 100%
```

## 样本格式

### `samples/paths.json`

一个 JSON 数组，一组一个对象。

| 字段 | 含义 |
|---|---|
| `name` | 这组路径的名字，进终端标题 |
| `route` | 目的前缀，只给人看，不参与哈希 |
| `hash_salt` | 哈希盐（设备侧 seed），同一批五元组换盐就换桶 |
| `base.src_ip` / `dst_ip` / `proto` / `dst_port` | 五元组里固定的四个字段 |
| `members[].id` | 成员 ID，只用 ASCII，进表格和 CSV |
| `members[].desc` | 人读的下一跳说明 |

源端口不在样本里：它由探测方式决定，写死就等于把结论写死了。

两组样本的差别是有意的：第一组 4 条 member（2 的幂，负载天然均分），第二组 6 条（不是 2 的幂，填充式落桶会歪）。

### `out/coverage.csv`

覆盖率曲线，一行一个（路径组，探测方式，探测次数）：

```text
path_set,mode,probes,covered,total,coverage
tor-a3f-01 → spine-01,fixed,1,1,4,0.2500
tor-a3f-01 → spine-01,random,10,4,4,1.0000
```

### `out/blindspots.jsonl`

故障可见性，一行一个（路径组，探测方式，坏掉的 member）：

```json
{"path_set":"tor-a3f-01 → spine-01","mode":"fixed","probes":100,"broken":"m0","observed_loss":0,"invisible":true}
```

## 这个实验故意留的坑

1. **ICMP 探不到全部路径**。样本只模拟 TCP/UDP。ICMP echo 没有端口，很多设备对 ICMP 只哈希 IP 对，于是无论怎么换源端口都落在同一分支。拿 ping 证明「路径都通」，在哈希口径上根本不成立。
2. **overlay 网络里哈希看的是外层五元组**。VXLAN 封装后，内层五元组散得再开，外层可能只有两个值（两台 VTEP 之间的流），覆盖率按外层算，不按你看得见的那个算。
3. **对称哈希不增加覆盖**。开了对称哈希（LAG 和部分 ECMP 配置里默认开）之后，源/目的互换落同一个桶。好处是反向路径一致，坏处是「从另一端再探一遍」拿不到新信息。
4. **等距预算端口不保证覆盖率**。第二组样本里预算 8 只覆盖 5/6，翻倍到 16 才满。端口号等差递增，CRC 后的差值也有相关性，撞桶不是随机的。预算要按实测 p99 定，不能按「member 数」定。
5. **覆盖率 100% 不等于负载均衡**。`make try` 那组 25.1/24.8/12.5/12.5/12.5/12.3 就是覆盖率满、负载歪一倍。前者决定你能看见几条路径，后者决定哪条先被打满。
6. **盐不可移植**。同一批五元组在 `tor-a3f-01` 落 m2，在 `tor-b7f-02` 落 m4。任何「我们测过了，全绿」的结论都只对测过的那台设备成立。
7. **逐包轮转的设备不适用**。按五元组哈希的设备才让探测说谎；逐包轮转（per-packet round-robin）的设备上，一个包就换一条路，这个模型反过来失效。IDC 里少见，但存在。
8. **`% n` 不是真实 ASIC 的做法**。真实硬件是「哈希 → 成员表下标」，成员带权重，权重不等时 `h % n` 的覆盖率含义要重算。表里那个 `crc32c-pow2` 只是最轻的一种真实变形。
9. **单次跑出的 4/4 不代表稳态**。随机端口的覆盖是概率量，一次跑满分可能只是这次的种子运气好。要下结论看 p90/p99，不看一次结果。
