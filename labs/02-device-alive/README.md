# 02-device-alive · 一万台设备的存活监测

第 08、09 课配套实验。一次探测只有两个结果：通、不通。这个实验把「不通」拆成三种原因——设备死了、设备在重启、探针自己瞎了。

判定层看不到真相。它只有一个布尔值、一条同源相关性规则、一个去抖计数器。真相由模拟器注入，最后两边对账。

全程虚拟时钟，不发一个真实数据包，不碰外网。

## 跑起来

```bash
cd labs/02-device-alive
make run      # 四类故障全开，默认几百台
make four     # 四类剧本各跑一遍，只看核对行
make test     # vet + 单元测试
make scale    # 一万台，10 秒周期跑一小时
```

## 判定链只有三步

```text
每轮探测（通/不通）
   → 按「同机房 + 同探针」算组内失败比例
   → 比例达阈值且连续若干轮：判定探测侧故障，整轮观测作废
   → 否则逐台推进去抖状态机：连续 N 次失败判下线，连续 M 次成功判恢复
```

第三步的「作废」是关键。探针自己瞎了的时候，它报的「通」和「不通」都不算数——失败不累计，成功也不累计。整组设备的判定停摆，等探针恢复后重新数。

两个 CLI 参数决定了误判的形状：

| 参数 | 默认 | 作用 |
|---|---|---|
| `-fail N` | 3 | 连续 N 次失败判失联 |
| `-ok M` | 2 | 连续 M 次成功判恢复 |
| `-interval P` | 30s | 探测周期 |
| `-corr` | 0.5 | 同源组失败比例阈值 |
| `-corr-min` | 4 | 同源组最小规模，低于它不做相关性判定 |
| `-corr-ticks` | 2 | 同源组连续满足可疑条件的轮数；必须小于 N |
| `-reboot-suspect` | 6m | 离线不超过这个时长，恢复时标 `suspect_reboot` |

## 发现延迟 = (N-1)×P 到 N×P

故障落在探测时刻上，第 N 次失败就是最后一次，延迟 (N-1)×P。故障落在两次探测之间，要多等一整轮，延迟 N×P。

| N \ P | 10s | 30s | 60s |
|---|---|---|---|
| 2 | 10–20s | 30–60s | 1–2m |
| 3 | 20–30s | 1–1.5m | 2–3m |
| 5 | 40–50s | 2–2.5m | 4–5m |
| 10 | 1.5–1.7m | 4.5–5m | 9–10m |

实测（`reboot` 剧本，真实失联 3–5 分钟）：

| 配置 | 检出 | 发现延迟 | 说明 |
|---|---|---|---|
| N=3, P=30s | 2/2 | 1m0s | 默认参数，够用 |
| N=5, P=30s | 2/2 | 2m0s | 慢一倍，换来抗噪音 |
| N=3, P=60s | 2/2 | 2m0s | 周期减半和 N 翻倍等价 |
| N=10, P=30s | 0/2 | — | **漏报 2 个**：4 分钟的重启攒不到 10 次失败 |

最后一行是这张表的意义。N 调大不是免费的：重启 4 分钟的设备，要 5 分钟连续失败才够 10 次，一次重启从头到尾看不见。

反过来 N 调小，`cpu-stall` 剧本立刻灌进来一堆假告警——下面细说。

## 四类剧本的期望输出

剧本名走 `-scenario`，时间参数在 `samples/scenarios.json`（文件缺失时用内置默认值，改规模不用改代码）。

| 剧本 | 注入 | 期望 | 实测（400 台 / 30 分钟 / N=3） |
|---|---|---|---|
| `hard-down` | 2 台设备彻底断电，15 分钟 | 2 down + 2 up，无探测侧事件 | 4 条事件，检出 2/2，延迟 1m0s |
| `reboot` | 2 台设备重启，4±1 分钟 | 2 down + 2 up，up 标 `suspect_reboot` | 4 条事件，检出 2/2，`downtime=3m0s` / `4m0s` |
| `cpu-stall` | 3 台管理面 CPU 打满，单次失败率 60% | **不该有设备下线事件** | 8 条事件，误报 3 台，劣化窗口内 66.7% 的轮次被判 down |
| `probe-outage` | room-c 的探针整段失联 5 分钟 | 只有 probe-fault / probe-recovered，没有设备事件 | 2 条事件，设备事件 0 条，作废 1000 轮次观测 |

`cpu-stall` 那一行是这个实验最该记住的地方。设备活着，只是它的管理面 PC 机箱里的 CPU 满了，ping 有六成的包丢了。N=3、P=30s 下，连续三次失败的概率每轮 21.6%，20 轮里几乎必然撞上一次，于是判定层给一台活着的设备开了一条下线工单。

三种失败形态里最贵的不是漏报，是这个——误报会消耗运维对告警的信任。

## 两种输出，只有一种能开工单

`out/events.jsonl` 是事件流，一条事件一行：

```json
{"seq":1,"at_ms":420000,"kind":"device-down","subject":"leaf-0113","evidence":{"consecutive_fails":3,"peer_total":100,"peer_failed":2,"peer_fail_ratio":0.02}}
```

`out/snapshot.json` 是终态快照，每台设备一行，只有当前状态和连击数。

快照的问题在 `flapped_devices` 这个计数上。跑完 `all` 剧本，快照里 400 台全是 `up`，看起来什么都没发生。事件流里有 7 台设备各下线过一次——其中 4 台已经恢复，3 台是 CPU 打满的误判。

```text
快照说明不了的事
  7 台设备在快照里是 up，期间都下线过。终态和一直健康的设备长得一模一样，
  工单只能从事件流开。
```

三件事决定了事件才是工单来源：

1. **快照有状态没有历史**。刷新一次就把上一轮覆盖掉，下线 30 秒后恢复的设备不会留痕。
2. **快照没法算时长**。恢复了多久、抖了几次、一致不一致，全靠时间序列反推。
3. **快照不可追加**。事件是 append-only，写一次不再改；快照要 UPDATE，并发下就是覆盖冲突。

快照该干的事是看板：现在多少台 up、多少台 down、哪台最新掉线。要查「今天几点掉的、掉了多久」，只能读事件流。

## 一万台是什么量级

```bash
make scale    # -n 10000 -interval 10s -duration 1h
```

| 项 | 实测（M 系列 Mac，Go 1.26） |
|---|---|
| 设备 10000 台 × 60 轮（30s 周期 30 分钟）= 60 万次探测 | 20 ms |
| 设备 10000 台 × 360 轮（10s 周期 1 小时）= 360 万次探测 | 120 ms |
| 判定层吞吐 | 约 3000 万次探测/秒 |
| 峰值内存 | 21 MB |
| `snapshot.json`（一万台） | 1.8 MB |
| `events.jsonl`（一万台） | 5.9 KB |

换算一下：一万台、30 秒一次，实时需求是每秒 333 次探测。判定层能跑 3000 万次/秒，差四个数量级。

结论：**规模不是这类系统的瓶颈**。真实的墙在探测本身——每次探测要发包、要等超时，一个 500ms 的超时挂住一个协程。判定逻辑再快，也快不过网络上等不到的回包。第 15 课讲探针的并发与超时，讲的就是这堵墙。

这个实验量的是判定层。3000 万这个数字说明：参数和口径想清楚了，断言一层皮很便宜；参数没想清楚，跑得再快也只是快地把错误结论发出去。

## 留的四个坑

**1. `suspect_reboot` 只看时长，会被 CPU 打满骗。** 判据是「离线时长 ≤ 6 分钟就恢复」。`cpu-stall` 剧本里那些误判都是离线 1–3 分钟就「恢复」，全被标成了疑似重启。真要知道是不是重启，得看 `sysUpTime` 是否归零——本实验的探测层只返回布尔值，拿不到这个证据。

**2. 同源相关性分不清「整机房真挂了」和「探针瞎了」。** room-c 100 台同时不通，判定层的结论是 probe-fault。这结论对一半：它说对了「这些失败是相关的」，说不出「是设备侧还是探测侧」。要往下一层分，只有两条路——跨机房探针互相探测（对上联做交叉验证），或者等探针恢复后查 `sysUpTime`。这是第 08 课那条四步判据链的后两步，本实验只实现前两步。

**3. `-corr-ticks` 必须小于 `-fail`。** 探测侧故障的确认要是比设备去抖还慢，整组设备会先被误判下线——探测侧故障第一轮 100 台同时失败，第三轮就够 N=3 了，而组判定还在等确认。这是个真实的参数耦合，程序直接拒绝：

```text
$ go run . -fail 2
失败: 同源组确认轮数必须小于判失联的失败次数，否则探测侧故障会先被当成设备下线
```

想用 N=2，就得同时 `-corr-ticks 1`。

**4. 探测被压成了一个布尔值。** 真实 ping 有 RTT、有 ICMP 类型（超时 / 主机不可达 / 被限速），SNMP 有 `sysUpTime`，SSH 有握手耗时。全丢掉只留通不通，误判率就是这个实验的结果；留一部分，判据就能往下走。跨协议交叉验证（ping 不通但 SNMP 通 → CPU 打满或 ICMP 被限速）留作练习，改一行 `probeFunc` 签名就能开始。
