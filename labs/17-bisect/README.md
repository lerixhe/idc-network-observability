# 17-bisect：五层链路里把故障段切出来

链路按顺序切成五段：服务器-接入、接入-汇聚、汇聚-核心、核心-对端、对端-互联出口。
每个场景都注入了唯一一个故障段，样本给的是每段时延、丢包和覆盖标志。
任务是只用测量样本把故障段定位出来，同时记账：探了几次、花了多少毫秒。

## 1. 定义

- 单段探测：一次只探一段，成本 = 该段探针成本 + 固定启动开销。
- 前缀探测：一次探「入口到第 k 段」整条前缀，成本 = 沿途各段之和 + 一次开销。
- 判定：时延超基线 2 倍，或丢包超 1%，算异常。
- 覆盖缺口：`covered=false` 的段测不出东西，既不健康也不异常，只能报「需补探针」。

前缀探测比单段探测贵得多，这是三种策略分出高下的根本原因。

## 2. 三种策略

顺序扫：从入口逐段点名，命中即停。相当于 `for i := range segments`。
盲区在末端——故障越靠后越贵，五段全扫一遍要五个探测。

对半二分：探前缀中点，异常往左收，健康往右收，收敛后再单段复核一次。
探测次数是 log 级，但每次探前缀都把前半条链路全带上，贵。

成本加权：还是探前缀，切点不取中点，用区间 DP 算「当前前缀代价 + 按剩余段数加权的期望代价」最小的位置，切点自然往前压。

对应 Go 里的类比：顺序扫是线性查找，对半二分是 `sort.Search`，成本加权是带权重的决策树。

## 3. 跑起来

```bash
make run     # 打印五个场景 × 三种策略的对比表
make test    # go vet + go test
make clean
```

样本在 `samples/case.json`，改 `latencyMs` / `covered` / `probeCostMs` 就能看结论怎么翻。

## 4. 实测对比

```
场景：故障在首段（注入故障段：服务器-接入）
  策略       探测次数     总耗时        结论
  顺序扫      1        9ms        服务器-接入 异常
  对半二分     4        60ms       服务器-接入 异常
  成本加权     3        33ms       服务器-接入 异常

场景：故障在末段（注入故障段：对端-互联出口）
  策略       探测次数     总耗时        结论
  顺序扫      5        102ms      对端-互联出口 异常
  对半二分     3        114ms      对端-互联出口 异常
  成本加权     4        129ms      对端-互联出口 异常
```

首段故障顺序扫最省，一次就中；末段故障二分最省，因为前缀贵但次数少。
成本加权在期望上最优，最坏情况反而不如二分。期望最优 ≠ 最坏最优。

## 5. 一条坑

覆盖缺口必须先判，不能当成健康。`classify` 里如果先查时延再查覆盖，`covered=false` 的段时延字段是 0，一定判健康，
整个搜索就会径直奔向「未发现故障段」，报出一个完全错的结论——样本里第四段就是这么埋的。
顺序：无覆盖 → 异常 → 健康，这个顺序写反了，测试是能过的，现场是查不出的。
