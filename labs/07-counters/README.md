# 07-counters · 计数器速率还原

第 18、36 课配套实验。计数器只给一个数字，三种算法能算出三个答案；差值是负的，只有两种解释——回绕，或者重启。

八条采样序列、七份错包样本、一个真值文件。全程整数算术，不发一个数据包，不碰外网。

## 跑起来

```bash
cd labs/07-counters
make run     # 全量：三列对比 + 采集周期告警 + 真值对账 + 错包归因，产物落 out/
make demo    # README 的样张：每个端口一行结论，不打逐区间明细
make wraps   # 回绕周期公式表，附一组采集周期的判定
make warn    # 只打那个 10 秒采一次的 10G 口
make test    # go vet + go test
```

`make run` 的退出码有含义：与真值对账不上就非零退出。判定逻辑与样本注入的真值不一致，不该悄悄当成功。

## 回绕周期 = 2^32 / 每秒增量

32 位计数器满量程 4294967295，涨到 4294967296 归零。走完一圈要多久，只取决于每秒涨多少：

```text
回绕周期 = 2^32 / 每秒增量
字节计数器：每秒增量 = 线速 / 8
1G  口满速：4294967296 B ÷ 125000000 B/s = 34.36 s
10G 口满速：4294967296 B ÷ 1250000000 B/s = 3.44 s
```

`make wraps` 打的就是这张表，`-poll` 带一个采集周期进去，它顺手告诉你配得对不对：

| 速率 | 字节计数器回绕 | 采集周期上限 | 包计数器回绕 | 采集周期上限 |
|---|---|---|---|---|
| 1G | 34.36s | 17.18s | 48m6s | 24m3s |
| 10G | 3.44s | 1.72s | 4m49s | 2m24s |
| 25G | 1.37s | 687ms | 1m55s | 57.72s |
| 40G | 859ms | 429ms | 1m12s | 36.08s |
| 100G | 344ms | 172ms | 28.86s | 14.43s |
| 400G | 86ms | 43ms | 7.2s | 3.6s |

包计数器按 64 字节帧算，含前导与帧间隙实际占 84 字节：`1e9 / (84×8) = 1.488 Mpps`，`2^32 / 1.488e6 = 2886 s = 48m6s`。同样的小包打满，字节计数器 34 秒一圈，包计数器 48 分钟一圈，差 84 倍。

采集周期上限取回绕周期的一半，不是整圈。半圈是能容许的最大增量：两个样本之间的增量要是能塞进半个量程，看到的差值既可能是「没回绕」，也可能是「回绕一圈之后又涨了这么多」，分母差一整圈，速率就没意义了。

这张表最扎人的一行是轮询默认值。采集器默认 300 秒一次，1G 口满速 34.36 秒一圈——一个周期走完 8.7 圈，拿到的差值是 8 圈半的余数，跟真实速率没关系。要用 32 位计数器，1G 口只能 10 秒轮询以下，10G 口必须放弃 32 位，换 `ifHCInOctets`。

## 三个算法，三列结果

三份算法实现各算一遍，同一个区间三列并排。分岔点自己会露出来。

| 版本 | 算法 | 认不认回绕 | 认不认实际间隔 |
|---|---|---|---|
| v1 简单差值 | `(cur-prev) / 标称周期` | 不认 | 不认 |
| v2 时间归一 | `(cur-prev) / 实际间隔` | 不认 | 认 |
| v3 回绕插值 | `补 2^32 后 / 实际间隔`，漏采时按轮数拆段 | 认 | 认 |

1G 口满速、10 秒采一次，第 18.36 秒撞到回绕。`make run` 里的这一段：

```text
tor-a3f-01/Ethernet1/49 · to-spine-a1-49
  ifInOctets 32 位 · 1.00G · 标称周期 10s · 满速回绕周期 34.36s（采集周期红线 17.18s）
  from->to         dt     delta          v1 naive   v2 norm    v3 wrap    flag       判定
  0.0->10.0s       10s    1250000000     1.00G      1.00G      1.00G      -          正常
  10.0->20.0s      10s    -3044967296    -2.44G     -2.44G     1.00G      ◄v2≠v3     回绕 1 圈（+4294967296），v2 在这一格出负数
  20.0->30.0s      10s    1250000000     1.00G      1.00G      1.00G      -          正常
  30.0->40.0s      10s    1250000000     1.00G      1.00G      1.00G      -          正常
```

`-3044967296` 这个负数就是回绕的形状：`205032704 - 3250000000`。补一个量程 `+4294967296` 得到 1250000000 字节，除以 10 秒再乘 8，正好 1.00 Gbps。

两类分岔，各有各的主人：

| 标记 | 谁跟谁分岔 | 成因 | 差多少 |
|---|---|---|---|
| `◄v1≠v2` | 简单差值 vs 时间归一 | 漏采，间隔是标称周期的几倍 | 差 N 倍，`20→60s` 那段 v1 报 800 Mbps，真相 200 Mbps |
| `◄v2≠v3` | 时间归一 vs 回绕插值 | 计数器回绕，或设备重启 | v2 出负数，v3 回到 1.00 Gbps |

10G 口满速、1 秒采一次，回绕点同样落在 `2.0->3.0s`：v2 报 -24.36 Gbps，v3 报 10.00 Gbps。

## 差值为负：回绕还是重启

只看计数器分不开这两件事。加上 `sysUpTime` 就能分开，判据是两条算术：

| sysUpTime | counter | 结论 | 这一段速率 |
|---|---|---|---|
| 增 | 增 | 正常 | 可信 |
| 增 | 减 | 32 位回绕 | 补一个量程，增量不到半量程就可信 |
| 减，`prev + 经过的 tick` 没越过 2^32 | 减 | 设备重启 | 不可信，记 0 |
| 减，`prev + 经过的 tick` 越过 2^32 且实测值落在回绕后 | 增或减 | sysUpTime 自己回绕（497 天一圈） | 可信，不是重启 |

`sysUpTime` 是 32 位 TimeTicks，单位 1/100 秒，满量程 `4294967296 / 100 = 42949672.96 s`，约 497.1 天。设备连开一年半，它会自己归零——把这件事当重启，就是丢一整天数据。

两段样张：

```text
  20.0->30.0s      10s    -3450000000    -2.76G     -2.76G     0          ◄v2≠v3     设备重启：sysUpTime 归零，计数器也回到 0，这一段不可信

  10.0->20.0s      10s    1000000000     800.00M    800.00M    800.00M    -          sysUpTime 回绕（497 天），计数器仍在增长 → 不是重启，速率可信
```

重启那一段的 v3 给 0 而不是补量程。计数器归零了，`600000000 + 4294967296 - 4050000000` 算出来的 845 MB 是幻觉，补一个量程只会把噪声算成流量。

## 采集周期踩红线的样子

`make warn` 打的是同一个 10G 口，采集周期被错配成 10 秒：

```text
tor-a3f-02/Ethernet1/2 · to-srv-a3f-02-nic1
  ifInOctets 32 位 · 10.00G · 标称周期 10s · 满速回绕周期 3.44s（采集周期红线 1.72s）
  from->to         dt     delta          v1 naive   v2 norm    v3 wrap    flag       判定
  0.0->10.0s       10s    -384901888     -307.92M   -307.92M   3.13G      ◄v2≠v3     观测增量 3910065408 ≥ 量程一半 2147483648，圈数不可判，这一段不可信
  10.0->20.0s      10s    -384901888     -307.92M   -307.92M   3.13G      ◄v2≠v3     观测增量 3910065408 ≥ 量程一半 2147483648，圈数不可判，这一段不可信
  小结：回绕 0 · 重启 0 · uptime 回绕 0 · 丢样 0 段 · 乱序 0 处 · 不可信 2 段 · 峰值 不可用（全段不可信）

⚠ tor-a3f-02/Ethernet1/2：采集周期 10s ≥ 满速回绕周期 3.44s（2^32 / 1250000000 B/s）的一半 1.72s，这个端口跑满时圈数不可判；采集周期必须小于 1.72s，或换 64 位计数器
⚠ tor-a3f-02/Ethernet1/2：2 段观测增量超过量程一半（32 位计数器 2147483648），回绕次数不可判，已标不可信
```

真相是 10.00 Gbps，v3 补一圈只补到 3.13 Gbps，差 3.2 倍。这个错误格外危险：差值是正的，速率低于线速，任何合理性检查都放它过去。挡住它的只有两条规则——端口级的配置红线（采集周期 ≥ 半圈就报警），区间级的半量程判定（观测增量 ≥ 2^31 就判不可判）。

两级告警是分开的，别混：

- 配置红线按线速算，一个端口一条。`spine-01/Ethernet1/1` 跑 1.6 Gbps，数字全对，红线照样报——它跑满就会错。
- 区间可信度按观测增量算，一段一条。`spine-01/Ethernet1/1` 除重启段之外都可信。

宁可让面板缺一格，不要一格错数。落盘那一份带 `trusted=false`、`ambiguous=true`，机器读的时候补不补，是读取方的决定。

## 错包归因：四类证据，四个方向

`ifInOctets` 涨得对不对是一件事，涨的里面有多少是坏包是另一件事。七份样本覆盖五个结论：

| 证据组合 | 归属 | 下一步 |
|---|---|---|
| 校验失败成片，符号错几乎为 0 | 线缆（含连接器、端面） | 换纤、清端面，两端对换定死哪一头 |
| 符号错 / 校验失败帧 ≥ 8 | 模块（收发器、编码层） | 换模块，先换收端 |
| 出向队列尾丢，校验失败 0 | 拥塞（出口队列溢出） | 看利用率与微突发，调队列或改 ECMP 权重 |
| 入向缓存不足丢，校验失败 0 | 拥塞（入口超订） | 算超订比，入口限速或换上行 |
| 交换机全干净，主机报接收丢弃 / 重传 | 主机（socket 缓冲、软中断） | 查 `netstat -s` 的 receive buffer errors |

```text
错包归因
  port                               util   fcs_ppm  sym      qdrop    hdrop    owner  证据 ｜ 下一步
  tor-a3f-01/Ethernet1/7             60%    90.0     12       0        1200     cable  校验失败帧 4210（90.0 ppm），符号错 12（每坏帧 0.00 个，低于阈值 8）——编码层干净，坏在帧上｜下一步：换纤、清端面；光纤看收发功率，铜缆看长度与串扰
                                                                                       还有：主机侧也报了 1200 个接收丢弃，坏包会一路传染到主机
  tor-a3f-01/Ethernet1/8             40%    20.0     2400000  0        0        module 符号错 2400000，校验失败帧 1800，每个坏帧摊到 1333 个符号错（阈值 8）——编码层在成片出错｜下一步：换模块，先换收端；两端对换能一次定死是哪一头
  tor-a3f-02/Ethernet1/1             4%     0.0      0        0        33000    host   交换机侧校验失败 0、符号错 0、队列丢 0，主机报了 33000 个接收丢弃 / 8400 次重传｜下一步：查主机 socket 缓冲与软中断分布（netstat -s 的 receive buffer errors），交换机不是瓶颈
  spine-01/Ethernet1/48              64%    4.5      20       60000    0        cable  校验失败帧 900（4.5 ppm），符号错 20（每坏帧 0.02 个，低于阈值 8）——编码层干净，坏在帧上｜下一步：换纤、清端面；光纤看收发功率，铜缆看长度与串扰
                                                                                       还有：同时有丢弃 60000 个（300.0 ppm），物理层修好之后拥塞问题还在
```

每百万帧的算术，读者要能自己代入：

```text
帧错率 = 校验失败帧 / 窗口内单播帧 × 1e6
       4210 / 46800000 × 1e6 = 90.0 ppm
利用率 = 窗口内字节 × 8 / (线速 × 窗口时长)
       22500000000 × 8 / (1e9 × 300) = 60%
```

三条门限写在 `attr.go` 里，改之前先想清楚代价：

- 帧错率 < 1 ppm 当噪声，不开工单。样本里 1G 口 300 秒 4680 万个帧，1 ppm 就是 47 个坏帧，TCP 重传能吞掉。
- 帧错率 > 100 ppm 必须换件，门限之上程序会额外喊一句。90 ppm 那条样本是 `4210 / 46800000`，每 1.1 万个帧坏一个，贴着线下面，照样是换纤的事——门限管的是提醒语气，不是换不换。
- 符号错 / 校验失败帧 ≥ 8 判模块。坏符号通常多于坏帧，比例接近 1 或反过来，问题不在编码层。

主结论只写一个，次要发现单独列。「纤有问题，同时队列在丢」那一条，主结论是线缆，`还有：` 那行写拥塞。修完物理层拥塞还在，不写清楚，值班人换完纤就走人。

## 样本格式

`samples/counters.json` 是一组采样序列，每个端口一段：

| 字段 | 含义 |
|---|---|
| `device` / `if_name` / `if_alias` / `if_index` | 端口身份。主键用 `device + if_name`，不用 `if_index` |
| `counter` / `counter_bits` | `ifInOctets` 是 32 位，`ifHCInOctets` 是 64 位 |
| `speed_bps` | 线速。回绕周期与线速上限都从这里推 |
| `note` | 这一段样本注入的真实情况，判定逻辑看不到 |
| `samples[]` | `t_ms` 相对起点的毫秒数、`value` 计数器值、`sys_uptime_ticks` 单位 1/100 秒 |

`samples/errors.json` 是错包计数，一个端口一条，字段按四个归属分组：

| 组 | 字段 |
|---|---|
| 物理层 | `fcs_errors`（CRC / FCS / 对齐错合并）、`symbol_errors` |
| 拥塞 | `out_queue_discards`（出向队列尾丢）、`in_buffer_discards`（入向缓存不足）、`out_discards`（出向丢弃总数） |
| 主机 | `host_rx_drops`、`host_retransmits` |
| 分母 | `in_octets`、`in_ucast_pkts`、`window_s`、`speed_bps` |

`samples/truth.json` 记注入的真值：`wraps`、`resets`、`uptime_wraps`、`gaps`、`reorders`，外加一个 `unjudgeable` 标记——标了它的端口，判定层必须告警而不是给数。`make run` 最后拿判定结果与它对账。

## 留的五个坑

**1. 半量程规则会误伤真跑满的慢采集。** 10G 口 2 秒采一次、真跑到 10 Gbps，每段增量 2.5e9 > 半量程 2.147e9，全部判不可信，其实一点问题没有。保守派的代价是假缺口，反过来就是假数据。这一格我选假缺口。

**2. 重启后计数器不一定从 0 起。** 不少平台重启后计数器从固件基线或硬件保留值开始，`cur` 甚至大于 `prev`。这时 `sysUpTime` 已经归零，但差值看起来正常，差值里混着一段假流量。样本里没有这一型，因为它的正确处理不在算术里，在「重启后第一次采样必须丢弃」这条规则里。

**3. `sysUpTime` 和计数器不是同一次快照。** 真实采集是两个 GET（或两个 GetBulk 里的两列），中间隔几十到几百毫秒。10G 口满速时，100 毫秒就是 125 MB，跟一次采样的增量同一量级。用 `sysUpTime` 判重启，判据本身带着这个抖动。样本里两个值是精确对齐的，真实世界不是。

**4. 丢样插值是均摊假设。** `20→60s` 那段漏了 3 轮，v3 把 1e9 字节均摊成 4 段 200 Mbps。真相可能是开头 10 秒跑满 800 Mbps、后面 30 秒一个字节没动，`800 Mbps × 10s = 1e9` 字节，总量一样。插值只保证总量对，形状是编的。要看形状，只能把采集周期压到故障时间尺度以下（第 40 课的微突发就是这个问题的极端版）。

**5. 符号错阈值 8 是经验值。** 没有光功率、没有误码率（BER）读数时，模块劣化和端面脏会互相冒充：两者都让校验失败涨。这条判据的置信度取决于手上有多少别的证据，`samples/errors.json` 里那两个端口是靠符号错数量级分开的，真实设备上经常分不开。

## 命令行参数

| 参数 | 默认 | 作用 |
|---|---|---|
| `-samples` | `samples/counters.json` | 采样序列 |
| `-errors` | `samples/errors.json` | 错包计数样本 |
