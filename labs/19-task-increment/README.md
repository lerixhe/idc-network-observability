# 19-task-increment · 任务增量与坏点替换

第 51 课配套实验。三件事：增量下发的字节账、坏点两问四格、震荡抑制的「换三次就停」。

零外部依赖，纯本地计算。

## 跑起来

```bash
cd labs/19-task-increment
make run     # 三个场景
make test    # go vet + go test
make clean   # 删 out/
```

## 场景一：增量 vs 全量

每探针 30 条任务、10 万探针，一次变更移机 1 条任务：

```text
全量重推   1216 字节/探针 × 100000 = 121.6 MB
差量下发     56 字节/探针 × 100000 =   5.6 MB（新增 1、删除 1）
比值        21.7×
变更比例    7%（超过 10% 退回全量）
```

任务集整体重排时，变更比例 200%，程序直接判定「退回全量推送」。第 51 课那次事故就是这个场景：差量包涨 12 倍，编码耗时从 2 秒到 40 秒。

## 场景二：坏点两问四格

```text
单探针全挂、同机架都正常     → 探针侧故障      换点
同机架多台同时全挂           → 环境故障        不换点
探针活着但全挂（位置问题）   → 网络侧故障      不换点
部分目标失败                 → 目标侧故障      不换点
```

只有第一行换点。第二行是第 51 课那个「43% 误判」的来源：同机架两台探针同时挂了，被当成环境故障。

## 场景三：震荡抑制

```text
第 1 轮：换点，断流 10 秒
第 2 轮：换点，断流 10 秒
第 3 轮：换点，断流 10 秒
第 4 轮：停止，转人工
合计：自动换点 3 次，断流 30 秒
```

不抑制的话 6 轮全部换点，断流 60 秒，任务在 6 台机器之间迁移。

## 这个实验故意留的坑

1. **差量按 TaskID 比较，内容变化检测不到**。同一个 TaskID 换了 target、改了周期，`Diff` 认为是「没变」。真实系统要靠版本号 + 内容哈希，或者每次变更重建 TaskID。这个坑在本实验里是硬编码的简化，落到生产必须在任务记录里带内容哈希。
2. **字节数是模型值**（任务 40 字节、差量条目 20 字节）。真实 protobuf 编码会小一截，但比值量级不变。
3. **换点次数没有时间衰减**。一个任务三天里换了 3 次（每次都不同原因）也会被停掉。真实系统要加窗口：24 小时内 3 次才算震荡。
4. **坏点判定的「同机架」假设机架有冗余探针**。单机架只有一台探针时，第二问永远答成「无对照」，判定退化成只看第一问。
5. **收敛时间的三段是常量**，没有模拟排队与重试放大。
