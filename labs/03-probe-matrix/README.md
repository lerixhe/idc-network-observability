# 03-probe-matrix · 探测矩阵与健康评分

第 10、11、14 课配套实验。干两件事：

1. 把一份拓扑翻成探测矩阵——谁探谁、跨过哪些链路、覆盖率多少、一年花多少钱
2. 读一轮探测结果，给每对打分，再把**探针侧异常**与**网络侧异常**分开

第 10 课说「探不到那条链路，你就没法说它好」。这个实验把「探得到多少」算成一个能贴进周报的数：节点对覆盖 60.3%，链路覆盖 100%，一天 142 MB 存储。

全程纯本地计算，一个包都不发，不碰外网。探针是仿真的，故障是样本里注入的。

## 跑起来

```bash
cd labs/03-probe-matrix
make run     # 生成矩阵 + 跑一轮探测 + 打分归因，产物落 out/
make test    # vet + 单元测试
make demo    # 多打归因汇总、节点判定与真值对账
make cost    # 换四个探测间隔看成本怎么变
make clean   # 删 out/
```

零外部依赖，Go 1.22 够。

## 谁探谁：三条规则，顺序不能换

```text
1. 同机架不探              同架流量不过上行链路，探它测到的是本机网卡
2. 上行必探                目标层级比源小，一律 1.0
3. 其余按层抽样            查下面那张表
```

第 1 条压过第 2 条。服务器探本机架的 TOR 是上行，但更属于同架，所以不探。代价在坑里第 2 条。

| 探针 \ 目标 | border | spine | tor | server |
|---|---|---|---|---|
| **server** | 上行 | 上行 | 0.50 | 1.00 |
| **tor** | 上行 | 上行 | 0.10 | 0.10 |
| **spine** | 上行 | 0 | 0.25 | 0.05 |
| **border** | 0 | 0.25 | 0.25 | 0.05 |

标「上行」的格子不看表，一律 1.0。「上行」的判据是目标层级更小，外加一个例外：服务器探**不是本机架**的 TOR 算横向，按 0.50 抽。

`server → server` 写 1.00，因为同机架已经排掉了。这一格一抽样，端到端覆盖率立刻掉一半——PingMesh 那张网里面数最多的就是它。

`spine → spine` 与 `border → border` 写 0。同层没有直连，探出来的路径要绕一层再绕回来，那条路径上没有任何一段是真实转发走的。

抽样用名字哈希，不用随机数：同一个 (src,dst) 明天再生成一遍还是同一条结论，否则覆盖率曲线画的其实是抽样噪声。

## 覆盖率：两个数，链路那个更要紧

```text
节点对覆盖率 = 选中对数 ÷ N×(N-1)          = 760 / 1260 = 60.3%
链路覆盖率   = 被跨过的链路 ÷ 总链路数       = 44 / 44   = 100.0%
```

节点对覆盖率回答「探了多少对」，链路覆盖率回答「有没有整条链路从来没被跨过」。第 10 课的举证包靠后者：一条从没被跨过的链路，出问题时你连一句「当时它还在」都说不出来。

省下来的 39.7% 拆成两段，别混着算：

| 规则 | 筛掉 | 占全量 |
|---|---|---|
| 同机架不探 | 120 对（server↔同架 server 72 + server↔本架 tor 48） | 9.5% |
| 层间抽样 | 1140 → 760，筛掉 380 | 30.2% |

同机架只省 9.5%。**真正省包的是层间抽样**，这一点和直觉相反：TOR 探 server 抽 0.10、spine 探 server 抽 0.05，把 144 + 96 对压成了 12 + 5 对。

## 成本：带宽可以忽略，存储才是账单

```text
pps       = 对数 ÷ 间隔秒数
带宽 bps   = pps × 74 字节 × 8          （Eth 14 + IP 20 + UDP 8 + 载荷 32）
带宽占比   = 探测带宽 ÷ 拓扑总带宽
记录数/天  = 对数 × 86400 ÷ 60          （60 秒聚合一条）
存储/天    = 记录数 × 单条字节数
```

代入 760 对、间隔 1 秒：

```text
pps    = 760 ÷ 1 = 760
带宽    = 760 × 74 × 8 = 449,920 bit/s ≈ 450 kbit/s
占比    = 449,920 ÷ (5000 × 10⁹) = 0.00000009 → 0.09 ppm（百万分之 0.09）
记录数  = 760 × 1440 = 1,094,400 条/天
聚合存储 = 1,094,400 × 130 B = 142.3 MB/天 → 30 天 4.27 GB
逐包原始 = 65,664,000 × 90 B = 5.9 GB/天 → 30 天 177 GB
```

`make cost` 的四个间隔：

| 间隔 | 包速率 | 带宽 | 聚合存储/天 | 逐包原始/天 |
|---|---|---|---|---|
| 1s | 760 pps | 450 kbit/s | 142 MB | 5.9 GB |
| 5s | 152 pps | 90 kbit/s | 142 MB | 1.2 GB |
| 10s | 76 pps | 45 kbit/s | 142 MB | 0.6 GB |
| 60s | 13 pps | 7.5 kbit/s | 142 MB | 0.1 GB |

聚合存储那一列不随间隔变：60 秒一条是固定口径，间隔只决定窗口里塞几个包。间隔拉到 60s，窗口里只剩 1 个包，丢包率只有 0 和 100% 两个取值——省下来的存储，是拿精度换的。

**带宽占比 0.09 ppm，等于不花钱。** 探测的代价不在带宽，在包数压设备 CPU、在存储。十万台机器两两全探是 10¹⁰ pps，是这套矩阵的 1300 万倍，这才是「撒不出去」的含义。

## 健康评分：四个维度，权重和阈值都写死

| 维度 | 权重 | 算式 | 满分条件 | 零分条件 |
|---|---|---|---|---|
| 丢包 | 0.40 | 分档，见下表 | 0 | ≥ 10% |
| 时延 | 0.30 | `100 × (3.0 - r) / (3.0 - 1.35)`，`r = p99 / 基线` | r ≤ 1.35 | r ≥ 3.0 |
| 抖动 | 0.15 | `100 × (0.6 - j) / (0.6 - 0.1)`，`j = jitter / p50` | j ≤ 0.10 | j ≥ 0.60 |
| 覆盖 | 0.15 | `100 × 实收样本 / 期望样本` | 100% | 0% |

丢包维度分档，不插值：

| 丢包率 | 分 | 理由 |
|---|---|---|
| 0 | 100 | — |
| ≤ 1/sent（60 个包里丢 1 个） | 85 | 落在泊松噪声里，不判异常 |
| ≤ 2% | 70 | 有点丢，还没到失败线 |
| ≤ 10% | 40 | 明确有问题 |
| > 10% | 0 | 这条链路在坏 |

分档的理由在 60 个包的样本上很实在：丢 1 个是 1.7%，丢 2 个是 3.3%，线性插值会把这点差异放大成十几分，工程上它们只是「噪声」和「有点丢」。

缺数据的维度不打分，权重按剩下的归一。一对探测没给基线，时延维度是 `-1`，剩下三项按 0.4/0.15/0.15 归一——不能把「不知道」算成 0 分，那是监控里最不该犯的错。

分级：`≥ 90 healthy`、`70–89 degraded`、`< 70 faulty`。

## 归因：一张 2×2 表

每台机器既是探针又是目标。它的行是「它探出去」，列是「别人探它」。两维交叉，四种答案：

|  | 列正常（别人探得到它） | 列红（别人探不到它） |
|---|---|---|
| **行正常**（它探得出去） | `ok` | `target_side` —— 网卡单通、上游 ACL |
| **行红**（它探不出去） | `probe_side` —— agent 挂了、探针网卡坏 | `host_down` —— 整机断电、重启 |

第五类 `network_side` 落在表外：行和列都不红，只有单对失败。

判定顺序就是排除法，按「结论有多硬」排：

```text
1. host_down    行红且列红             整机没了，其他结论都不用谈
2. probe_side   行红且列绿             先怀疑自己的探针
3. target_side  列红且行绿             再怀疑对端
4. network_side 单对失败               最后才怪路径
5. ok
```

阈值：一对丢包 ≥ 2% 算失败；一个节点的行/列失败率 ≥ 90% 算红，≤ 50% 算绿；少于 3 对不给节点定罪。四个数都在 `score.go` 的常量区，改完记得重跑样本看误判怎么变。

**两轮统计**是这里唯一需要解释的设计。第一轮用全部对算行/列失败率，只为找出 `host_down`；第二轮把已经判死的机器从所有人的分母里剔掉，再算一次。不做第二轮，一次机房断电能让半个集群的行失败率都虚高，进而被判成探针侧异常——误报的数量正好等于受影响的对数。

## 样本格式

### `samples/topology.json`

两个数组。36 个节点、44 条链路。

```json
{"name": "tor-a03", "role": "tor", "pod": "pod-a", "rack": "rack-a03"}
{"from": "tor-a03", "to": "spine-a1", "bw_gbps": 100}
```

| 字段 | 含义 |
|---|---|
| `name` / `role` | `border` / `spine` / `tor` / `server`。层级（tier）由角色推出来，样本里不写第二遍 |
| `pod` | 故障域。跨 pod 的探测要过 border |
| `rack` | 只有 tor 与 server 有。同机架不探全靠这一格 |
| `bw_gbps` | 链路带宽，成本占比的分母。接入链路 25G、TOR 上行 100G、spine 上行 400G |
| `uplinks` | 接入链路也写进来。漏掉它们，覆盖率的分母少 24 条 |

加载时校验：重名、未知角色、TOR 缺机架、机架无 TOR、跨层直连（server 直连 spine）、链路重复、服务器没连本机架 TOR。任何一条不过就报错退出，不做「尽量跑」。

### `samples/incidents.json`

剧本。窗口、间隔、四类注入事件。

```json
{"kind": "link_loss", "links": [["tor-a03", "spine-a1"]], "loss": 0.12, "latency_us": 90}
```

| kind | 注入什么 | 矩阵里的样子 |
|---|---|---|
| `host_down` | 整机断电（3 台） | 行无记录，列全丢 |
| `probe_agent_down` | agent 挂了（1 台） | 行无记录，列全正常 |
| `nic_rx_down` | 接收方向不通（1 台） | 行正常，列全丢 |
| `link_loss` | 一条光纤劣化，12% 丢包 | 跨这条链路的对全部丢包 + 时延涨 90µs |

窗口 60 秒、间隔 1 秒就是每对 60 个包。这个口径写在样本里，不藏在代码里——它同时决定「丢包率怎么算」和「存储花多少」。

## 这个实验故意留的坑

1. **12% 丢包的链路，有一对只丢了 1 个包**。60 个包的窗口里，丢包数是离散的：期望 7.2 个，真实落在 5~10 个之间，偶尔一个不丢。对账里「漏判 1」就是这么来的——那一对丢了 1 个包，按噪声处理判了 ok。要抓它只能加长窗口或加密采样，第 10 课「精度」那一条说的就是这个。
2. **同机架不探把接入链路也关掉了**。服务器探本架 TOR 被否决，接入链路只能靠跨架探测顺带跨过。它 100% 被覆盖，但没有一条探测是专门测它的——接入链路单独坏了，看到的是「这台机器到所有地方都丢一点」。
3. **探针掉线在矩阵里是一整行空白**。不先判行，25 条空白会变成 25 条网络告警。第 14 课整节课讲这一件事。
4. **整机断电的行和列同时红**。只判列，一次机房断电会同时产出「探针侧异常」和「三个对端侧异常」两批工单，然后值班人学会无视这批告警。
5. **ECMP 在这里被抹平了**。每条对固定捆一条哈希路径（邻居展开顺序由名字哈希定），另一条等价路径坏了，覆盖率和健康分一点反应都没有。这是第 12 课的活，`04-ecmp-hash` 会把这条假设拆开。
6. **链路覆盖率 100% 不等于每条链路被单独测过**。「被跨过」和「被测量」是两件事：一条链路在 500 条对的路径里被跨过，它的质量仍然只能从端到端的丢包率里反推。
7. **共同链路段只是最大公约数**。92 条异常对全部指向 `spine-a1↔tor-a03`，看着像铁证；换一份抽样，两条不同的链路完全可以承载同一批对。第 12 课会让这一招彻底失效。
8. **间隔决定精度的下限**。`make cost` 里间隔 60s 那一行只花 7.5 kbit/s，代价是窗口里只剩 1 个包，丢包率只有 0 和 100% 两种取值。
