## 这一篇解决什么

SNMP 是最老、最广、最不体面的一层。它慢、它土、它经常是设备唯一开放的接口。第二部分已经用过它的一个 OID 讲链路状态，这一篇讲协议本身和工程约束，然后往 gNMI 的订阅模型过渡。

三个坑必须先说清：

**OID 是树形命名空间**，一个表要按列走。`ifIndex` 是本地索引，换设备、换板卡就变——指标主键绝不能是它，要用 `ifName`/`ifAlias` 映射。这个坑几乎所有新平台都踩过一次：设备重启后端口编号重排，历史曲线接错了对象。

**采得全**和**别把设备采死**是一对矛盾。老 TOR 的 SNMP 单线程，一次 GetBulk 要 50 条，管理面 CPU 就到 30%。做法是按设备能力分档限流、失败设备降频隔离、把「不可达」和「响应慢」分开统计。

**计数器会回绕**。32 位计数器最大约 42.9 亿，1G 口满速 34 秒绕一圈，10G 口 3.4 秒。采集周期必须小于回绕周期的一半，否则速率算出来是负数。

## 配套实验

- `labs/06-snmp-walk`：对着内置 agent 按列遍历 `ifTable` + `ifXTable`，四档限流排队不丢，样本含一台响应慢、一台不可达、一台换板后 `ifIndex` 重排
- `labs/07-counters`：三个版本的速率算法同场对比，样本埋了 1G/10G 回绕、重启清零、漏采、乱序，错包四类归因

## 读完你应该能

- 解释为什么指标主键不能用 `ifIndex`，以及换板卡之后历史曲线会错成什么样
- 算出一个端口的回绕周期，并据此定出采集周期上限
- 在「采得全」和「把设备采死」之间给出一份分档限流方案
- 说清订阅式采集比轮询好在哪、代价在哪
