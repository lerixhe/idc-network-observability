第 08、09 课判定设备重启时用过「按模 2^32 算增量」，那只是预热。这一课把回绕摊开：在你的口上它多久绕一圈，绕的时候速率算成什么，绕和清零怎么分开。

## 32 位装得下 34 秒，装不下一次轮询

计数器存的是累计字节数。32 位无符号整数表示 0 到 4,294,967,295，约 4.29 GB 的字节计数。装满要多久，只取决于每秒进多少字节。

回绕周期 = 2^32 ÷ 每秒字节数 = 4,294,967,296 ÷ (端口速率 bit/s ÷ 8)。代入 1G：4,294,967,296 ÷ 125,000,000 = 34.36 秒；10G 十分之一，3.436 秒；100G 再缩一个数量级，0.344 秒。

| 端口 | 每秒字节 | 回绕周期 | 60 秒里绕几圈 |
|---|---|---|---|
| 1G | 125,000,000 | 34.36 秒 | 1.75 |
| 10G | 1,250,000,000 | 3.44 秒 | 17.5 |
| 25G | 3,125,000,000 | 1.37 秒 | 43.7 |
| 40G | 5,000,000,000 | 0.86 秒 | 69.9 |
| 100G | 12,500,000,000 | 0.34 秒 | 174.6 |

按满线速算，速率低就等比拉长。周期一超过回绕周期，模运算剥掉整数圈后的余数与真实流量无关。

64 位：2^64 ÷ 12,500,000,000 ≈ 1.476 × 10^9 秒，46.8 年。

## 采集周期卡在回绕周期的一半

判据只有一行：`T < 回绕周期 ÷ 2`。

一半是给丢采样留的：超时丢一轮，实际间隔从 T 变成 2T，模运算要唯一就得 2T < 回绕周期。这是采集器里唯一值得固定下来的常数。

| 端口 | 回绕周期 | T 上限 | 60 秒轮询 | 120 秒轮询 |
|---|---|---|---|---|
| 1G | 34.36 秒 | 17.2 秒 | 超 3.5 倍 | 超 7 倍 |
| 10G | 3.44 秒 | 1.72 秒 | 超 35 倍 | 超 70 倍 |
| 100G | 0.34 秒 | 0.17 秒 | 超 349 倍 | — |

结论很硬：**32 位计数器在 10G 以上端口没有可用的采集周期**。这正是 `ifXTable` 里那组 64 位计数器的存在理由。

「超标」的含义是无意义：你拿到半圈余数，而它长得像正常数字。

## 速率算法的三个版本，只有第三个能上生产

**版本 1：简单差值。** `rate = v1 − v0`。单位就错了，字节数不能当速率用；数值还随采集周期线性放大。同一份 960 Mbps 流量，15 秒周期存 1,800,000,000，30 秒周期存 3,600,000,000。这个错法低级，出现率却高：「除以周期」被留给了下游。

**版本 2：按时间归一。** `rate = (v1 − v0) ÷ Δt`，差值按有符号整数算。1G 口满速 960 Mbps，30 秒轮询：前一段算出 120,000,000 B/s 是对的，34 秒后绕一圈，下一段算出 −23,165,576 B/s。满速下一个 30 秒区间跨一次回绕的概率是 87%（30 ÷ 34.36），三种处置全错——clamp 成 0，近九成采样点贴着零；整点丢弃，放弃 87% 的点；原样入库，看板上全是向下尖刺。

**版本 3：回绕检测加插值。** 无符号相减拿到模 2^32 的增量，再用 `sysUpTime` 排掉清零，用前置条件排掉多重回绕。

```go
const (
	wrap32      = 1 << 32
	windowTolCs = 3000  // 30 秒窗口，留一倍余量
	rebootCs    = 30000 // 5 分钟，超过判定为重启（第 08 课口径）
)

// speed 单位 bit/s。前置条件：这个端口配这个间隔还能不能用 32 位
func usable32(speed uint64, dtSec int64) bool {
	return speed*uint64(dtSec) < wrap32*8 // 等价于 dt < 回绕周期
}

func rateV3(a, b sample) (float64, int64, error) {
	dUp := b.upTime - a.upTime
	switch {
	case dUp > rebootCs:
		return 0, 0, errReboot // 计数器清零，按重启处理
	case dUp > windowTolCs:
		return 0, 0, errUncertain // 窗口异常，这一段不判
	}
	if !usable32(b.speed, b.at-a.at) {
		return 0, 0, errMultiWrap // 中途绕了不止一圈，模运算无解
	}
	d := b.bytes - a.bytes // uint32 相减，溢出即回绕
	dt := float64(b.at - a.at)
	wrapAt := int64(-1)
	if b.bytes < a.bytes { // 区间内跨了一次 2^32，插值求时刻
		frac := float64(wrap32-a.bytes) / float64(d)
		wrapAt = a.at*1000 + int64(frac*dt*1000)
	}
	return float64(d) / dt, wrapAt, nil
}
```

`d := b.bytes - a.bytes` 就是全部魔法，Go 的 `uint32` 相减天然按模 2^32 回绕。Java、Python、C# 里整数提升成有符号数，要显式 `(b - a) & 0xFFFFFFFF`。

**上限校验抓不到多重回绕。** 很多人写 `if rate*8 > speed` 就当防住了，它永远不成立：真实增量 Δ_true = Δ_mod + k·2^32（k ≥ 0），剥掉 k 圈后 Δ_mod ≤ Δ_true ≤ speed × Δt，算出来只会偏小。10G 口、30 秒轮询、真实速率 8,000,000,000 B/s（64 Gbps）的账：

| 项 | 算式 | 结果 |
|---|---|---|
| 真实增量 | 8,000,000,000 × 30 | 240,000,000,000 字节 |
| 模 2^32 取余 | 240,000,000,000 − 55 × 2^32 | 3,776,798,720 |
| 算出速率 | 3,776,798,720 ÷ 30 | ≈ 1.007 Gbps |

1.007 Gbps 落在 10G 额定范围里，任何上限校验都放行，而它实际跑 64 Gbps。能抓住它的只有 `speed × Δt < 2^32`，用端口速率和实际间隔算。按端口算：1G 管理口与 100G 上行的结论相反。

插值另有用处：拿到回绕时刻，才能把 Trap 对到「绕圈前」还是「绕圈后」，把跨区间增量切开，否则一次回绕让相邻两个区间各错一半（第 46 课）。

## 归零和回绕是两件事，判据在 sysUpTime

设备重启，计数器从 0 开始。32 位上它与回绕在数值上完全一样：后一个值比前一个小。

64 位不必纠结：46.8 年才绕一圈，负差值只能是清零，看符号就够。

32 位必须借 `sysUpTime`，判据按模 2^32 算增量：

| 条件 | 判定 | 处置 |
|---|---|---|
| Δup ≤ 3000 | 正常推进（30 秒窗口加一倍余量） | 直接算速率 |
| Δup > 30000 | 设备重启过（5 分钟以上） | 标 gap，不写速率 |
| 3000 < Δup ≤ 30000 | 判定不了 | 这一段丢弃，不猜 |

中间那档必须留：周期被临时拉长、管理面卡顿、NTP 步进都会落进来。判定不了就不判断。

两个字段交叉，四种组合各有各的处置：

| Δ计数器 | ΔsysUpTime | 判定 | 这一段怎么办 |
|---|---|---|---|
| 正 | 正常 | 无异常 | 直接算 |
| 负 | 正常 | 回绕（32 位） | 模 2^32 算，再过前置条件 |
| 负 | 远超窗口 | 设备重启 | 标 gap，不写 0，不写速率 |
| 正 | 正常但前置条件为假 | 中途多绕了一圈 | 标 gap，换 64 位或缩短周期 |

第三行是最贵的一处误判：清了零的计数器过了模运算，会给出一个看着正常的速率（判据一节有完整算例），能拆穿它的只有 `sysUpTime`。

写 0 等于告诉告警「流量归零」，写一个假速率等于编数，只有标 gap 是事实。gap 是时序库里的合法状态，缺了它，缺数据被当成零。

## 64 位、两个 OID、重复计数

`ifInOctets` 32 位，`ifHCInOctets` 64 位，两个都在标准 MIB 里，说「语义只差宽度」只对了一半。

老设备的 32 位计数会卡死：部分老 TOR 的 `ifInOctets` 超过某个值就不再增长，或回绕后从非零值继续，曲线长时间水平，与流量无关。支持 64 位就一律用 64 位。混用还会在切换点造出阶跃——一块看板 60% 端口走 64 位、40% 走 32 位，两边采样误差差一个数量级，那个阶跃会被第 39 课的基线学成「正常形态」，之后真故障反而不报警。

计数单位与线速单位也不同。`ifHCInOctets` 计帧字节（含 FCS），不含前导码与帧间隙。1G 口跑 64 字节小包满线速，帧速率 = 1,000,000,000 ÷ (84 × 8) = 1,488,095 帧/秒（64 + 8 + 12 = 84 字节），计数器只读到 1,488,095 × 64 = 95,238,080 B/s = 761.9 Mbps，利用率 76.2%。链路真的满了，计数器报 76.2%；换 1518 字节大包，这个折算几乎为零。「利用率 80%」在小包业务上可能已是百分百，第 36 课回来算这笔账。

**重复计数单独说一句**：`ifInErrors` 已包含 CRC 错误，加上 `dot3StatsFCSErrors` 等于双倍。规矩是选一条主链做趋势，其余只做归因细分，两个错误类计数器永不相加。私有 OID 上重复更严重——出口队列丢弃常同时进 `ifOutDiscards` 和一个厂商私有计数器，跨厂商比较只能用标准 OID。

## 错包归因：errors 归线，discards 归拥塞

端口有错包，第一反应是换模块。一半的时候错在归因。先分两类：`errors` 是帧本身坏了（线、模块、协商），`discards` 是帧好的但没地方放（拥塞、缓存满）。两个数合成一个「丢包」，方向就没了。

| 计数器 | 谁丢的 | 判据 | 归属 |
|---|---|---|---|
| `dot3StatsFCSErrors`（CRC） | 光模块、光纤、跳线、接头 | 单端增长，另一端不涨 | 线或模块 |
| `dot3StatsSymbolErrors` | 编码层：收光不足、模块劣化 | 与收光曲线同步 | 模块 |
| `dot3StatsAlignmentErrors` | 帧边界错位，通常伴随 CRC | 与 CRC 同源同向 | 线或模块 |
| `ifInDiscards` / `ifOutDiscards` | 出口队列满、缓存耗尽 | 与流量峰值同步，CRC 不涨 | 拥塞 |
| 队列深度、buffer 水位（无标准 OID） | 芯片共享缓存被抢空 | 毫秒级尖峰，秒级轮询采不到 | 拥塞（第 40 课） |

三条判据，前两条定九成：

1. **CRC 只在一端涨** → 收侧的光或线，换模块、擦接头、换跳线。两端都涨 → 大概率问题在对端发送侧或中段传输。
2. **discards 涨而 CRC 不涨** → 拥塞，查队列与带宽，不要换模块。
3. **丢包只在毫秒级出现** → 微突发，60 秒轮询看不出变化，得靠队列深度与 buffer 水位（第 40 课）。

会失败的样子：某条上联每小时 200 个 CRC，团队换了三次光模块、两次跳线，一周没解决。翻 `ifOutDiscards` 同步在涨——根因是出口拥塞，CRC 只是缓存溢出的副产品。三次换件按一次 40 分钟窗口算，两小时白费，真问题是带宽。

配套实验 `07-counters` 给一组录好的采样序列，埋了回绕、清零、gap、乱序、判定不了五类样本，同一份输入版本 2 与版本 3 的曲线能差一半。

## 判据

1G 端口，`ifInOctets` 32 位，间隔 15 秒：

| 时刻 | `sysUpTime` | `ifInOctets` |
|---|---|---|
| 14:00:00 | 18,000,000 | 4,180,000,000 |
| 14:00:15 | 18,001,500 | 1,685,032,704 |
| 14:00:30 | 18,003,000 | 2,585,032,704 |
| 14:00:45 | 900 | 40,000 |
| 14:01:00 | 2,400 | 130,000,000 |

四问各写两行：

1. 14:00:00 → 14:00:15 的速率是多少，用了哪一步？
2. 14:00:15 → 14:00:30 有没有异常？
3. 哪一段不可信，判定用了哪个字段、阈值取多少？
4. 只给你版本 2 的算法，这条曲线画成什么样？

验收：第一问 960 Mbps 且点明「无符号相减即模 2^32」；第二问 480 Mbps；第三问第三段不可信、判据 `ΔsysUpTime`、处置是标 gap，不写 0。

::: details 参考

1. 增量 (1,685,032,704 − 4,180,000,000) mod 2^32 = 1,800,000,000，÷ 15 = 120,000,000 B/s = 960 Mbps。
2. 增量 900,000,000，÷ 15 = 60,000,000 B/s = 480 Mbps，未回绕。
3. 第三段（14:00:30 → 14:00:45）不可信。`ΔsysUpTime` = (900 − 18,003,000) mod 2^32 = 4,276,965,196，远超 30000，判定重启、计数器清零，标 gap。误用回绕算法这里是 113,998,306 B/s ≈ 912 Mbps，看着正常；`1G × 15 s = 1.875 GB < 2^32` 这条前置条件也成立，两道校验都放行。
4. −2,494,967,296 ÷ 15 = −166,331,153 B/s（回绕段）、−2,584,992,704 ÷ 15 = −172,332,847 B/s（清零段）。clamp 成 0 掉两次零，原样入库出两个向下尖刺。

:::

## 小结

32 位计数器 1G 口 34.4 秒绕一圈，10G 3.4 秒，100G 0.34 秒。可用条件 `T < 回绕周期 ÷ 2`，一半留给丢采样。10G 以上没有可行周期，必须走 64 位。

速率三版：差值错在单位，归一在回绕时变负，回绕检测加插值才对。上限校验抓不到多重回绕，能抓住的只有 `speed × Δt < 2^32`，按端口算。

归零与回绕在数值上一样，判据在 `sysUpTime`：Δup ≤ 3000 正常，> 30000 判重启，中间那档丢弃。重建区间标 gap。

错包先分 errors 与 discards：前者归线，后者归拥塞。CRC 单端涨查光，两端涨查对端，discards 涨查带宽。
