title: 17 · SNMP 采集工程

上一课把一台设备的 1920 个 varbind 数清了，这一课乘上设备台数，然后想办法别把设备采死。

## 采得全和别采死，争的是同一颗 CPU

老 TOR 的 SNMP agent 单线程，跟 CLI、SSH 登录、syslog 吐日志抢同一颗管理面 CPU。你 walk 全表那几秒，运维在 SSH 上敲的 `show interface` 卡三秒，那是排队排出来的。

采集器视角只有「采得全」，设备视角只有「你在打我」。中间没有仲裁者，只有你写的那层限流。

第 07 课算过状态类轻量轮询的账：800 台、120 秒、631 MB/天、设备侧 0.004%，便宜到不用犹豫。这一课算另一笔——采满 `ifTable` 加 `ifXTable` 那 1920 个 varbind，同一批设备上贵 36 倍的那件事。

## 30% 那个数是窗口喂出来的

规模先摆出来：2000 台，每台 48 口，采满 1920 个 varbind，周期 300 秒，max-repetitions 取 25。

```text
单台每轮
  varbind        1920
  请求数         1920 / 25 = 76.8 → 77
  响应           25 × 30 B（完整 OID + 值 + 长度类型）+ 头 ≈ 850 B
  请求           约 100 B
  一对报文       950 B
  报文量         77 × 950 ≈ 73 KB

全局
  请求速率       2000 × 77 / 300 = 513 请求/秒
  包速率         1026 包/秒
  带宽           513 × 950 ≈ 487 KB/s ≈ 3.9 Mbps
  一天           487 KB/s × 86,400 ≈ 42 GB
```

带宽和包速率都不是问题。一条千兆管理口用掉 0.4%，交换机控制面处理 1000 pps 的 SNMP 毫无压力。

问题在设备侧的 CPU 占空比：

```text
单 varbind 的 agent 成本   0.5 ms（老 TOR，MIB 走线性索引查找，无缓存）
单台每轮 CPU              1920 × 0.5 ms = 960 ms
摊进 300 秒                960 / 300,000 = 0.32%
```

0.32%。现场读到的 30% 从哪来：

```text
采集窗口 = 请求数 × 请求间隔
77 个请求连发（间隔由响应时间与并发会话决定），窗口 = 3 秒
窗口内占用 = 960 ms / 3,000 ms = 32%
```

CPU 读数取的是窗口内的占用，周期平均看不到尖峰。同一份数据，摊在 3 秒是 32%，摊在 15 秒是 6.4%，摊在 60 秒是 1.6%。

**占空比 = varbind 数 × 单 varbind 成本 ÷ 采集窗口长度。** 三个变量里只有一个受设备型号约束，后两个全在你手里。

窗口怎么拉长？两个旋钮：max-repetitions 调小，请求间隔被响应时间自然撑开；或者在设备上挂一个令牌桶。前者粗，后者可控：

```text
限流 4 请求/秒 → 77 个请求摊到 19 秒 → 960 / 19,000 = 5.1%
再砍到 960 个 varbind（只留 64 位计数器与状态列）
               → 480 / 19,000 = 2.5%
```

代价写清：一台设备一轮占 19 秒，300 秒周期里 6.3%。这个数就是并发会话数的分子，下一节用。

## 按能力分档，一套参数走不了全场

分档不能靠型号表，那张表三年就过时。用实测标定：上线前对每台设备发一次 200 varbind 的标定 walk，记中位 RTT 与折算的 varbind/秒，落到一档。

| 档 | 判据 | max-reps | 超时/重试 | 每设备并发 | 设备限流 | 周期 |
|---|---|---|---|---|---|---|
| A 弱 | 标定 > 400 ms，或 < 500 varbind/s | 10 | 3 s / 1 | 1 | 4 req/s | 300 s |
| B 中 | 100–400 ms | 25 | 2 s / 2 | 2 | 10 req/s | 180 s |
| C 强 | < 100 ms | 50 | 1 s / 2 | 4 | 25 req/s | 60 s |
| D 订阅 | 支持 gNMI ON_CHANGE | — | — | — | — | 600 s 兜底（第 19 课） |

四列参数各自的理由：

**max-repetitions。** 上限由 MTU 反推，1400 ÷ 30 ≈ 46。A 档取 10，因为它慢在每个 varbind 都要现查，不在包大小上——批越大，单次请求在 agent 里待得越久，窗口反而更难控制。

**超时与重试。** A 档给 3 秒，因为它真的慢；给 1 秒等于每次都判失败再重试，请求量乘 3 还拿不到数据。重试不免费：重试 2 次把请求量乘 3，也把单台最坏占用从 19 秒抬到 57 秒。

**每设备并发。** agent 单线程，同一台设备的多个请求不会并行，只会在设备侧排队。并发 4 的唯一作用是缩短窗口——正好是上一节要压的那件事。A 档并发必须是 1。

**设备限流。** 令牌桶按设备算，不按全局算。全局桶救不了「四个采集任务同时打同一台老 TOR」，那台设备在全局统计里只占万分之五。

```go
type Tier struct {
	RPS     float64       // 单设备限流，令牌/秒
	Burst   int           // 允许的突发，一般 4
	Timeout time.Duration // 单请求超时
	Retries int
	Reps    int           // max-repetitions
	Period  time.Duration
}

// 一台设备一个桶：桶控的是「这台设备每秒挨几个请求」。
func (d *DeviceGauge) Walk(ctx context.Context, root string) ([]VarBind, error) {
	if err := d.bucket.Wait(ctx); err != nil {
		return nil, ErrBudgetExceeded // 等不到令牌就放弃这一轮，不算异常
	}
	ctx, cancel := context.WithTimeout(ctx, d.Tier.Timeout)
	defer cancel()
	return walk(ctx, root, d.Tier.Reps, d.Tier.Retries)
}
```

用 `Wait` 不用 `Allow`：拿不到令牌就等，别丢请求。丢请求等于把「限流」翻译成「超时」，后面那条「超时当成 down」的坑就从这里开始。

## 调度：把几百个请求摊进几百个秒槽

2000 台、300 秒周期，平均每秒 7 台设备开工。写成一个全量循环，真实发生的是第 0 秒 2000 台一起上——第 09 课描述过同一个场面，那次是 10000 个 ICMP 挤在一秒里。

做法照 09 课：`device_id` 哈希到 0–299 的秒槽，每台设备的采集时刻固定可复现；槽内按机架二次散列，避免同一台接入交换机下的 48 台同时被打。

真正要算的是并发会话数。它不等于需求速率乘 RTT，因为请求大半时间在等令牌：

```text
并发 ≈ Σ(每台设备的采集窗口) ÷ 周期
A 档  300 台 × 48 秒（192 请求 ÷ 4 req/s）= 14,400 秒
B 档 1500 台 × 7.7 秒（77 请求 ÷ 10 req/s）= 11,550 秒
C 档  200 台 × 1.6 秒（39 请求 ÷ 25 req/s）=    320 秒
合计 26,270 秒 ÷ 300 秒周期 = 88 个活跃会话
```

88。按「513 请求/秒 × 8 ms ≈ 4」配会话池，A 档那 48 秒窗口根本拉不开，窗口被并发挤回去，CPU 尖峰照样来。会话池配 88，加 1+1 冗余再按机房分片，落成 160 个槽位。

同一份 960 ms 的活，A 档摊成 48 秒是 2%，B 档摊成 7.7 秒是 12.5%。分档真正在分的是窗口长度。

超时与重试的退避单独说。失败设备按固定周期重试，一批同时失败的设备会在同一个边界上一起回来，第二次脉冲比第一次更高：

```go
// 失败设备的下一轮时刻：指数退避 + 封顶 + 抖动
func nextAttempt(fails int, base time.Duration) time.Duration {
	if fails > 5 {
		fails = 5
	}
	d := base << fails                                 // 300 s → 9600 s 封顶
	return d - time.Duration(rand.Int63n(int64(d/10))) // 落在 [0.9d, d]
}
```

9600 秒是一天 9 次。彻底采不到的设备占着周期没有产出，退频只是止损。

## 不可达和响应慢要分开记

一台设备每轮的结果只有四种，混着记等于放弃判断：

| 结果 | 判据 | 数据怎么处理 | 说明什么 |
|---|---|---|---|
| ok | 响应，RTT ≤ 档位阈值 | 入库 | 正常 |
| slow | 响应，RTT 超阈值 | 入库，另记 slow | 该降档了 |
| timeout | 无响应 | 缺值，不覆盖上一轮 | 设备还是采集器，待判 |
| error | 有响应，error-status ≠ 0 | 缺值，记 status | OID 不存在，或响应 tooBig |

`slow` 是整张表的关键。慢设备的响应是对的，数据能用，它是最早那个「你打太猛」的信号。混进 ok，你会一直等到它变成 timeout；混进 timeout，你会白扔掉三成可用数据。

`error` 也常被当成 timeout。`noSuchName` 是「这台设备没这个 OID」，`tooBig` 是「你要得太多」，两者都说明采集配置错了，重试一百次也一样。这两个码不重试，直接进配置问题清单。

落成每设备一行健康分：连续 3 轮 slow 降一档，连续 10 轮 ok 升一档，单次升降不超过一档。升降带回差，否则一台设备在阈值附近来回抖，周期和参数跟着一起抖。这是第 38 课抑制思路的另一处用法，对象换成采集配置。

## 三种失败：超时当 down、队头阻塞、隔离后不回归

**一、超时写成 down。** 采集器所在物理机调了一次网卡参数，1400 字节以上的响应被丢，800 台设备里 63 台连续三轮超时。采集器把「没拿到值」写成 0，`ifOperStatus=0` 不在七个合法枚举里，下游当成「非 up」，3024 个端口同时 down，出一条 P1。

真故障 0 条。修复不在采集器，在缺值语义：没采到就写 `null` 并记 `stale_since`，不写 0，不猜。状态类不沿用上一轮的值，计数器类可以沿用但要打 `stale` 标（第 18 课算速率时读这个标）。第 07 课那条「超时、非法枚举、映射缺失三项任一不过就标 unknown」是同一条规矩的另一处落点。

**二、队头阻塞。** 一个 worker 串行处理一个机房的 30 台设备，其中两台 A 档：3 秒超时 × 2 次重试 = 9 秒/台，两台吃掉 18 秒，整个机房的数据时间戳一起后移。表现是「每分钟一次全体延迟」，根因是两台老设备。

修法不在调大超时预算，在把等待挪出 worker：请求在设备桶里等，不占 worker 槽位；每台设备独立任务，worker 池只负责发起；周期末尾留 20% 余量，300 秒按 240 秒排程。超预算的设备终止本轮，记一条 `budget_exceeded`，下一轮重排秒槽。

**三、隔离后不回归。** 大促前把 12 台抖动设备扔进隔离名单，降频到 1 小时，活动结束没人捞。半年后这 12 台的曲线还在画，只是每个点隔一小时——第 36 课算可用率时，它们的分母是别人的十二分之一。更糟的是其中 3 台换过板卡，`port_identity` 半年没更新，第 16 课那套索引漂移检测跟着一起失效。

隔离必须自带出口：

| 状态 | 采集频率 | 进时序 | 出口 |
|---|---|---|---|
| 正常 | 档位周期 | 是 | — |
| 观察 | 2 × 周期 | 是 | 连续 3 轮 ok 回正常 |
| 隔离 | 900 秒低频探针 | 否，只留最近值 | 连续 3 次 ok 回观察；TTL 24 小时到期强制重试 |

隔离台数单独上大盘。这个数超过 5%（2000 台里的 100 台），问题在采集器或管理网，不在那 100 台设备。少了这个数，隔离名单会变成一个只进不出的黑洞。

## 判据

按自己的规模填，三问都要算：

```text
设备数            800
每台 varbind      1920
采集周期          180 s
max-repetitions   25
单 varbind 成本   0.5 ms
单设备限流        10 req/s
```

1. 全局请求速率、带宽（一对报文按 950 B）、一天多少 GB？
2. 单台设备的采集窗口多长，管理面 CPU 占空比多少？压到 5% 以下动哪个旋钮最省事，代价是什么？
3. 63 台设备连续三轮超时。一分钟内判断是设备侧还是采集器侧，写出判据。

配套实验 `06-snmp-walk` 给的是录好的设备响应序列，档位参数、限流桶与隔离出口留给你填；同一份序列，max-repetitions 取 10 和取 50，出来的窗口长度差四倍。

::: details 参考

1. 800 × 77 ÷ 180 = 342 请求/秒；342 × 950 ≈ 325 KB/s ≈ 2.6 Mbps；一天 28 GB。
2. 窗口 = 77 ÷ 10 = 7.7 秒，960 ÷ 7700 = 12.5%。压到 5% 需要窗口 19.2 秒，限流降到 4 req/s；代价是一台设备占周期 10.7%，并发会话从 34 涨到 86（342 ÷ 4）。
3. 看同源相关性：同一采集器下其他设备是否同时失败、失败是否集中在响应大的请求、设备 `sysUpTime` 是否连续。第 09 课那条「单探测点失败率超 20% 判定探测点异常」是同一个思路，换成采集器。

:::

## 小结

采满全表，一台 48 口设备 1920 个 varbind；2000 台、300 秒周期就是 513 请求/秒、3.9 Mbps、42 GB/天。带宽用掉 0.4%，真正的约束在设备管理面 CPU。

占空比 = varbind 数 × 单 varbind 成本 ÷ 采集窗口长度。3 秒窗口读到 32%，19 秒窗口读到 5%，数据量一个字没变。拉长窗口靠分档限流与并发控制，代价是周期被吃掉一截。

结果分四类记，`slow` 最重要。三种死法记牢：超时写成 0、队头阻塞拖垮整轮、隔离名单只进不出。

下一课进计数器：那些 32 位的数每 34 秒绕一圈，速率算法得自己处理。

## 思考

1. 你的采集器按全局 QPS 限流还是按设备限流？把最慢那 20 台的窗口长度算出来，看它们有没有被并发挤回去。
2. 隔离名单里现在有几台？各自进去多久了？谁负责把它们捞出来？
3. 把 `slow` 阈值从档位 RTT 的 3 倍改成 5 倍，降档会少多少，CPU 会多多少？用你那批设备的 RTT 分布算一遍。
