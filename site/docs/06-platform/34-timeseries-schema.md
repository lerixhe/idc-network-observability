## 一个查询为什么慢，两个键说了算

上一课把迟到三分钟的数据塞回窗口，点了落库。这一课问一个更硬的问题：同样十亿条数据，为什么有的查询 10 毫秒出来，有的跑两小时。

判据先摆出来：**能解释「为什么按设备维度查很快、按端口名模糊查很慢」。**两个查询读同一张表、同一段时间、同一批数据，快慢差五十万倍，原因全在建表时定下的两个键——排序键和分区键。

类比一句。时序库相当于一本通讯录，排序键是里面按什么排（按姓名排，直接翻到那页；按身份证号排，只能从第一页读），分区键是把通讯录拆成几个分册（查 2024 年的人，只开 2024 那册）。TTL 与降采样管第三件事：哪些记录根本不进书架。

## 排序键决定跳几跳，分区键决定开几扇门

基准配置见[附录 C · 基准配置](../appendix/benchmark)：口径 B 的 P1 是每秒 20 万条探测明细，每条 150 字节。

```text
每分钟    200,000 × 60        = 1,200 万行
每小时    200,000 × 3,600     = 7.2 亿行
每天      200,000 × 86,400    = 172.8 亿行
每天体积  172.8 亿 × 150 B    = 2.6 TB
```

一天一个分区，按 `index_granularity = 8192` 切 granule，一个分区 172.8 亿 ÷ 8192 = 211 万个。主索引是稀疏索引，每 8192 行取一个键：这是它能扁扛十亿行的原因，也是它慢起来的来源——**索引只说「这 8192 行里可能有」，不说哪一行是。**

排序键 `(link_id, ts)` 的读法是两层：

- `link_id` 是前缀。给定一条链路，索引二分到那一段 granule，剩下的全跳过。
- `ts` 在段内有序。给定时间区间，段内再跳一次。

先算单链路的量，公式只有周期：5 秒一轮、双向，一小时 3,600 ÷ 5 × 2 = 1,440 行。这 1,440 行在一天的 172.8 亿行里是连续的几段——**跳数是 2 次二分，扫描量 1,440 行**。

换成 `WHERE port_name LIKE '%0/24'`：`port_name` 不在排序键里，没有前缀可用，引擎只能把这一小时的全部 7.2 亿行读出来逐行匹配。

```text
7.2 亿 ÷ 1,440 = 500,000
```

五十万倍。这个倍数调优调不出来，它由排序键的排列决定。

分区键管另一件事：**开几扇门**。按天分区，查 1 小时开 1 个；查 45 天开 45 个；不带时间条件，45 个全开——「一个大查询拖垮写入」的标准起点。

粒度有三档：按天 45 个分区，裁剪干净、TTL 按天删；按月 2 个，文件少但 TTL 只能整月删，最多多留 31 天；按小时 1,080 个，单分区极小但元数据与文件句柄吃紧、合并跟不上。按天是这套数据的正确档位，分区键基数上限在**千级**。

## 三张表，两个键

第一张，探测明细。一条探测包一行，写多读少，读只发生在举证与回溯。

```sql
CREATE TABLE probe_packet
(
    ts         DateTime64(3),
    link_id    UInt64,
    device_id  UInt32,
    port_id    UInt32,
    probe_id   LowCardinality(String),
    src_ip     IPv4,
    dst_ip     IPv4,
    rtt_us     UInt32,
    lost       UInt8,
    pkt_size   UInt16
)
ENGINE = MergeTree
PARTITION BY toDate(ts)
ORDER BY (link_id, ts)
TTL toDate(ts) + INTERVAL 45 DAY
SETTINGS index_granularity = 8192;
```

`(link_id, ts)` 是给举证包用的：第 10 课那个只读接口，输入时间窗加一条路径，走的就是这个前缀。`src_ip`、`dst_ip` 只存不排，它们是**列不是键**，这笔账后面还。

第二张，1 分钟聚合。面板、告警、横向对比都读它。

```sql
CREATE TABLE metric_1m
(
    ts            DateTime,
    device_id     UInt32,
    link_id       UInt64,
    port_name     LowCardinality(String),
    rtt_p50_us    UInt32,
    rtt_p95_us    UInt32,
    rtt_p99_us    UInt32,
    loss_ppm_a2b  UInt32,
    loss_ppm_b2a  UInt32,
    samples       UInt16
)
ENGINE = ReplacingMergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (device_id, link_id, ts)
TTL ts + INTERVAL 12 MONTH;
```

第一列换成 `device_id`，因为控制台的入口永远是「一台设备下钻到它的几条上行」（第 55 课的分层下钻）。方向不做成行、做成两列——第 04 课要求两端比对，成对存进同一行，一次读出来就能比。

`port_name` 是冗余列，从 CMDB 抄的别名，给人看。它**不在排序键里**，这是故意的：端口名会改（第 23 课），改了历史就断。这条冗余列最容易被误用成查询条件，下面算它的代价。

第三张，5 分钟层，从 1 分钟层滚出来。

```sql
CREATE MATERIALIZED VIEW metric_5m
ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (link_id, ts)
TTL ts + INTERVAL 36 MONTH
AS
SELECT toStartOfFiveMinute(ts)   AS ts,
       link_id,
       avgState(rtt_p95_us)      AS rtt_p95_avg,
       maxState(rtt_p99_us)      AS rtt_p99_max,
       maxState(loss_ppm_a2b)    AS loss_ppm_a2b_max
FROM metric_1m
GROUP BY ts, link_id;
```

键换回 `(link_id, ts)`：三年趋势按链路看，不按设备看。聚合列用 `avgState`、`maxState` 存中间状态，读的时候要 `-Merge`。它从 1 分钟层滚，不重算明细——明细 45 天就删了。

第四类载体是事件表，键 `(device_id, ts, event_id)`，TTL 36 个月。它比明细小四个数量级，不进这三层的压缩账，但复盘、对账、季度对比只认它。

## 六条查询，扫描量实算一遍

两个键定完，快慢就成了算术题：举证与趋势共用 `(link_id, ts)`，面板用 `(device_id, link_id, ts)`。按扫描吞吐 1 亿行/秒 估（窄列、冷缓存，宽列与高并发更低）：

| # | 查询 | 表与条件 | 排序键 | 扫描行数 | 耗时 |
|---|---|---|---|---|---|
| 1 | 举证包：一条链路 1 小时逐包 RTT | `probe_packet`，`link_id=?` 加 1 小时 | 命中 | 1,440 | < 1 ms |
| 2 | 面板：一台 TOR 一天的 8 条上行曲线 | `metric_1m`，`device_id=?` 加 1 天 | 命中前缀 | 11,520 | < 1 ms |
| 3 | 同一张表按 `link_id` 查一天 | `metric_1m`，`link_id=?` 加 1 天 | 不命中（第二列） | 2,880 万 | 0.3 s |
| 4 | 季度对比：20 条链路三年趋势 | `metric_5m`，`link_id IN (20)` | 命中 | 630 万 | 63 ms |
| 5 | 按端口名模糊查 1 小时 | `probe_packet`，`port_name LIKE '%0/24'` | 无 | 7.2 亿 | 7.2 s |
| 6 | 按源 IP 查 45 天全量 | `probe_packet`，`src_ip=?` | 无 | 7,776 亿 | 2.2 小时 |

算式：

```text
第 1 行   3,600 ÷ 5 × 2（5 秒周期、双向）   = 1,440
第 2 行   8 条上行 × 1,440 分钟            = 11,520
第 3 行   2 万条链路 × 1,440 分钟          = 2,880 万（全扫一天聚合层）
第 4 行   20 × 288 × 365 × 3              = 630 万
第 6 行   172.8 亿 × 45 = 7,776 亿 ÷ 1e8   = 7,776 秒
```

第 3 行要看仔细。它和第 2 行读**同一张表**，只换了条件里的维度，慢 2,500 倍——排序键只有一列能做前缀。同一份数据被两个维度访问，出路三条：建两张键不同的表、用 projection、在 API 层挡掉。

第 6 行是 2.2 小时。「按源 IP 查这条链路昨天的事」，原生写法就是它。

## 基数：排序键、分区键、标签，三个地方同一笔账

排序键有一条硬规矩：**第一列必须是查询必带的维度，且基数可控**。

`device_id` 基数一万，`link_id` 基数两万，`src_ip` 基数上亿。`src_ip` 挪到第一列，任何不带 IP 的查询都退化成全扫——第 6 行那 2.2 小时就是这么来的。

分区键的基数更危险，它是文件系统级的。按 `src_ip` 分区等于建上亿个目录，元数据先崩。

标签基数是同一笔账的第三处，第 37 课专门算它，这里只看磁盘后果：**标签每加一维，聚合表行数乘一次基数**。

1 分钟聚合按链路建模，一年 2 万 × 1,440 × 365 = 105 亿行，每条链路每小时 60 行。往标签里加 `src_port`、`dst_port`：

```text
加端口标签前   每链路每小时 60 行
加端口标签后   每链路每小时 1,440 行（几乎条条不同）
```

聚合表当场退回明细表。第 37 课算的是基数爆炸在内存与索引上的账，这里是它在磁盘上的同一笔账——**降采样不省钱，只要标签够多。**

一条共识写在任何表设计之前：**库里只存 CMDB 的整数 ID，不存名字、不存 IP**。反过来做，第 23 课那场「设备改名，历史断成两截」会在存储层再演一遍。

## 查询侧的现实：分页、下钻、降级，以及一次大查询怎么拖垮写入

下面三件事要在 API 层定死，数据库管不了。

**分页用游标。**`LIMIT 100 OFFSET 20000` 在时序库上等于扫 20,100 行、丢掉 20,000 行，翻得越深越贵。改成 `WHERE (ts, link_id) > (上一页的末一个键)`，代价恒定。

**下钻分四层。**机房 → 机架 → 设备 → 端口，第 55 课的界面就是这四层。四层扫描量是 11、48、11,520、1,440 行，高低差四个数量级；混成一条 SQL，等于每次都从底层扫。

**超时要能降级。**3 秒没出结果，查询改写到 5 分钟层，每行带 `degraded: true`。曲线看得出趋势，举证拿不到秒级，这个差别必须写进响应里。

三件事不做，就会撞上第 55 课那则复盘：**一次大查询把写入拖垮。**

```text
某开发写了个 LIKE '%0/24' 的导出，时间范围 45 天
  → 引擎开 45 个分区，扫 7,776 亿行
  → page cache 被打穿，写入侧 flush 排队
  → 探针上报超时，本地缓冲堆积
  → 超时触发重报，写入量再翻一倍
  → 同一个磁盘池，读把写饿死，闭环
```

误判在归因。值班的人只看到「探针大面积上报失败」，先去查探针和网络（第 14 课那套动作），真凶在自家查询窗口里。真代价是数据缺口：探针本地缓冲有上限（第 30 课、第 33 课），那两小时的明细永久丢了。

五条防护，一条省不掉：

| 防护 | 做法 | 缺了会怎样 |
|---|---|---|
| 强制时间窗 | `WHERE` 里没有 `ts` 直接 400 | 45 个分区全开 |
| 执行时限 | `max_execution_time = 30` | 一个查询占住 CPU 半小时 |
| 并发配额 | 按用户限并发，明细查询单列一条道 | 导出把面板挤死 |
| 读写分离 | 明细查询走只读副本 | 读把写饿死 |
| 结果上限 | 超阈值转异步导出 | 一页 500 万行塞进内存 |

第五条：转异步，不硬拒。45 天的明细导出排队跑完给链接，同步接口只服务「人盯着看」的量级。

下一课把 45 天、1 年、3 年这三个数字变成一张账单。

## 接口长什么样

表建对了，接口还能在三个地方把查询打死：没有时间窗上限、没有游标分页、导出与交互抢同一批磁盘。

一个能活的查询接口，五条约束：

| 约束 | 做法 | 不做会怎样 |
|---|---|---|
| 时间窗上限 | 交互查询默认 1 小时、硬上限 24 小时，超了转异步导出 | 用户点「最近 90 天」，一次扫 90 个分区，写入被拖垮（第 55 课第二则复盘） |
| 游标分页 | 按 `(排序键, ts)` 做 key-set 分页，不用 `OFFSET` | `OFFSET 10000` 要让库扫过前一万行，越翻越慢 |
| 下钻参数固定四层 | `room_id` / `rack_id` / `device_id` / `port_id`，不给自由维度组合 | 自由组合等于让用户自己写 SQL，排序键当场失效 |
| 权限在查询里裁 | 行级过滤拼进 `WHERE`，不在应用层过一遍 | 应用层过滤要先把数据拉回来，几万行白读 |
| 导出与交互隔离 | 导出走队列，结果落对象存储，每人一个并发上限 | 见上表第一行那条事故 |

接口返回里还有一样东西不能少：**覆盖说明**。

```text
GET /v1/link/rtt?link_id=L48&from=…&to=…&agg=1m&limit=500
→ {
    "window": {"from": "…", "to": "…", "tz": "+08:00"},
    "agg": "1m",
    "coverage": 0.91,          // 这段时间里有多少采样点真的到了
    "missing": ["14:23:10-14:23:52"],
    "points": [ {"ts": "…", "p50_us": 210, "p99_us": 780, "loss_ppm": 30000}, … ]
  }
```

`coverage` 与 `missing` 是第 10 课那个「说清我没测到什么」在接口层的兑现。没有这两个字段，一屏干净的曲线会被读成「这段时间链路很好」，而它可能只是采集器那半小时没上报——第 40 课讲的「缺失」形态，源头在这里。

## 判据

一家 IDC，一期 2 万条已探链路、5 秒周期、双向，每秒 20 万条明细，每行 150 字节，表如上。判断三条查询的扫描量，指出哪个键没命中。

```text
A: probe_packet  WHERE link_id = 8812 AND ts 取 14:00–15:00
B: metric_1m     WHERE port_name LIKE '%ge-0/0/24%' AND ts 取某一天
C: probe_packet  WHERE dst_ip = '10.60.1.9' AND ts 取最近 7 天
```

验收标准三条：

1. 三条都给出扫描行数与算式，单位写清
2. 每条指出哪个键命中、哪个键没命中，没命中的给出改法
3. 说出 C 在生产上的后果，以及你用哪两条防护挡住它

::: details 参考

A → 命中 `(link_id, ts)` 双层前缀，扫 3,600 ÷ 5 × 2 = 1,440 行，毫秒级。

B → `port_name` 不在排序键里，无前缀可用，全扫一天分区：2 万 × 1,440 = 2,880 万行，约 0.3 秒。改法是让 CMDB 先把端口名解析成 `port_id`。

C → `dst_ip` 是列不是键，全扫 7 天：172.8 亿 × 7 = 1,210 亿行，约 20 分钟，读把写饿死。挡它用强制时间窗加只读副本。

:::

## 小结

同样的数据，五十万倍差距，全在排序键的排列上。`(link_id, ts)` 让一条链路的 1 小时变成 1,440 行，让按端口名的模糊查变成 7.2 亿行。

分区键开几扇门：按天 45 扇，按小时 1,080 扇，按 IP 上亿扇，末一档是元数据先崩。

三张表两个键对三个入口：举证按链路、面板按设备、趋势按链路看三年。排序键只有一列能做前缀，多一个入口就得多一份索引。

基数在三个地方是同一笔账：排序键前缀、分区键、聚合标签。加一维端口标签，105 亿行的聚合表当场退回明细。

查询侧的账在 API 层：游标分页、四层下钻、超时降级。三件不做，一次 LIKE 加 45 天能花两小时把写入拖死。
