上一课把鉴权与限速收口在探针这一侧，这一课从收到的这一头往回算：数据面能拿回来多少东西，全看控制面当初答应过什么。

## 接缝：控制面的四个选择，数据面各接一道后果

第 30 课比过三个方案，选定之后还剩四个问题。每个问题在数据面留一道不能商量的约束。

| 控制面的选择 | 数据面的后果 | 落点 |
|---|---|---|
| 探针多久拉一次任务 | 上报是「一批一批」还是「一条一条」，决定批次边界存不存在 | 幂等键的形状 |
| 断连之后能补多久 | 最大补报延迟决定水位线最宽能到多少 | 水位线宽度 |
| 限速超了丢还是排队（第 32 课） | 数据是「缺了」还是「晚了」 | 缺口标记 / 放宽水位线 |
| 长连接一条还是两条 | 位点状态存一份还是两份 | `acked_batch_seq` 的副本数 |

第 30 课已经把这条结论说过一遍，这里再说一次，因为它最容易被推翻：**水位线宽度由控制面的最大补报延迟推出来，流处理没有拍板的余地。**

常见的反例：水位线设 1 分钟，跑半年，然后怪探针补报不及时。1 分钟这个数从哪来没人答得出。数据面把拍出来的数当成约束，控制面从来没承诺过它，两边各说各话，直到某次机房割接之后曲线断了一个下午。

第三行最容易被放过。第 32 课讲过丢与排的取舍，那个结论在这条链路的下游要兑现成字段：丢了必须有缺口标记，排了必须放宽水位线。一个 `gap=true` 的布尔值，比十页「数据质量良好」的说明有用。

第四行决定位点存几份。控制与数据共用一个连接，位点只有一份，探针换个连接就归零；拆成两条连接，位点要在两份状态里各记一次，十万探针就是二十万条。拆开的好处是一个大批次不推迟下一个任务下发，第 31 课那条「全量雪崩」的放大路径就断在这里。

## 编码：两条公式，两个都不卡

一条探测结果的结构：

```go
type ProbeResult struct {
    ProbeID  string // prb-sh-3f-0217
    TargetID string // tgt-10-2-3-4
    MetricID uint16
    TsMs     int64
    RttUs    uint32
    Lost     uint16
    Sent     uint16
}
```

同一条走 JSON：

```json
{"probe_id":"prb-sh-3f-0217","target_id":"tgt-10-2-3-4","metric_id":3,"ts_ms":1735689600123,"rtt_us":842,"lost":0,"sent":10}
```

数一遍 125 字节，其中字段名占了 66 字节，一半以上是重复的键。

Protobuf 每个字段一个 tag（字段号 1–15 时占 1 字节），加长度或 varint 值：

```text
probe_id   1 + 1 + 14  = 16
target_id  1 + 1 + 13  = 15
metric_id  1 + 1       = 2
ts_ms      1 + 6       = 7     41 bit 的时间戳，varint 6 字节
rtt_us     1 + 2       = 3
lost       1 + 1       = 2
sent       1 + 1       = 2
合计                   47
```

125 ÷ 47 = 2.66 倍。日均十亿点换算成速率：

```text
10^9 ÷ 86400 = 11574 点/秒
JSON      11574 × 125 B = 1.45 MB/s = 11.6 Mbps
Protobuf  11574 × 47 B  = 0.54 MB/s =  4.3 Mbps
差        0.90 MB/s = 7.2 Mbps
```

一个万兆口的 0.07%。这条线路还有大量余量。

CPU 也照算。`encoding/json` 走反射约 100 MB/s，序列化加反序列化按 3.8 μs 一条；protobuf 生成代码约 800 MB/s，连接口开销按 0.5 μs 一条：

```text
JSON      11574 × 3.8 μs = 44 ms/s = 0.044 核
Protobuf  11574 × 0.5 μs = 5.8 ms/s = 0.006 核
```

差 0.038 核。

结论：**在日均十亿点的算例上，编码之争是个假问题。**带宽差 7.2 Mbps，CPU 差 0.04 核，两个都不够格进选型会。

这一节的算例取整到日均十亿点（11,574 点/秒），生产基准是 16.8 亿点/天即 19,405 点/秒，见[附录 C · 基准配置](../appendix/benchmark)第三节。量级差七成，带宽与 CPU 的结论不变——按 19,405 点/秒重算，差 12 Mbps 与 0.06 核。

编码真正值钱的地方在存储侧。一天十亿条落库，一年 3.65 × 10^11 条：

```text
JSON      3.65×10^11 × 125 B = 45.6 TB
Protobuf  3.65×10^11 ×  47 B = 17.2 TB
gzip 后（JSON 约 6:1，protobuf 约 1.5:1）
JSON      45.6 ÷ 6  =  7.6 TB
Protobuf  17.2 ÷ 1.5 = 11.5 TB
```

最后一组数值得停一下：**压缩之后 JSON 反而更小**。字段名每条重复，压缩器把它们吃掉；二进制里的 tag 与 varint 边界是噪声，压不动。所以「Protobuf 省存储」只在不开压缩时成立，而时序库基本都是压着存的（第 34 课）。

**2.66 只是这个函数的一端。** `labs/13-pipeline` 拿 5 个字段的确认点位实测，JSON 138.2 B 对紧凑二进制 8.2 B，差 16.94 倍，六成开销是键名。差距来自三件事：字段名进不进报文、字符串维度重不重复、有没有用列式加 delta。本节算例是「字段名不进报文、每点 ID 唯一、逐条编码」，实验样本是「字符串表 + varint + 批内 delta」，两个都真实，落在函数两端。三个判据与完整的对照表在[附录 C · 基准配置](../appendix/benchmark)第七节。

选 Protobuf 的理由跟字节数无关：schema 演进。加字段不破老客户端，删字段靠 `reserved`，这是 JSON 靠人肉约定撑不住的地方。字段从 7 个涨到 70 个的那天，你会需要它。代价也要说清：线上抓包看到的是二进制，得带着 `.proto` 才能解开，第 42 课那套三处对照的证据链要提前备好解码工具。

## 批次与幂等键：整批重放干净，部分写入靠两级

拉取式上报天然带批次。探针每 5 秒拉一次任务，执行一轮，把这轮的 N 个结果打成一个批次：

```text
batch {
  probe_id     "prb-sh-3f-0217"
  batch_seq    48217            // 单调递增，重启不复位
  produced_at  1735689604000    // 产出时刻，只做观测，不参与排序
  points       [ {metric_id, target_id, ts_ms, rtt_us, lost, sent}, ... ]
}
```

幂等键取 `(probe_id, batch_seq, metric_id)`。为什么是这三个，第 30 课讲过；这里算代价——批次边界存在，整批重放就能去重干净。

去重分两级：

| 级别 | 判据 | 处理 |
|---|---|---|
| 位点级 | `batch_seq ≤ acked_batch_seq[probe_id]` | 整批丢弃，不解码 |
| 窗口级 | `(probe_id, batch_seq)` 在窗口内已见过 | 逐条按 `metric_id` 去重 |

两级都要，缺一级就漏。

只有位点级，部分写入会丢数据：一批 100 条，位点先推了、数据只落了 40 条，剩下 60 条永远补不回来。只有窗口级，超窗重放全放行，重复数据直接进库。

规则一句话：**`acked_batch_seq` 只在整批写入成功后推进，回执与写入在同一个事务里。**

会失败的样子：位点只存在探针内存，重启回到 0，一天的数据重放一遍。只要服务端回执表里的 `acked_batch_seq` 是持久化的，这次重放被位点级去重整批吃掉，代价只是一次无效上传。反过来，服务端回执也跟着内存丢了，去重退化成窗口级，窗口一关，重复数据全进库，指标翻倍，口径当场作废（第 36 课）。

## 迟到数据：水位线 = 最大补报延迟 × 安全系数

数据面真正的难点在迟到，写入峰值反而好办。

网络抖了 40 分钟，恢复后探针把本地缓冲区一次性补报。三分钟前采的数据现在才到，水位线早已越过窗口右边界，窗口已关掉。

第 30 课算的是下限，这一课在下限上加一层余量，再把它的代价算清。

```text
第 30 课的下限  15 分钟（最大补报延迟）+ 1 分钟（时钟容差）= 16 分钟
尾部余量        2 分钟（上传 30 秒 + 重试 1 分钟 + 聚集 30 秒）
水位线          16 + 2 = 18 分钟，等价于 15 × 1.2
```

那 2 分钟对应一个具体的分布形状。补报到达时间在 [0, 15] 分钟上不均匀，末尾那一小时里恢复的探针会一起上传，尾部比均匀分布胖得多。

系数取 1.2。取 2 就是 30 分钟，所有查询的可见延迟跟着变成 30 分钟；取 1.1 是 16.5 分钟，余量只剩 30 秒，一次三重试就吃完。1.2 给出的水位线正好是 P99 入库延迟门限的三倍，而那个门限（6 分钟）就是第 32 课时效性指标的上界，两处对得上。

水位线的代价能直接算。水位线覆盖的这段时间里，每个活跃探测对一份状态：

```text
十万探针 × 20 目标 = 200 万活跃键
每键（计数器 + 去重位图 + 位点）约 200 B
200 万 × 200 B = 400 MB
```

水位线收窄到 1 分钟，这份状态降到 22 MB，省 378 MB 内存，代价是所有迟到超过 1 分钟的数据全丢。

## 乱序、重复、回放

乱序在这套系统里是常态。同一探针的批次按 `batch_seq` 有序，补报批次与实时批次会交叉到达：seq 48210 的补报可能晚于 seq 48220 的实时批次。

处理规则一条：**按事件时间入窗口，按 `batch_seq` 决定接不接受，不按到达顺序。**

重复有四个来源，各要一道防线：

| 来源 | 防线 |
|---|---|
| 上报失败后重试 | 幂等键 `(probe_id, batch_seq, metric_id)` |
| 探针重启后位点回退 | 服务端持久化的 `acked_batch_seq` |
| 控制面重复下发（第 31 课） | 任务版本号，探针只执行最高版本 |
| 灾备双写（第 53 课） | 同上，靠幂等键，不靠去重表 |

第四行要单说。热切时两条写路径同时落库，同一批数据进两次。靠幂等键能去重，前提是键在两条路径上完全一致——`batch_seq` 由探针生成，两条路径看到同一个值。键里一旦掺了「接收时间」这类服务端字段，双写立刻变成双倍计数，大屏数字跳一下，第二天运维就来问（第 53 课）。

回放：**同一批输入必须产生同一份输出。**三个条件缺一不可。

1. 处理函数是纯的，不读当前时间、不读外部状态
2. 时间来源是事件时间（记录里的 `ts_ms`），处理时间（`time.Now()`）不参与分桶
3. 去重状态能从位点重建：给定 `acked_batch_seq` 与窗口内的批次，重放出同样的结果

回放有两个用途。重算：口径改了、聚合逻辑改了，拿历史批次重跑，得到可比的曲线。故障复现：某天早上曲线断了一段，把当天的批次重新灌一遍，看是断在窗口边界还是断在去重。

回放跑不起来，八成坏在第 2 条。「5 分钟聚合」写成按处理时间分桶，重放时所有数据进入「现在」这个桶，跑出来的曲线跟线上完全两样。这类 bug 只在回放时暴露，而回放本身很少做，于是它常年待在里面。

## 两种失败形态：水位线太窄，和水位线太宽

水位线太窄：迟到数据被丢弃，**数据少但不报错**。

症状是曲线在断连恢复后缺一段，缺的位置与断连时长对得上。危险在于没有任何告警——流处理把超窗数据当正常丢弃，日志里只有一行 debug。等到有人发现「上周割接之后曲线有一段空白」，已经是复盘会。

判据：完整性 SLO（第 32 课三个指标里的第一个）掉到 99.5% 以下，且掉的时间点与探针断连时间点重合。缺口必须打标记，让图上看得出来，不能让「没有数据」长得像「一切正常」。

水位线太宽：查询永远慢一步。

18 分钟的水位线意味着「现在这一刻」的聚合数滞后最多 18 分钟。值班的人打开大盘，看到的是十几分钟前的世界，先怀疑平台，再怀疑自己。更大的浪费是它不解决任何问题：真实补报延迟的 P99 是 3 分钟，设 18 分钟只是白等 15 分钟。

两个方向摊开看：

| | 水位线太窄 | 水位线太宽 |
|---|---|---|
| 数据 | 少 | 齐 |
| 有没有报错 | 没有 | 没有 |
| 症状 | 曲线有洞 | 大盘滞后 |
| 发现时机 | 复盘会 | 上线第一天 |
| 修复方向 | 查控制面的最大补报延迟 | 同一个数，往下收 |

最后一行是一样的：两个方向的修复都指向同一个数。**控制面没把这个数写清，数据面怎么调都是猜。**

## 判据

读完这一课，你应该能对下面三条各给一个数。

```text
A: 控制面承诺断连后最多补 10 分钟，入库延迟 P99 是 2 分钟。水位线设多少？
B: 一条记录 JSON 125 B、Protobuf 47 B，日均 5 亿点。两者带宽差多少，值不值得为它改协议？
C: 某天 03:10–03:40 曲线缺一段，完整性掉到 97%，探针日志显示那段时间 CPU 打满 100%
```

验收标准三条：

1. A 能给出水位线宽度，并说出这个数怎么随控制面变化
2. B 能算出两条公式的差，并给出「不值得」或「值得」的判据
3. C 能区分是水位线太窄还是缺口没标记，并指出该补哪个字段

::: details 参考

A → 10 × 1.2 = 12 分钟。控制面把补报上限改成 20 分钟，水位线就得跟着到 24 分钟，数据面没有自主权。

B → 5 亿 ÷ 86400 = 5787 点/秒，差 5787 × 78 B = 0.45 MB/s = 3.6 Mbps。不值得为带宽改，改的话理由是 schema 演进。

C → 探针 CPU 打满造成的是缺口，放宽水位线救不回来。要补的是缺口标记，让图上一眼看出那 30 分钟没有数据，显示成一条平滑的线就在骗人。

:::

## 小结

四个控制面选择，四道数据面约束，成对出现。水位线宽度由最大补报延迟推出，流处理没有拍板的权力。

编码在日均 17 亿点的量级上不卡：差 12 Mbps、0.06 核。它值钱的地方在存储与 schema 演进，压缩之后 JSON 反而比 Protobuf 小。

幂等键 `(probe_id, batch_seq, metric_id)` 让整批重放干净，部分写入靠窗口级去重兜底。`acked_batch_seq` 只在整批落库成功后推进。

水位线 = 15 分钟 × 1.2 = 18 分钟，代价是 400 MB 状态与 18 分钟的可见延迟。

水位线太窄数据少而不报错，太宽查询永远慢一步。两个方向的修复都指向同一个数。

下一课把这个保留期落到表上：排序键、分区、TTL 各怎么定，一个查询为什么慢。

## 思考

1. 控制面把补报上限从 15 分钟放宽到 60 分钟，水位线、内存、可见延迟三个数各变成多少？这笔账该由谁批准？
2. 位点 `acked_batch_seq` 和幂等键里的 `batch_seq` 如果由两个组件分别生成，会出什么事故？
3. 回放要求「同一批输入同一份输出」，而聚合里有一项是 p99。p99 的近似算法（比如 t-digest）会不会破坏这个性质？
