## 这一篇解决什么

前六篇讲的是网络本身：端口、探测、SNMP、流、拓扑、事件。这一篇换问题——这些东西怎么变成一个**系统**。

开发者的直觉会把它当普通后端服务：写接口、存库、加缓存、水平扩容。这套直觉在这里大半失效。六个约束，就是这一篇存在的理由：

| 普通业务后端 | 网络可观测平台 |
|---|---|
| 请求驱动，没用户就没数据 | 采集驱动：数据量 = 设备数 × 指标数 ÷ 周期，与业务量无关，恒定且只增 |
| 延迟 200ms 算合格 | 发现要秒级，举证要能回溯到毫秒级，而且时间戳本身得先对齐 |
| 单集群 + 水平扩容拉吞吐 | 双向管控：任务下发到十万探针，数据从十万探针回来，两条路失败方式不同 |
| 关系型库，慢就加索引 | 时序库，写多读少差一个量级，降采样策略决定成本上限 |
| 数据丢了重试一次 | 迟到、乱序、重复、探针自身不可信，四件事同时发生 |
| 用户是前端页面 | 用户是凌晨三点被叫醒的值班人，一次误报的代价是下一次真故障被忽略 |

这一篇分两半，分界线是一次任务的往返：**控制面**（30–32）管「谁在哪、该干什么」，任务发下去；**数据面**（33–35）管「数据怎么回来、存在哪、花多少钱」。

两半之间的接缝要单独讲清：控制面的四个选择——拉取周期、补报上限、限速丢还是排、长连接条数——各自在数据面接一道必须兑现的约束。一条硬规矩：**水位线宽度不是流处理拍出来的，是控制面的最大补报延迟推出来的**。

## 课程

| 课 | 标题 | 解决的问题 | 实验 |
|---|---|---|---|
| 30 | 探针管控：拉取还是推送 | 短轮询、长连接、消息队列的取舍 | `10-task` |
| 31 | 任务编排的失败模式 | 重复下发、全量雪崩、坏点震荡、过期不回收 | `10-task` |
| 32 | 探针鉴权与速率整形 | 签名与双向 TLS、密钥轮换、两级令牌桶 | `10-task` |
| 33 | 编码与流处理 | Protobuf vs JSON 的成本；批次与幂等键；窗口、水位线、乱序 | `11-pipeline` |
| 34 | 时序库、表设计与查询 | 排序键、分区、TTL、降采样；一个查询为什么慢 | `11-pipeline` |
| 35 | 容量规划与成本 | 每秒多少点、每点多少字节、一年多少钱；证据分级保留 | `11-pipeline` |

35 课要给出一套**证据分级保留**，这是第三部分「举证包」在存储层的兑现：原始探测明细留 30–90 天（举证与回溯用）、1 分钟聚合留 1 年（曲线与告警用）、5 分钟聚合留 3 年（容量规划用）。三层的压缩比、磁盘、年花费列一张表，把这笔钱写成一条产品决策，而不是交给运维在工单里干等。

## 配套实验

- `labs/10-task`：任务管控，含拉取与推送两种模式的对比仿真
- `labs/11-pipeline`：文件模拟 Kafka、SQLite 模拟时序库，输入样本里混一批迟到 90 秒、重复、乱序的批次

## 读完你应该能

- 说出业务后端经验哪些能用、哪些得重学，落在采集驱动、双向管控、时序存储三处
- 在推拉之间做选择，并说清这个选择对批次边界、幂等键、补报上限、位点状态各留下什么约束
- 解释一个按端口名模糊查的查询为什么慢，并给出能快起来的表设计
- 算出一套平台一年的存储成本，并给出一份分层保留的产品决策
