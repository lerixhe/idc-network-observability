上一课在两端抓包，指认一个包的生死。这一课往中间走：它死在哪一跳，那台设备为什么丢弃它。

## traceroute 那一列地址，是几条路径的拼贴

传统 traceroute 的机制：发一个 TTL=1 的包，第一台路由器把 TTL 减到 0，丢弃，回一个 ICMP Time Exceeded。再发 TTL=2，第二跳回。一直加到目的端回应端口不可达或 Echo Reply。

要紧的是每一行都是一只新包。

| 轮次 | 发出的探测 | 回包 | 源端口 |
|---|---|---|---|
| 1 | TTL=1 | hop1 回 ICMP | 20000 |
| 2 | TTL=2 | hop2 回 ICMP | 20001 |
| 3 | TTL=3 | hop3 回 ICMP | 20002 |

第 12 课算过：一组五元组只对应一条哈希路径，换一个源端口就换一条。traceroute 每行都换标识（多数实现靠递增的 UDP 目的端口或 ICMP id 区分探测），于是第 2 行和第 3 行可能落在不同的 Spine 上。输出看着像一条线，底子是几条互不连通的路径拼出来的图。

后果落在判定上，不在显示上。一条 4 分支的上行，Spine-3 的光模块劣化三个月，你跑十次 traceroute 可能一次都没经过它，输出永远「四条腿都在」。这与第 12 课那张覆盖率收敛曲线是同一件事，区别只在于 traceroute 的输出里没人标覆盖率。

三个工具的边界摊开：

| | 每行代表 | 能答 | 不能答 | 每轮成本 |
|---|---|---|---|---|
| traceroute | 某 TTL 下某条分支上的一台设备 | 地址序列、大致跳数 | 丢包率、路径是否连贯 | 一次几十个包，跑完即止 |
| mtr | 该跳回包的成功率，持续几百轮 | 哪一段开始异常、随时间怎么变 | 转发面是否真丢、各跳是否同一路径 | 每跳每秒 1 个包，长期挂着 |
| paris-traceroute | 一条哈希路径的完整轨迹 | 单条路径的逐跳一致序列 | 其他分支、时延分解 | 同 traceroute，另加容器与权限 |

同为「路径工具」，三者回答三个不同的问题。运维问的常是第四个：为什么这条业务流慢。这个问题三样都答不了，理由在最后一节。

## mtr 的丢包列：从哪一跳开始丢，丢到终点才算数

mtr 把 traceroute 变成常驻：每秒一轮，把每跳的回包成功率累计成百分比。输出长这样：

```text
HOST                                  Loss%   Snt   Last   Avg  Best  Wrst StDev
  1. 10.32.0.1                          0.0  1200    0.4   0.4   0.3   0.9   0.1
  2. 10.32.254.9                        0.0  1200    0.9   1.0   0.7   4.2   0.3
  3. 172.20.8.1                        47.3  1200    1.2   1.3   0.9  18.6   1.1
  4. 172.20.11.6                       47.3  1200    1.6   1.7   1.2  22.0   1.4
  5. 172.20.11.30                      47.4  1200    1.8   1.9   1.3  19.4   1.2
  6. 198.51.100.1                       0.0  1200    2.1   2.2   1.6  26.8   1.9
```

第一眼看，第 3 跳到第 5 跳丢百分之四十七，像严重故障。看最后一行：终点 0.0%，Snt 1200 个包一个没少。结论立刻反过来——这条路径**一个包都没丢**，中间那三个 47% 全是回包侧的采样损失。

分母是「这一跳回过多少次 ICMP TTL 超时」。设备对这类回包普遍配 CPU 保护（control plane policing），限速一类的策略按 pps 卡。探测包每秒几十个是小事，一万条采集任务挤在同一分钟窗口里就不是：

```text
路径采集任务 3000 条，调度器把它们挤在同一秒下发
  → 该跳每秒收到约 3000 个 TTL 超时探测包
设备 ICMP 回包限速 1000 pps
  → 通过比例 1000 / 3000 = 33.3%，该跳显示损失 66.7%
转发面：一个包没丢
```

66.7% 这个数与链路好坏毫无关系，它是 1000 与 3000 的比值。值班的人拿这张图派单，两个人查两小时中间设备，最后靠终点 0.0% 收场——这类工单在网络团队里每年总要来几次。

判据给三条，按顺序用：

1. **看终点压不压得住。** 终点（或目标前最后一跳）丢包率接近 0，中间任何跳的丢包率都不作数，一律记为「回包侧损失」。
2. **看阶梯有没有被继承到终点。** 第 4 跳 2.8%、第 5 跳 2.8%、终点 2.8%，三级同高，这是真丢，丢点在第 4 跳之前。中间跳升高而终点回落，是限速。
3. **换一种探测复核。** ICMP 限速只作用于 ICMP 类报文。同一路径改用 UDP 或 TCP SYN 探测，中间跳的丢包率掉到 0 而终点读数不变，限速坐实。

第三条是判据里最硬的一条，因为它换掉了被限速的那类报文。代价是 UDP 探测常被防火墙拦，TCP SYN 探测要挑一个真在听的目标端口，两者都会引入新的假阴性。

反例得留一个：从第 3 跳起丢 2%、第 5 跳起丢 12%、终点 12%，这在同一条路径上同时存在两处丢点，前面的阶梯不是后面的原因。按「丢率变化的那一跳」定位，别只看最大值。

还有一处常被漏掉：mtr 的每跳 RTT 也是回包时间，含设备生成 ICMP 的处理开销。上表第 3 跳 Wrst 18.6 ms，第 6 跳 Avg 只有 2.2 ms，中间设备的抖动被 CPU 策略放大了十倍。把它读作转发时延，会得出「中间某跳很慢」的错误结论。

### 丢多少算真丢

判据解决了「哪一跳开始丢」，还差一个量：多小的丢包率值得写进工单。

mtr 的百分比是回包采样，业务感受到的丢包率要用 TCP 重传比去代理（第 44 课的 `RetransSegs`）。两者换算差一个常数，但量级一致，可以直接算业务后果。取一条 30 ms RTT 的流、MSS 1460 字节，按 Mathis 近似，随机丢包下的稳态吞吐：

```text
B ≈ MSS ÷ (RTT × √p)
  = 1460 ÷ (0.03 × √0.003)
  = 1460 ÷ (0.03 × 0.0548)
  ≈ 888 KB/s ≈ 7.1 Mbps
```

0.3% 的丢包把单流压到 7 Mbps，而 ping 一百个包只掉一个，任何阈值告警都不会响。这就是第 02 课那张工单的物理基础：业务确实卡，网络确实「正常」。所以真丢包的门槛不在告警配置里，在业务吞吐量的下降幅度里——一条千兆链路上 0.3% 的随机丢包，把单流业务的可用容量从千兆砍到个位数 Mbps，差两个数量级。

## paris 给同一条路径，而平台要的是一条曲线

paris-traceroute 的改法很小：同一轮里所有探测包打同一个流标签，让哈希在每一跳都算出同一个结果，整轮被设备当成一条流。IPv6 的 Flow Label 天生干这件事，IPv4 上要靠容器或扩展头配合。

换回来的是路径一致：一列地址来自同一条路，跳与跳之间能横向比较，第 4 跳的 2.8% 与第 5 跳的 2.8% 才真能读出「丢点在进入第 4 跳之前」。

它的边界一样硬：一次只覆盖一条分支。4 条等价路径，paris 跑一轮拿到 25%，剩下的 75% 得靠散列端口段去撞（第 12 课的 C(N) 曲线）。于是两个需求在平台上直接打架——paris 要求标签固定，覆盖率要求端口乱跳。可行的做法是两条采集并行：

- 固定标签的路径一致性曲线，看地址序列有没有变。路径变了比路径慢了更该叫醒人：一次变更把流量挪到了没做过容量的分支上，丢包是几小时后才显形的
- 端口段散列的逐跳丢包率，看每条分支在不在。落库时必须带源端口，不然同一个目标的两次结果没法比

这两条曲线合起来仍然答不出「哪个加数变大了」。逐跳丢包率是分母侧的估计，逐跳 RTT 含 CPU 开销，两者都不是转发时延。要拆时延得靠 INT 的 `hop_latency`（第 13 课）：每跳设备自己把内部耗时写进包头，收端读出来，端到端那个和才有加数。工程上的分工很清楚——路径工具负责**指方向**，INT 负责**定位置**。

一条平台侧的硬要求，顺手记：路径变化要落成事件，带地址序列指纹（序列的哈希）和变更单关联。指纹变了而没人知道为什么，是下一轮工单的引信。

## 判据

下面是一段 mtr 输出，先自己判，再看参考。目标是一台业务服务器，探针在另一个机架，两层 ECMP。

```text
HOST                                  Loss%   Snt   Last   Avg  Best  Wrst StDev
  1. 10.32.0.1                          0.0  1200    0.3   0.4   0.2   0.8   0.1
  2. 10.32.254.9                        0.0  1200    0.8   0.9   0.7   2.1   0.2
  3. 172.20.8.1                        12.4  1200    1.1   1.2   0.9   9.4   0.8
  4. 172.20.11.6                       12.4  1200    1.7   1.8   1.3  11.2   0.9
  5. 172.20.11.30                      12.4  1200    1.9   2.0   1.4  10.8   0.9
  6. 198.51.100.77                     12.4  1200    2.6   2.8   2.1  15.3   1.4
```

三个问题：

1. 这 12.4% 是真丢还是限速，判据是哪一行
2. 如果第 6 跳是 0.0%，结论怎么改，你要补哪一个探针才能坐实
3. 这条路径的病灶在第几跳，能得出的最强结论是什么

验收标准三条：判据必须指名到具体行与具体列，结论要带「覆盖了哪条分支」，还要说出这个工具答不出什么。

::: details 参考

1. 真丢。判据是第 3 跳 12.4% 一路继承到终点第 6 跳 12.4%，阶梯没有回落。第 3 跳自身也可能在限速，但终点同高，说明丢点在第 3 跳及其上游转发面。
2. 第 6 跳变 0.0%，则全部中间数字作废，按回包侧损失处理。补一个 UDP 或 TCP SYN 探测复核，同时看第 3 跳设备对应端口的出口丢弃计数（第 40 课）——两者一致才敢派单。
3. 病灶在第 3 跳之前，即第 2 跳到第 3 跳这一段。最强结论只到「这一段在丢 12.4%」，答不出是队列、光模块还是聚合口某条成员，也答不出这 12.4% 影响哪条业务流，因为每轮探测的哈希落点可能不同。

:::

## 小结

traceroute 每跳换新包，ECMP 下每一行可能来自不同分支，一列地址是几张图拼的。mtr 把这件事变成常驻曲线，代价是丢包率的分母变成「回过多少次 ICMP」——中间跳丢包而终点正常，基本可以断定 ICMP 限速，不是故障。paris 用流标签换回路径一致，前提是你接受一次只测一条。

三者都指方向，都不定位置。定位要逐跳时间戳，第 13 课。

下一课换一头：交换机、路径、探针全绿，业务还是慢，答案在主机的网卡里。

## 思考

1. 你的路径采集任务在同一分钟窗口里打向同一批设备，这一分钟的 ICMP 回包速率是多少？这台设备的限速值你查得到吗？
2. 一条 4 分支上行，paris 的覆盖率是 25%，散列到 96% 要跑多少条流。两条采集同时挂着，存储与告警该按哪一条的结论走？
3. 路径地址序列的指纹变了，而变更单上是空的。这个事件该派给谁，多久之内？
