上一课把曲线认成形状，这一课把形状换成手：看到这个形状，该拿哪把工具去敲。

## 七行症状，一眼分出方向

工单从来不带你想要的判据。业务方说「时通时不通」，运维要知道的是先 ping，还是先去防火墙团队那边要个数。中间那一步，就是这张表。

| 症状 | 先看什么 | 常见误判 |
|---|---|---|
| 时说时不断 | ping 分段、mtr 看哪一跳丢 | 把中间跳的 ICMP 限速当成丢包 |
| 单纯慢，不丢包 | ping 看 RTT 分布、traceroute 看路径是否变了 | 只看平均 RTT，漏掉双峰 |
| 丢包且与流量相关 | 端口计数器、队列丢弃、微突发 | 只看 5 分钟均值 |
| 完全不通 | 端口状态、MAC/ARP 表、VLAN 配置 | 只在本端看，不看对端 |
| 特定业务不通、同网段其他业务正常 | 防火墙会话表、NAT 池水位、负载均衡健康检查 | 把中间设备当透明，只查交换机和路由器 |
| 时快时慢且周期性 | 光功率与温度曲线、ECMP 哈希分布 | 当成随机故障 |
| 一台机器与所有机器都不通 | 该机器网卡（ethtool）、驱动、ring buffer | 报网络故障，实际是主机侧 |

七行里前四行判的是网络，后三行判的是「不是网络」。这个比例跟工单比例差不多。

用表之前先答两个二值问题，能砍掉一半分支：

```text
通不通？
├─ 不通 ─── 是全部目标都不通，还是只有这一个？ ── 第 4 行 / 第 5 行
└─ 通
   ├─ 快不快？
   │  ├─ 不快 ─── 持续慢还是忽快忽慢？ ──────── 第 2 行 / 第 6 行
   │  └─ 快 ───── 那就是丢包，跟流量相关吗？ ── 第 3 行
   └─ 时断时续 ── 断的周期跟什么同步？ ──────── 第 1 行
```

第 5 行是七行里最贵的一行。它对应的设备不在网络组的命令行历史里。第 7 行正好相反：一台机器跟谁都通不了，最省事的解释是「网络坏了」，最可能的解释是这台机器的网卡 ring buffer 太小（第 44 课）。方向反了，两天砸在交换机上。

## 八类工具：右边那一列才是重点

工具手册讲怎么用，这一课讲它答不了什么。八类摊一张表。

| 类别 | 常见命令 | 能答什么 | 不能答什么 |
|---|---|---|---|
| 连通性 | `ping`、`arping` | 目标此刻可达；二层 ARP 有没有回应；RTT 量级 | 带宽；低丢包率；路径；单向问题 |
| 路径 | `traceroute`、`mtr`、`paris-traceroute` | 走哪几跳，从哪一跳开始异常，路径变没变 | 单向丢包；ECMP 的全部分支；设备内部 |
| 抓包 | `tcpdump`、`tshark` | 包到没到、头部字段对不对、握手与重传 | 没到它那一侧的包；高 PPS 下它自己的丢弃 |
| 主机与网卡 | `ethtool -S/-g/-k`、`ss`、`/proc/net/snmp` | 丢在主机哪一层；ring buffer 大小；offload 状态 | 交换机侧；线上真实分段；跨主机比对 |
| 设备命令 | `show interface counters`、队列与 buffer | 队列深度、丢弃与错误计数、buffer 水位 | 历史（不留）；跨设备关联；瞬时峰值 |
| 中间设备 | 会话表、NAT 池、LB 健康检查、传输误码 | 会话建没建起来、端口池水位、后端被谁判死 | 逐包；单条流的完整路径 |
| 主动测量 | `iperf3`、`twamp` | 可用带宽、单向时延、抖动 | 业务真实负载下的表现（它自己就是负载） |
| 时间 | `ntpq -p`、`chronyc tracking` | 各源偏差多少，能不能对齐 | 已经过去那一段的偏差（补不回来） |

八类里最容易被高估的是第一行，最容易被漏掉的是最后两行。设备命令那一类的落地是文本解析：三家的 `show interface counters` 列名不同，单位在固件升级后会从 bytes 改成 packets，模板得按厂商与版本分开维护。配套实验 `15-tools-parse` 考的就是这个，工程约束在第 45 课。

ping 答不出丢包率，代价是一次错误的「网络正常」。20 个包全通，真实丢包率的 95% 上界算得出来：

```text
1 − 0.05^(1/20) = 1 − 0.861 = 13.9%
```

业务说的「偶尔卡」，如果是 0.3% 的丢包，它稳稳落在这个区间里，你的 20 个包一声不响。要说出「0.3%」这个词，样本量有下限：按三倍法则，观察到至少一次丢包需要 3 ÷ 0.003 = 1,000 个包；要把置信区间压到同一量级，得上万。这就是持续探测存在的理由（第 10、11 课）——人 ping 二十个包是抽签，探针每秒发一个是普查。

主动测量也有它的盲区：`iperf3` 测的是「空载能跑多快」，它自己会填满链路，测出来的数在业务高峰没有意义。测带宽要窗口，判故障不要。

时间这一类最容易漏，因为没人把它当工具。`ntpq -p` 给出每个源的四项：`st`（层级）、`offset`（偏差毫秒）、`jitter`（抖动）、`reach`（最近八次探测的成功位图）。判据只取一项：偏差绝对值超过采集周期的三分之一，这个源的数据就不能用来定因果。采集周期 60 秒，偏差 25 秒已经越线——两个相差 25 秒的结论拼在一起，先后顺序可能整个反过来。`reach` 掉到 0 的设备更干脆：它根本没在同步，时钟在自由运行，一天的漂移能到几秒到几十秒。

## 中间设备：不在你登录列表里的那一类

防火墙、NAT、负载均衡、波分传输，这四样对网络组是黑盒。它们不给你逐包，只给计数和状态。而「时通时不通」这类工单里，它们占的比例不比交换机端口 down 低。

四个形态，四个判据。

**会话表满。** 防火墙有并发会话上限，逼近上限时新连接被拒，或老会话被提前老化。两个数：水位与斜率。水位 86% 不一定动人；15 分钟从 60% 爬到 86% 必须动人——斜率 1.73 个百分点每分钟，剩 14 个点，8 分钟后打满，而人工介入要 20 分钟。这就是变化率比水位有用的地方。

**NAT 端口耗尽。** 最会骗人的一种。判据不在整体水位，在单地址水位：PAT 池按四元组哈希落到具体公网地址，一个地址可用端口约 64,000。整体 71% 看着安全，某个地址 100% 时，哈希落到那个地址的会话全部新建失败，重试换个源端口可能落到别的地址上，于是表现为「时通时不通」。

```text
单地址可用端口    65,535 − 1,024（保留）  = 63,488，按 64,000 估
单地址告警阈值    64,000 × 90%            = 57,600
四地址池总量      64,000 × 4              = 256,000
日峰值会话        190,000                 → 整体水位 74%，看着很安全
单地址峰值        61,000                  → 单地址水位 95%，先响的是这一格
```

**健康检查误判。** 负载均衡按间隔、超时、失败次数三个参数判后端死活。典型配置 5 秒间隔、1 秒超时、2 次失败判死：一次 1.2 秒的抖动就能让一台健康的后端下线，下线到恢复至少十几秒。四台后端摘掉一台，剩下各承 33%，容量不致命；致命的是反复摘挂，同一批连接被排空两次。

判据不是「有没有摘除」，是「每小时摘几次」和「每次摘多久」。一小时摘 40 次，说明阈值比链路抖动还敏感，那是配置问题，不是设备问题。

**传输设备误码。** 波分与传输设备给的是纠前误码率。纠前误码逼近纠错门限，链路不按比例丢包，而是成段丢——一次断 200 毫秒，业务侧看到「连接被重置」，交换机端口全程 up。这一层要的是趋势：纠前误码从 1e-6 抬到 1e-4，抬了两个数量级，离门限不远了。

这四样的采法跟交换机不同。交换机采 `ifOperStatus` 与计数器，中间设备只给会话数、命中计数、状态位，判据只能靠**水位 + 变化率**，瞬时值几乎没有信息量。这也是平台必须存历史的一条硬理由：一次 100% 的端口耗尽，如果只留当前值，事后什么都查不到。

## 按成本排一遍，别从最贵的开始

工具没有优劣，只有代价。同一句症状，几条路的开销差十倍。

| 动作 | 耗时 | 要谁配合 | 砍掉什么 |
|---|---|---|---|
| 本端 `ping` + `arping` | 10 秒 | 无 | 彻底不通、二层到不了 |
| `mtr` 跑 100 个包 | 100 秒 | 无 | 方向：从哪一跳开始异常 |
| 登设备看计数器 | 3 分钟 | 设备账号 | 本端设备侧丢弃与错误 |
| 业务机上 `ethtool -S`、`ss -s` | 5 分钟 | 业务方开权限 | 主机侧丢包与 accept 溢出 |
| 抓包 30 分钟 | 30 分钟起 | 窗口、落盘、人来判 | 包到没到、头部对不对 |
| 防火墙会话表 / NAT 水位 | 小时级 | 另一个团队 | 中间设备是不是瓶颈 |
| `iperf3` | 半天 | 两端装机、避开高峰 | 可用带宽上限 |

规矩一条：动之前把判据写下。`mtr` 跑完看到中间跳 3% 丢包、终点 0%，你要是没提前定「只有末尾几跳算数」，这 100 秒就白花了（第 43 课）。

## 会失败的样子：工具全跑过，结论还是错的

三个高频错法，后面各有专章。

**把中间跳的丢包当真丢包。** `mtr` 第 6 跳 3%，第 7 到 12 跳 0%，终点 0%。这是设备对 ICMP 限速，不是链路丢包。代价是派人去查一条根本没问题的链路，一次 40 分钟，一天两次就是 1.3 小时。

**把抓包自己丢的包算成链路丢的。** 高 PPS 口上跑 `tcpdump`，它自己跟不上，退出时打印 `packets dropped by kernel`。那个数字不是链路证据，是抓包不全的自白（第 42 课）。

**时间没对齐就下结论。** 业务说 14:23，你的数据从 14:22:47 开始有变化。这未必推翻结论，但会改变结论覆盖的区间：写「14:23 网络正常」和写「14:22:47 之后网络正常」，在复盘会上是两句话（第 46 课）。

第 5 行那一类最贵。把中间设备当透明，只在交换机和路由器上查，三天过去，最后发现是负载均衡把唯一健康的后端判死了。这个方向错得彻底——你查过的东西里根本没有答案。

## 判据

三条工单，各写「第一个动作 + 判据 + 排除掉什么」。

```text
A 财务部反馈：昨天下午访问 ERP 偶发超时，重试就好
B 同网段 40 台机器，只有 10.32.7.18 一台不通，其余正常
C 同一层楼的服务器都能 ping 通网关，访问某个 VIP 却时快时慢
```

验收三条：

1. 每条指出落在七行表第几行，第一个动作用哪个命令
2. 每条写出「什么数出现，就排除这条分支」
3. 自己补一条这三条覆盖不到的工单，说明它落在哪一类工具上

::: details 参考

A → 第 1、2 行。先 `mtr -c 100` 看 RTT 分布与末跳丢包。判据：只有末尾几跳持续丢包才算，中间跳丢包且终点干净一律当 ICMP 限速；RTT 双峰说明路径有两条分支，不是抖动（第 12、43 课）。

B → 第 7 行。先 `arping` 再 `ping`。同网段其他机器正常，交换机端口与 VLAN 已经排除。判据：ARP 不到、且交换机 FDB 里查不到这个 MAC，故障在主机或它的接入端口（第 27 课）。

C → 第 5 行。先要负载均衡的后端状态与摘除计数，不是先 ping。判据：每小时摘除次数大于 10、且摘除时刻与超时时刻对得上，问题在健康检查参数。

:::

## 小结

七行症状是一张判决表：前四行查网络，后三行先证明不是网络。八类工具每类都有盲区，右边那一列比左边值钱——20 个 ping 说得出「通」，说不出 0.3%。

中间设备是黑盒，判据只有水位与变化率。NAT 看单地址不看整体，健康检查看摘除频次不看单次状态。

工具按成本排，越往后越要人配合。判据在动手之前写好，跑完才知道算不算数。
