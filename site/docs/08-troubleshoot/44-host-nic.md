上一课把路径查干净了：每一跳都通，丢包率趋近零。工单还挂着，业务方说慢。这一课查一个常年被跳过的位置——被监控的那台机器本身。

## 网卡自己丢的包，交换机一点不知道

「网络丢包」这四个字在工单里出现时，八成的人第一反应是登交换机看端口。有一类丢包根本到不了交换机：包已经在网卡上，内核没接住。

`ethtool -S` 是这一层的入口。字段名随驱动变（千兆与万兆不同厂牌各有各的叫法），语义只有三类：

| 计数器 | 谁丢的 | 典型成因 |
|---|---|---|
| `rx_fifo_errors` | 网卡 FIFO / ring 满 | 收到的包比驱动取走的速度快，队列顶满 |
| `rx_missed_errors` | 主机没及时取走 | 中断被合并太久、软中断被别的核占住 |
| `rx_dropped` | 驱动或协议栈 | skb 分配失败、VLAN/协议不匹配、`netdev_max_backlog` 溢出 |
| `rx_crc_errors` / `rx_frame_errors` | 链路 | 光模块、跳线、接头脏了，属真链路问题 |
| `tx_dropped` / `tx_errors` | 发送侧 | 队列满、qdisc 丢弃、MTU 不匹配 |

前三个是这一课的主角。它们的共同点：**交换机那一侧的计数器完全干净**。端口 up、光功率正常、出口丢弃为零，因为包确实转发到了这台机器，只是没进到应用。你在交换机上无论查多久都是零证据，这也是这类工单最常被拖成两周的原因。

取数要带基线。`ethtool -S` 出来的多数是自开机以来的累计值，直接把 847 读成「丢了 847 个」没有意义，得算速率：

```bash
ethtool -S eth0 | grep -Ei 'drop|miss|fifo|crc|error'
# 两次采样间隔 60 秒，取差值
```

丢包率的分母用同一段时间的 `rx_packets`。0.001% 在万兆上行上等于每秒几个到上百个包（取决于包长：1500 字节约 815 kpps，64 字节约 14.88 Mpps），TCP 单流会缩窗，但 ping 一百个包只丢一个——第 02 课那张「ping 通了 20 个包，恰好一个没丢」的工单，物理基础就在这里。

### 256 个描述符，在万兆上是 17 微秒的缓冲

`ethtool -g eth0` 看 ring buffer 的三个值：最大值、当前值。出厂默认常是 256，很多驱动保守，很多发行版装完就是这个数。

算一遍它到底能装多少：

```text
容量：256 个描述符 × 1.5 KB（一个 skb 加头部预留）= 384 KB
千兆线速大包：384 KB ÷ 125 MB/s = 3.07 ms
千兆线速小包：256 ÷ 1.488 Mpps = 172 µs
万兆线速小包：256 ÷ 14.88 Mpps = 17.2 µs
```

最后一行是这节的标题。万兆口上跑 64 字节小包打到线速，ring 每 17 微秒轮流一次。内核从收到中断到把描述符取走，中间要经过合并、软中断调度、同核上其他任务的抢占——这段延迟在 17 微秒里放不下。链路一出现微突发（第 40 课），`rx_fifo_errors` 就开始涨，丢掉的包 TCP 重传，业务表现为「时快时慢，看不出规律」。

一次批量同步能把这个窗口踩实。09:00 四十台机器同时拉一个包，某台在 200 ms 里收 300 MB（≈1.5 GB/s，超过万兆线速，多出来的部分被上行汇聚设备排队后成串推下来），ring 只有 384 KB，等于 0.26 ms 的量。这一波里丢多少取决于驱动多快能把描述符还回来。

改法只有一条：

```bash
ethtool -g eth0                       # 先看当前值与上限
ethtool -G eth0 rx 4096 tx 4096       # 不能超过 -g 报的 max
```

代价要算清。4096 × 1.5 KB = 6 MB 每队列，8 个接收队列就是 48 MB 常驻内存。一台 48 核的机器上配 16 队列，96 MB 就出去了，三千台机器是 96 MB × 3000 ≈ 281 GB——这笔账在几千台机器的规模上是要报批的。

配大 ring 治的是抖动，不治吞吐不足。链路真的打满了，加 ring 只是把丢包从网卡挪到上行交换机。

还有一层不在这三个计数器里：`/proc/net/softnet_stat` 的第二列是内核收包队列溢出（`dropped`）。ring 配到 4096 还丢，看这里。这一列涨说明瓶颈在软中断处理，方向是 RPS/RSS 与中断绑核，跟网卡无关。

## offload 开着，抓到的分段不是网上的分段

上一课在两端抓包对照。这里有个前提要先拆掉：抓到的包，未必是线上跑的包。

`ethtool -k eth0` 看 offload 开关，几个关键项：

| 开关 | 作用位置 | 对抓包的影响 |
|---|---|---|
| `tso` / `gso` | 发送侧，网卡切段 | 本机抓包看到 64 KB 的「TCP 段」，线上是多个 1448 字节的包 |
| `gro` | 接收侧，内核合并 | 本机抓到的入向包被合并成大段，包数与时间戳都不对 |
| `lro` | 接收侧，网卡合并 | 比 GRO 更彻底，连转发出去的包都可能已合并 |
| `tx-checksumming` / `rx-checksumming` | 校验和由硬件算 | 抓到的校验和是错的或全 0，别当成损坏 |

推论很硬：开着 TSO/GRO 抓包，你数出来的包数、量出来的包长、看到的握手时序，全是主机的视角，不是链路的视角。拿它算 PPS 会少算，拿它看 MTU 问题会看不出，拿它判断「有没有分片」直接判错。

要拿真实分段就得关掉：

```bash
ethtool -K eth0 gro off lro off     # 只在诊断窗口里关，抓完就开回来
tcpdump -i eth0 -s 96 -w /tmp/cap.pcap 'tcp port 3306'
```

关 GRO 会让 CPU 涨，高pps机器上可能直接丢包，反过来污染你要抓的东西。诊断窗口控制在几分钟内，抓完立刻开回来——这是第 42 课那条「按接口限、按时长限」的具体落点。

## 应用 accept 不过来，与网络丢了，是两条路

到这里两种慢还混在一起。分开它们只需要三个计数器。

```bash
ss -s                                  # 总览：timewait、orphaned、closed
ss -lnt                                # 每个监听口：Recv-Q / Send-Q
grep -E 'ListenOverflows|ListenDrops' /proc/net/netstat   # 表头 TcpExt 那一行
awk '/^Tcp:/ {print "RetransSegs=" $9}' /proc/net/snmp     # 值行第 9 个字段，换内核先用表头行核对
```

`ss -lnt` 里 LISTEN 状态的两列语义和 ESTAB 不同：Send-Q 是 backlog 上限，Recv-Q 是已完成三次握手、还等着 `accept()` 的连接数。后者长期非零，应用就是慢在收连接这一步。

| 现象 | 计数器 | 结论 |
|---|---|---|
| 等待 accept 的连接堆积 | `ss -lnt` Recv-Q 持续 > 0，`ListenOverflows` 涨 | 应用 accept 循环被阻塞，跟网络无关 |
| 连接能被拒 | `ListenDrops` 涨 | backlog 满了，内核直接丢 SYN，客户端表现为超时重连 |
| 包丢了但主机侧干净 | `rx_*` 不动，`RetransSegs` 按丢包率涨 | 真丢在路径上，有证据派单 |
| 包丢在主机 | `rx_fifo_errors` / `rx_missed_errors` 涨 | ring 或软中断，改配置 |
| 表满 | `dmesg` 里 `nf_conntrack: table full` | 主机防火墙或 NAT 设备，跟链路无关 |

`TCPRetransSegs` 是全网最诚实的一个计数器，也是最容易被误读的一个。它涨只说明有重传，重传的成因可能是路径丢包、对端 ring 溢出、也可能是乱序——乱序会触发伪重传，而乱序在 ECMP 多路径上是常态（第 12 课）。所以它只能作为「有异常」的信号，方向靠 `rx_*` 与路径探测补齐。判断重传是丢包引起的还是乱序引起的，看 `RetransSegs` 与 `InErrs` 是否同时涨。只涨重传、入向错误为零，优先怀疑乱序。

### 主机侧嫌疑表

把这一课的判据压成一张表，工单进来先跑一遍，十分钟能省掉两周。

| 嫌疑 | 证据 | 结论 | 下一步 |
|---|---|---|---|
| ring buffer 太小 | `rx_fifo_errors` 速率 > 0，`ethtool -g` 当前 256 | 网卡侧丢包 | `-G` 调到 4096，观察一个业务高峰 |
| 软中断处理不过来 | `softnet_stat` 第二列涨，`rx_missed_errors` 涨 | 主机侧丢包 | 中断绑核、RPS、加队列 |
| 应用 accept 慢 | `Recv-Q` 长期 > 0，`ListenOverflows` 涨 | 应用问题 | 转应用侧，网络无责 |
| 物理层误码 | `rx_crc_errors` / `rx_frame_errors` 涨 | 真链路问题 | 换模块/跳线，查光功率（第 06 课） |
| offload 制造假象 | 抓包里出现 64 KB TCP 段 | 证据不可用 | 关 GRO/LRO 重抓 |
| 路径上真丢 | 主机计数器干净，`RetransSegs` 涨，mtr 终点也丢 | 网络侧问题 | 按第 43 课定位到跳，带证据派单 |

最后一行是这张表的价值所在。它把「我怀疑是网络」变成「主机侧三个计数器全为零，路径终点丢 2.8%，这是证据」。反过来，前两行把一张本该派给网络的单子留在主机侧，省下的是机房里两个人两天。

会失败的样子：某机架四十台服务器报「网络丢包」，每天上午九点最严重。网络团队换了两块光模块、重插了六根跳线、爬了三轮配置，历时两周。最后是 `ethtool -g` 报 256，`rx_fifo_errors` 在这两周里涨了 41 万次，而同期交换机端口出口丢弃为零。改成 4096 之后，工单消失。

这段的代价算得出来：两周两人力 = 20 人日，两块光模块按 2000 元一块 = 4000 元，真正的修复动作是一次 `ethtool -G`，两分钟。误判的成本不在钱上，在那两周里所有人对「网络丢包」这个结论的信任度。

## 判据

一台应用服务器，业务抱怨「每晚八点卡，十几分钟就好」。交换机侧端口 up、出口丢弃为零，路径探测终点丢包 0.0%。主机侧数据如下：

```text
ethtool -g eth0:   RX 256 / TX 256   (max 4096)
采 60 秒差值：rx_fifo_errors +118,204   rx_missed_errors +4,102
             rx_crc_errors 0   rx_packets +21,300,000
ethtool -k eth0:  tso on  gro on  lro off
ss -lnt:          LISTEN Recv-Q 0   Send-Q 128
/proc/net/netstat TcpExt 行：ListenOverflows 0   ListenDrops 0
RetransSegs 60 秒 +9,847
```

三个问题：

1. 丢在哪一层，判据是哪两个数字的比值
2. 该不该派给网络团队，一句话给出理由和证据
3. 有人在同机抓包，看到平均段长 22 KB，这个结论能不能用

验收标准三条：能算出丢包率，能说出第一优先级动作与它的代价，能指出那份抓包结论为何作废。

::: details 参考

1. 丢在网卡。丢包率 = 118,204 ÷ 21,300,000 = 0.55%，`rx_fifo_errors` 与 `rx_missed_errors` 同时涨，`rx_crc_errors` 为零，排掉物理层。`RetransSegs` 涨是结果，重传是这一层丢包的下游现象。
2. 不该派。判据是交换机出口丢弃为零、路径终点丢包 0.0%、主机侧接收错误计数在涨。三处对照里两处干净，病灶在本机 ring。第一动作是 `ethtool -G eth0 rx 4096`，代价是 4096 × 1.5 KB = 6 MB 每队列的常驻内存。
3. 不能用。`gro on` 会把入向包合并，22 KB 的平均段长是主机侧的观察值。诊断时要关 GRO 重抓，窗口控制在几分钟，抓完开回来。

:::

## 小结

`rx_fifo_errors`、`rx_missed_errors`、`rx_dropped` 是网卡侧丢包，交换机永远看不见它们。这层丢包的玩法是算容量：256 个描述符 384 KB，万兆小包下 17 微秒见底。

offload 开着，抓包给的是主机视角的包，包长与包数都不是线上的。诊断时临时关掉，抓完开回来。

`Recv-Q`、`ListenOverflows`、`RetransSegs` 三个数把「应用慢」和「网络丢」分开。分开之后才谈得上派单，否则两拨人互相举证。

## 思考

1. 你那批机器 `ethtool -g` 报的是多少？有多少台还在出厂默认值上？
2. `RetransSegs` 在涨而主机侧计数器全干净，你会先怀疑丢包还是乱序？用哪两个数分开它们？
3. ring buffer 从 256 调到 4096，丢包只是减少而没有消失。下一个方向是什么，代价比内存大还是小？
