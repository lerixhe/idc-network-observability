上一课在主机侧看 ring buffer 和 offload 造成的假象，这一课回到设备侧。有一批数字 SNMP 给不出来，只能登上去敲命令。

## 队列深度、BGP 邻居、MAC 表：SNMP 拿不到的那一半

`ifTable` 加 `ifXTable` 撑起了端口的状态与计数，平台的地基就在这里。往上一层问，路会断。

| 想要的数据 | 标准 MIB | 卡在哪 | 只好走 CLI |
|---|---|---|---|
| 出队列深度、buffer 池占用 | 无 | 厂商私有 OID，同一家不同版本也对不上 | `show interface queue` 一类 |
| 完整 MAC 表 | `dot1dTpFdbTable` | 几十万条一次 walk 几分钟，按 VLAN 分表时给不全 | `show mac address-table` 一类 |
| BGP 邻居状态与建立时长 | BGP4-MIB | VRF 与 IPv6 多实例支持参差 | `show bgp neighbor` 一类 |
| 硬件清单与序列号 | `entPhysicalTable` | 常列到板卡为止，模块字段空白 | `show inventory` 一类 |
| 光模块诊断细项 | 私有 MIB | 只报五参量粗值，误码分级拿不到 | `show interface transceiver` 一类 |

命令名是示意，不同厂商差得远，同一个命令在同一个厂商的不同平台上也可能不同名。

于是每个平台里都有一条「SSH 执行命令 + 解析文本」的通路。它的定位是 SNMP 的补集：SNMP 走周期、走大覆盖、走机器可读；CLI 走按需、走小范围、走文本解析。主力采集还得留在 SNMP，拿 CLI 顶上去，一周就能把几百台设备的管理面拖垮——第 17 课那笔 CPU 账在这里只会更难看，一条命令的输出序列化比一次 GetBulk 贵一个量级。

这条通路容易被写成某个工程师顺手写的 SSH 脚本，长在平台外面，谁也不敢改。它得被当成受管组件来做。五条约束，缺哪条都会出一次事故。

## 五条约束，每条带一次事故

**一、只读白名单。** 命令按「型号 + 命令串 + 参数模式」三元组列入白名单，白名单之外一律拒绝。禁止前缀判断，「以 show 开头就放行」会放行 `show run | redirect flash:/x`，这条命令把输出写到设备 flash，写满就报存储告警。管道参数只放 `| include`、`| match`、`| count`。

事故是这样的：`clear counters` 看着像读操作，实际把接口错误计数清零。故障前有人跑过一次，误码累计从 8.4 万变成 0，复盘时判不出这条链路是长期劣化还是突发劣化，最后按「疑似」结案。白名单得按语义审，按字面审必然漏。

**二、并发与限流。** 硬规矩：一台设备同时只有一个 CLI 会话。真正的约束在 VTY 线路数量——多数设备只有 5–16 条，采集器开 50 并发就把登录取空。故障时人自己登不上去，这是最坏的一种越权。

会话时长的账：

```text
单会话     登录 1.5 s + 命令 2 s + 输出传输 4 s ≈ 8 s
800 台全量 800 × 8 = 6,400 s 会话时长
并发 20    6,400 / 20  = 320 s  ≈ 5.3 分钟 / 轮
并发 5     6,400 / 5   = 1,280 s ≈ 21 分钟 / 轮
并发 107   6,400 / 107 ≈ 60 s   ← 这时被打满的是设备的 vty
```

结论很硬：CLI 采集的周期下限是分钟级。15 分钟一轮，并发 3–5 就够。想压到 60 秒，先确认设备有多少条 vty 空着。

**三、超时与降级。** 三个超时分别设：建连 3 s，输出静默 10 s，单条命令总时长 30 s。三个都要，缺一个就有一次卡死。超时后必须能中断——发会话中断符，或者断链并确认设备侧会话已释放，别留一个半开会话占着 vty。

只有建连超时的后果：一条 `show tech-support` 吐 20 MB，采集器读了 40 分钟，任务队列积压 1,700 条。第二天的日报是空的，队列里的任务全过期了还在跑。

降级三层：单条超时记 `timeout`、不写值；同一设备连续 3 次超时降到 1 小时一轮，进「CLI 不可用」清单；连续 24 小时不可用就摘出采集池并开工单。输出要有上限，单条 1 MB / 4 万行，超了截断并落 `truncated=true`，截断的数据不进趋势图。

**四、输出解析。** textfsm 模板按「厂商 + 平台 + 命令 + 固件大版本」四元组建索引，模板文件头写版本号，每条落库数据带 `template=counter-v3`。版本号跟着数据走，半年后才说得清这条曲线是哪套解析器算出来的。

反面写法先说清：解析不到就写 0。0 会变成曲线上的一个点，而队列深度 0 意味着「很健康」。连续两周的零曲线说明解析器坏了，平静是它的假象。正确做法是返回显式错误，落库写 `NULL` 加 `parse_error`，聚合跳过它，面板上留一个缺口。

**五、审计留痕。** 每条记录六个字段：采集器实例、会话起止时间、设备、命令原文、拿到多少行、结果码。留存 30 天，与举证期对齐（第 10 课）。

审计的第二个用途更常用：证明平台没动过设备。设备自己重启，厂商第一句话常常是「你们是不是跑了什么命令」。翻不出命令原文，这句质疑只能靠嘴接。

## 格式漂移，比解析器写错更常见

模板写对一次不难，难在三年后它还对不对。固件升级不受你控制，一次升级可能加列、改单位、换语言。这是稳态，偶发才是例外——某平台一年处理 47 次漂移，其中 12 次把解析成功率从 100% 打到 0。

| 漂移类型 | 长什么样 | 检测办法 | 兜底 |
|---|---|---|---|
| 列变多 | 中间插一列 `Output errors` | 整行匹配失败，模板级失败率跳到 100% | 按表头取列名，不按列序取值 |
| 列名改动 | `Output Queue` → `Output queue` | 关键字段全空但行数正常 | 大小写与空格归一化后再匹配 |
| 单位变化 | bytes 改成 packets，bps 改成 pps | 数值同比跳 2 个数量级，同期无业务事件 | 单位进 schema，落库带单位，不做隐式换算 |
| 数值格式 | 千分位逗号、`1.2M`、`--`、`N/A` | 解析值落在合理区间外 | 统一归一化函数，非法值标 `invalid` |
| 分页与截断 | `--More--`、行尾省略号 | 行数低于基线，或末尾出现提示符 | 会话开头关分页；截断打标 |
| 语言切换 | 列名变中文，表头变宽 | 字段全空、行数正常 | 模板按语言分文件，索引加语言维度 |

三条检测手段能兜住大半：模板级解析失败率（按型号聚合，超 5% 告警）、字段数变化（模板声明 5 个字段，输出给出 6 列）、数值量级突变（同一指标跨版本比，跳两个数量级就人工看一眼）。

兜底的顺序：新模板与旧模板并存，不覆盖——固件分批升级的半年里两种格式同时在线；解析失败先降级到「只存原文」，原文留 7 天，模板修好之后重放；失败率告警走低优先级通道，这条告警一响就是几百台。

## 一段 textfsm 与两份输出

下面三段都是示意，字段名与列宽不对应任何真实厂商。

命令输出，固件 r9.2：

```text
dev-a# show interface counters
Interface    Input        Output       Input        Output
             packets      packets      errors       drops
ge-0/0/1     18420331     19204881     0            0
ge-0/0/2     902114       884310       12           0
ge-0/0/3     0            0            0            0
```

模板 `counter-v3`：

```text
Value INTERFACE (\S+)
Value IN_PKTS (\d+)
Value OUT_PKTS (\d+)
Value IN_ERR (\d+)
Value OUT_DROP (\d+)

Start
  ^Interface\s+Input\s+Output\s+Input\s+Output\s*$$
  ^\s*packets\s+packets\s+errors\s+drops\s*$$ -> Data
  ^\s*$$
  ^. -> Error

Data
  ^${INTERFACE}\s+${IN_PKTS}\s+${OUT_PKTS}\s+${IN_ERR}\s+${OUT_DROP}\s*$$ -> Record
  ^\s*$$ -> Start
  ^. -> Error
```

同一台设备升到 r10.1 之后：

```text
dev-a# show interface counters
Interface    Input        Output       Input        Output       Output
             packets      packets      errors       drops        errors
ge-0/0/1     18420331     19204881     0            0            0
ge-0/0/2     902114       884310       12           0            3
```

六列对五条 Value，`Data` 那条正则整行匹配不上，落到 `^. -> Error`，模板抛错。这是好的失败：采集侧收到明确的解析错误，写 `NULL`，面板出现缺口，模板级失败率告警起。

坏的失败长另一边：模板报错之后，有人图省事，给 `Data` 那条正则尾巴补一个 `.*`。六列照样匹配，多出来的 `Output errors` 被 `.*` 吃掉，五个字段全填对，少的那一列半年没人发现——等到有人问「这个口有输出错误吗」，库里压根没有这一列。

解析完统一成这个结构：

```text
{device: "dev-a", port: "ge-0/0/2",
 in_pkts: 902114, out_pkts: 884310,
 in_err: 12, out_drop: 0,
 unit: "packet", template: "counter-v3", firmware: "r9.2",
 captured_at: "2024-06-11T06:23:07Z", source: "cli"}
```

`unit`、`template`、`firmware` 三个字段必须跟数值一起落库。少了 `unit`，一年后没人知道这条曲线的纵轴是字节还是包——第 36 课那些口径问题，源头常常就在这里。

## 判据

一台设备固件从 r9.2 升到 r10.1，采集侧看到这些：

```text
02:00          固件升级（变更单 CHG-4471）
00:00–02:00    counter-v3 解析失败率  0.0%
02:10–06:00    counter-v3 解析失败率 100.0%
同期           SNMP 采集正常，端口 up 数 48 不变
```

四问：

1. 这 100% 算什么故障，该进哪个告警通道，优先级比「设备失联」高还是低？
2. 这四个小时库里该写什么？写 `NULL`、写 0、还是不写这条记录，各自的后果是什么？
3. 修的时候动哪三样东西，为什么不该动设备侧？
4. 如果平台当初的设计是「解析不到就写 0」，这四小时在面板上长什么样？

验收标准：第一问答出「采集可用性故障」并给出通道选择；第二问卷出 `NULL` 与 0 的差别，落到「零曲线看不出坏」；第三问答出模板新增一版、索引加固件维度、失败样本进回归。

::: details 参考

一、采集可用性故障。走「CLI 不可用」清单加低优先级告警，优先级低于设备失联——设备还在，SNMP 数据完好，缺的是 CLI 那一列。

二、写 `NULL` 加 `parse_error`：曲线缺口，聚合跳过，能被看见。写 0：队列深度连续四小时为 0，面板显示健康。不写记录：等于告诉下游「那段时间没采」，但没人会去看采集器自己的统计。

三、模板加 `counter-v4` 认六列、模板索引加固件大版本、把这四小时的原文抽三份进回归样本。设备侧不能动，固件回退的代价远大于改一个模板。

四、一条贴着零轴的直线，全绿。有微突发的那几个小时也压在这条直线上，第 40 课讲的那种丢包，在这里彻底看不见。

:::

## 小结

SNMP 覆盖状态与计数，队列深度、完整 MAC 表、BGP 邻居这些藏在 CLI 里。平台里那条 SSH 通路只是补集，主力采集留在 SNMP。

五条约束：白名单按语义审、一台设备一个会话、三个超时都要、解析失败写 `NULL`、命令原文留 30 天。

格式漂移是失败主因。列变多、单位改、语言换，都能用「字段数 + 版本号」的比对抓住，抓住之后让新模板与旧模板并存，别覆盖。

下一课换维度：数据都对上了，时间对不对得上。

## 思考

1. 你平台的 CLI 白名单按命令前缀判断还是按完整串判断？`| redirect` 能不能穿过去？
2. 一台设备的 vty 是 5 条，你的采集器并发多少？这个数除以设备数，故障时你还登得上去吗？
3. 模板失败率从 0% 跳到 100% 会有告警，从 0% 跳到 3% 不会。哪一种漂移只造成 3%？
