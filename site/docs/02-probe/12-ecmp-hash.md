## 一条流只走一条分支

上一课按链路条数算覆盖率和成本。这个分母不对。两个地址之间通常不是一根线，是一组等价路径。

```text
                ┌── Spine-1
   TOR-A ───────┼── Spine-2
                ├── Spine-3
                └── Spine-4
```

四条上行等价，设备挑一条。挑法叫 ECMP：取出包头里几个字段算哈希，取模落到某个 bucket，bucket 绑死出端口。源 IP、目 IP、源端口、目端口、协议，五个字段一个字节都不变，哈希结果恒定，包永远从同一个口走。

结论很硬：**你以为在测一条链路，其实在测一条哈希路径**。另一条成员的光模块劣化三个月，你的探测包一次都没从它身上过，RTT 曲线平得像尺子。

例外只有一类：逐包轮转的设备，同一个流的不同包分头走。IDC 里少见，它会让乱序变严重，做 spine-leaf 的芯片基本不用。默认按流哈希，碰上轮转的单独标出来。

顺带一句，LAG 聚合口的成员选择用的是同一套哈希。下面关于 ECMP 的每一句，对 bond 的四条腿同样成立。

从这里能推出一个反直觉的事。常说「固定五元组覆盖率 50%」，这句话本身没有意义。M=2 的时候一条流要么落 A 要么落 B，一次测量的读数只有 0 或 100%，没有 50% 这个东西。50% 是多次实验的期望，不是任何一次测量的结果。分清这两者，后面才算得动预算。

## 哈希场域不止五元组

哈希输入叫场域（hash field）。五元组是最小集，各家往里面加料。

| 字段 | 是否必选 | 能不能改 | 改了会怎样 |
|---|---|---|---|
| 源 IP | 常见必选 | 能，要多个源地址 | 占地址池，代价最高 |
| 目的 IP | 必选 | 不能 | 改了就换了测量目标 |
| 源端口 | 常见必选 | 能，几乎零成本 | 首选散列手段 |
| 目的端口 | 常见必选 | 不能 | 业务端口固定 |
| 协议号 | 必选 | 能，但只有三档 | 颗粒太粗 |
| 源/目 MAC | 部分设备参与 | 同网段内能改 | 只影响二层转发 |
| 入接口 | 部分设备参与 | 不能 | 决定不了 |

七行里只有源端口可自由取值、不影响语义、不额外占资源。UDP 探测包源端口从 20000 换成 20001，场域变了，哈希重算，落点重选。整本书的散列手段都压在源端口上，原因就在这张表。

两个坑。一，部分设备把入接口算进场域，探针换个口插进来，路径就变了——换板卡之后这事静默发生，覆盖率的账跟着变。二，隧道封装把内层五元组藏起来，中间设备只看外层隧道端点地址，源端口怎么调都在同一条隧道里，散不开。

再记一件会让覆盖率账本作废的事：哈希种子（hash seed）。部分设备支持配种子、配置重载后重算 bucket，同一组五元组的落点会整体搬一次。改动那天什么都正常，第二天你发现探到的那条腿换了——不是设备坏了，是账本过期。探针侧要把源端口段与落点一起记账，落点变了从头统计。

## 覆盖率是一条收敛曲线，能自己算

设 M 条等价成员，哈希均匀，每次的源端口独立随机。N 个流之后，某条指定成员一次没被命中的概率是 (1−1/M)^N。M 条全被命中过的概率，按独立近似：

C(N) = [1 − (1 − 1/M)^N]^M

代入 M=4：

| N | (1−1/M)^N | C(N) | 漏掉至少一条 |
|---|---|---|---|
| 1 | 0.7500 | 0.4% | 99.6% |
| 4 | 0.3164 | 21.8% | 78.2% |
| 8 | 0.1001 | 65.6% | 34.4% |
| 16 | 0.0100 | 96.1% | 3.9% |
| 24 | 0.0010 | 99.6% | 0.4% |
| 32 | 0.0001 | 99.96% | 0.04% |

N=16 手算一遍：0.75^16 = 0.010023，1 − 0.010023 = 0.989977，四次方 = 0.9605。

曲线形状有用。前 4 个流只买到 21.8%，8 到 16 这一段冲得最猛（65.6% → 96.1%），过 24 个流基本封顶，再堆端口只补最后零点几个百分点。顶在哪由最不常被抽中那条成员决定，单个成员漏掉的概率按幂次衰减，覆盖率跟着按幂次收敛。曲线线性外推会出错：16 个端口给 96.1%，不是「32 个给 192%」。

一对目的地址配 16 个源端口，成本 16 包/轮，换 96.1%。加到 32 个只多 3.9 个百分点，不值。

M 变宽，收敛变慢。M=8 时 N=16 的覆盖率是 [1−0.875^16]^8，0.875^16 = 0.11807，1 − 0.11807 = 0.88193，八次方 = 0.3660，就是 36.6%。同样 16 个端口，八分支只覆盖三分之一多一点。上行的 ECMP 宽度必须先查清，再定端口预算。

比公式更麻烦的是 bucket 分配不均。1024 个硬件 bucket 分给 4 条成员，常见 37% / 33% / 24% / 6%。那条 6% 的腿，单个流命中概率 0.06，要 95% 把握至少踩到一次，N ≥ ln0.05 / ln0.94 = 48.4，取 49。均匀假设下 24 个流够，不均假设要 49 个，差一倍。

权重还要单算。6% 的成员慢下来，对总流量的影响只有 6%，端到端均值几乎不动。覆盖率够了不等于影响看得见。

## 多跳把路径空间乘起来

单跳 4 分支，三跳就是 4×4×4 = 64 条端到端路径，每跳独立算哈希。把 M 换成 64 代进同一个式子：

```text
[1 − (63/64)^N]^64 ≥ 0.90
(63/64)^N ≤ 1 − 0.9^(1/64) = 1 − 0.998355 = 0.001645
N ≥ ln(0.001645) / ln(0.984375) = 6.4095 / 0.015748 = 407
```

四百个流才 90% 的路径覆盖。这四百个流在每一跳上的落点还是随机的，越深的跳越难保证每条成员被踩到。

工程上不追端到端路径覆盖，改追**逐跳覆盖**：只要求每一跳的每条成员在统计窗口内被至少一个流命中。流数需求取 max(各跳需求)，不是各跳相乘。同样几百个流，配得巧可以满足每跳 90% 以上。第 50 课那句「按机架和上行算出值得探的链路」，算的就是这个数：链路条数，不是路径条数。

一个判断后果跟着来。端到端路径覆盖上不去，「这条路径上的每一跳我都测过了」这句话就说不出口。举证包里能写的是「这一跳的每条成员都被探到，那一跳的第 3 条成员整窗无数据」——覆盖逐跳标，不按路径标（第 10 课）。

## 一条成员劣化，均值什么都看不见

失败形态很具体。4 条 10G 上行的 LAG，第三条光模块老化，收光从 −6 dBm 掉到 −13 dBm，误码上来，重传把这条腿上的流时延从 0.12 ms 抬到 1.4 ms。

四个计数器全绿。聚合逻辑口 up，40G 带宽用一半，端到端 RTT 均值从 0.9 ms 涨到 1.2 ms——这个幅度落在日周期波动里，看曲线的人不会多看一眼。

按流看才看得出来：25% 的流慢十倍，p99 从 1.1 ms 到 4.8 ms。均值 1.2 ms 是 0.75×0.9 + 0.25×1.4 的加权，一条劣化腿被三条好腿冲平了。

三个可观测切入点，从便宜到贵。

```bash
# 主机侧：聚合口成员状态与各腿流量
awk '/Slave Interface|MII Status|Link Failure Count/ {print}' /proc/net/bonding/bond0
```

`MII Status: up` 而 `Link Failure Count` 在涨，这条腿在闪，没彻底断。再看各腿包计数是否均衡：不均衡是哈希分布偏了，不是这条腿坏了。

```text
设备侧逐成员口取 ifHCInOctets / ifHCOutOctets
  四条腿出口字节偏差 > 15%     → 哈希分布偏，或某条腿在丢（第 18 课的速率算法）
  单口 dot3StatsFCSErrors 与 ifInErrors 同步上涨 → 光或线的问题（第 06 课）
  单口 error 涨而流量低        → 这条腿在劣化，只是承载的流少
```

第三处是探测自己：给每个探测结果打上「源端口 → 命中哪条成员」的标签，直接看每条成员的 RTT 与丢包。这一处最贵，没有 INT 只能靠端口计数器反推（第 13 课）。

会失败的样子：平台只看聚合口和端到端均值，一条成员带误码跑了三个月。业务方的描述是「有时候慢」，拿出来的证据是一段毫秒级波动的曲线，谁都不认。代价不是查错方向，是这条腿一直烂到光模块彻底报废才被发现。

## 判据

某个 TOR 到 Spine 的上行，4 条 10G，ECMP 4 分支。现有探测配置：

```text
目标：192.0.2.10 → 198.51.100.1
协议：UDP
周期：每 60 秒一轮
源端口：20000–20004 五个固定值
哈希场域：源 IP、目 IP、源端口、目端口、协议
```

C(5) = [1−0.75^5]^4 = 0.7627^4 = 33.8%。平台上报的覆盖率是「上行 4 条已探」，实际只有三成四的概率把四条都踩到。

三个问题，先自己写，再看参考：

1. 这 33.8% 漏的是哪一类故障
2. 用端口段预算把覆盖率补到 90% 以上，端口段怎么分，每对目的地址的探测包速率变成多少
3. 补完之后还剩什么看不见

验收标准三条：能说出漏掉的故障类型并给一个具体例子；算出 N 与端口段，写出速率；给出至少两处残余盲区。

::: details 参考

补到 90% 要 N=13：[1−0.75^13]^4 = [1−0.023756]^4 = 0.976244^4 = 90.8%。端口段取 16 个（20000–20015），留三个余量给端口占用和配置漂移，覆盖率 96.1%。

速率：一轮 16 个包，60 秒一轮，16 / 60 = 0.267 pps 每对目的地址。原来 5 个端口是 0.083 pps。翻三倍多，对设备毫无影响。

漏掉的故障：只落在未命中成员上的那类。4 条腿各 25% 的流，33.8% 的覆盖率意味着任何一轮都有 66.2% 的概率至少有一条腿整轮零数据，那条腿恰好在这轮劣化的概率不受你控制。具体例子是 6% 权重成员误码：均匀假设下 16 个流都不一定踩到，33.8% 的配置更没戏。

残余盲区两处。一是采样权重失真：16 个源端口等概率发，实际流量在 4 条腿上是 37/33/24/6，探到的比例不代表流量比例，用它算「这条腿的丢包影响了多少业务」会错。二是第二跳之后的 ECMP：TOR→Spine 覆盖了，Spine→Core 的哈希另算一套，源端口在那段重新洗牌，逐跳覆盖得逐跳做。

加分项：一轮必须把 16 个端口全发一遍。随机抽 4 个发，覆盖率立刻退回概率游戏，且不可复现——同一个故障窗重跑一次，命中的腿不一样，举证时说不清。

:::

## 小结

ECMP 按五元组哈希选出端口，同一组五元组的探测包永远只走一条成员。你以为在测链路，实际在测一条哈希路径。

场域七项里只有源端口能自由改。改它，哈希重算，路径重选。

覆盖率按 C(N) = [1−(1−1/M)^N]^M 收敛，M=4 时 16 个源端口给 96.1%，再往上不值。M 变宽、bucket 不均、多跳相乘，三个因素都让同一份端口预算买到的覆盖变少。

一条成员劣化时，聚合口正常、均值正常，只有按流看才现形。最便宜的切入点不在交换机上，在 `/proc/net/bonding`。

覆盖的账算清了，还剩一件问不出来的事：这条路上到底哪一跳慢。下一课让包自己带答案。

## 思考

1. 你的上游 ECMP 有几条等价路径？这个数能从哪几个地方读到，谁对它负责？
2. 端口段从 16 个扩到 64 个，覆盖率只涨几个百分点，探测包翻了四倍。这笔账在什么规模下会反过来算？
3. 一条成员只承载 6% 的流量，端到端 p99 涨了三倍。举证包里给哪两张图，才能说清这不是「整体变慢」？
