title: 23 · CMDB 是主数据

上一课把流记录做成了可查的表，每条记录都带 `device` 和 `ifName` 两个标签。这一课问一句：这两个标签是谁给的，给错了会错成什么样。

## 改一次名字，曲线断成两截

一台 TOR 的主机名从 `tor-3f-02` 改成 `TOR-A3F-02`。新规范要求全大写，改名的人花了 40 秒，顺手在台账里改完就下班了。

数据形态在改名那一刻分叉：

```text
改名前   ifHCInOctets{device="tor-3f-02",  ifName="ge-0/0/1"}
改名后   ifHCInOctets{device="TOR-A3F-02", ifName="ge-0/0/1"}

查询 device="tor-3f-02"   → 只返回 00:00 到 14:22 的点
查询 device="TOR-A3F-02"  → 只返回 14:23 之后的点
```

两条曲线各自完美。大盘按 `sum by (device)` 聚合，改名当天这台设备的总流量掉到零再重新爬，画出一个「先下线再上线」的 V 字。没人报警，因为 V 字的两头都是真实数据。

更安静的一处是告警规则。规则里写着 `device="tor-3f-02"`，改名后它匹配零个对象。多数时序系统对空匹配不报错，规则状态停在 `inactive`，列表里还挂着，绿得让人放心。这台设备的端口 down、CPU 高、光功率低，从此全部静默。

代价算得出来。一台 48 口设备按 20 个指标估，48 × 20 = 960 条 series，60 秒一个点，一天 1,382,400 点。一个 300 台设备的 IDC，全部改名就是 300 × 960 = 288,000 条 series，历史要回填 300 × 138.2 万 ≈ 4.1 亿点。按 5 万点/秒的回填速度，4.1 亿 ÷ 5 万 = 8,294 秒，2.3 小时。这 2.3 小时里查询走别名映射，存储同时存在新旧两份。

台账上改 40 秒，事后补 2.3 小时。这个比例是主数据的典型比例。

## 换一块业务板，新端口接上了旧端口的历史

48 口千兆板换成 48 口万兆板。厂商的 `ifIndex` 按板卡位置和初始化顺序生成，换板之后整段索引会漂移：旧板占 501–548，新板占 601–648，而 501–548 这一段可能被新板的逻辑口重新占走。

主键写的是 `(device_id, if_index)`，两边都不变，于是新端口的第一条记录写进了旧端口的历史。

```text
t-1 天   if_index=524   ifName=ge-0/0/24   流量 320 Mbps    ← 旧千兆口
t   天   if_index=524   ifName=xe-0/0/24   流量 9.2 Gbps    ← 新万兆口
```

曲线在换板那一刻跳一个 28.75 倍的台阶（9.2 Gbps ÷ 320 Mbps），然后平稳。看起来像一个「业务量上涨」的故事：曲线平滑、没有断点、`rate()` 算得出来、基线也跟着上去了。

有一次真实排查是这样的。业务方说这条链路「昨天开始丢包」，运维打开曲线，看见一条从未见过的流量，两天里查了光模块、查了对端、查了限速策略，最后发现那是邻居端口的历史被接了过来。两个人两天，四十八人时，根因是一个字段的语义。

点的数量能估。48 口 × 90 天 × 1440 点 = 6,220,800 点混在两段历史里，无法自动分离。只能按 `ifName` 变更的时刻把数据切开重算，切完还要人工确认哪一段属于谁。库里没存 `ifName` 历史的地方，这一段只能整体删除重采。

硬判断：`ifIndex` 是设备本地的、会变的、而且不通知你的编号。它能做「当前映射」，做不了「历史身份」。主键必须落在 `ifName` 或者更稳的 `port_id` 上。

设备换板不会举手告诉你。唯一线索是 `sysUpTime` 归零，或者 `entPhysicalTable` 里那块板卡的序列号变了。采集每一轮比对 `ifIndex → ifName` 的映射，不一致就断链，不要续接。第 16 课讲的 `ifIndex` 语义和第 17 课讲的采集工程都没提这一步，它属台账。

## 一台报废设备，训练出无视告警的习惯

台账里 3,800 台设备，其中 47 台三年前就拆了，状态那一栏常年写着 `active`。采集器按台账全量轮询，三台一批超时，每天生成 47 条「设备失联」。

47 × 365 = 17,155 条/年。同期真实设备故障告警大约 150 条/年，假告警与真告警的比例 114 : 1。

值班的人第一次会查：登带外、ping 不通、翻台账、发现机器早没了，15 分钟。第二次 5 分钟。第三十次他把这条告警的推送关掉，第四十次他开始跟新同事说「设备失联那条先不用管」。

最坏的后果不是多一条噪声，是训练出了忽略告警的习惯。真有一台核心设备失联那天，那条告警和另外 46 条长得一模一样。

修复代价比想象中高。删台账不是修复：时序库里这 47 台设备的 series 还在，告警历史里 17,155 条记录还挂着它们的 `device_id`，工单里有几十张单引用着同一批 ID。硬删会让这些引用变成悬空外键，查询要么报错，要么静默返回空——后者更糟，因为你不知道自己拿到的是空的。

正路是把状态标成报废，采集器和告警规则按状态过滤（第 24 课的状态机）。已经产生的 17,155 条假告警要批量标注，或者重算基线。这活儿没人愿意干，通常就留着。

三个错法指向同一句话：**CMDB 不是一张表，是其他所有表的引用目标。** 名字、ID、状态交出去那一刻，你就欠了一笔债，还款方式只有三种——软删、迁移、重写历史。

## 名字是人给的，身份必须是机器给的

判断一个字段算不算主数据，只看一条：还有没有第二个地方独立存着它。

主机名只存在 CMDB，时序库只存 `device_id`，这是主数据。主机名同时存在 CMDB、采集配置、告警规则、工单表单里，就有四份副本，改一次要改四处，漏一处就是上面三种错法。

身份字段的要求只有一条：不会因为人的操作而变。

| 候选 | 会变吗 | 能不能当主键 |
|---|---|---|
| 主机名 | 会：规范调整、命名冲突、迁机房 | 不能 |
| 管理 IP | 会，而且会回收复用给别的设备 | 不能 |
| `ifIndex` | 会，换板就重排 | 不能 |
| 序列号 | 不会，RMA 换机是一台新设备 | 能 |
| 资产编号 | 不会，但可能录错、被重录 | 能，要校核 |

`device_id` 从序列号派生，所有表存 `device_id`，展示时 join 出名字。名字改了，join 的结果跟着变，历史一行不用动。

IP 复用这一段值得单独看。10.32.7.18 三年里换过三台设备：第一台报废、IPAM 回收，第二台领到，第二台迁到别的机房、第三台接手。翻去年这个 IP 的流量曲线，三台设备混成一条，而它看起来是一条连续的、有峰谷的线。

改名还有个放大器：命名规范迁移从来不是一台。某次规范调整把 300 台 TOR 全部改成大驼峰，分散在三个月里做完，于是平台上有 300 个断点，每个断点对应一次人工确认。一次性改完反而更好处理——一次别名映射、一次批量回填、一次告警规则改写。**批量比分散便宜，因为代价是固定的，收益是线性叠加的。** 这条判断也适用于机房搬迁、VLAN 大改、厂商替换。

## 引用方向 × 处理策略

平台里指向 CMDB 对象的表，至少有六类。处理策略只有三种，按「能不能重算」分。

| 引用方向 | 典型存储 | 改名 | 删除 | 硬删的后果 |
|---|---|---|---|---|
| 时序标签 | `device`、`ifName` label | 建别名映射，查询时展开 | 停止写入，保留旧数据 | 历史曲线上出现断口 |
| 告警规则与实例 | 规则选择器、告警标签 | 选择器改用 `device_id`，规则不重写 | 规则标「对象已退役」，不删规则 | 规则静默，无人知晓 |
| 工单与变更单 | 设备清单、端口清单 | 冻结快照，不回溯正文 | 冻结快照，加退役标记 | 复盘时对不上当时那台 |
| 拓扑与链路 | 两端 `port_id` 外键 | ID 不变，名字是属性 | 先解链路再删端口 | 悬挂外键，路径算不出来 |
| 采集与探测任务 | 任务目标、管理 IP | 按 ID 重解析 | 任务停用 | 任务报错，或采到新设备 |
| 事件与日志 | 归一化后的对象标识 | 归一化表加旧名映射 | 永不删，只标退役 | 历史事件丢归属 |

三种策略落到纸上：

1. **软删 + 别名**：名字会呼吸的那一类。时序标签、日志归一化映射都属此列，旧名保留在映射表里，查询时展开成一组 ID。
2. **按 ID 迁移**：关系能从当前数据重算的那一类。拓扑、采集配置、探测任务存 `device_id` 与 `port_id`，名字降级成属性，改名零成本。
3. **冻结快照**：带流程含义的那一类。工单、变更单、复盘报告存 `device_id` 加当时的名字副本，永不回溯。五年前那张单上写的是 `TOR-A3F-02`，今天它还应该写这四个字，这不叫错。

选择依据一句话：**能不能重算**。关系能从现网重新推出来的走迁移，重算不出来的冻结或者留别名。硬删永远不是选项，它只是把一次改名事故换成一次查不出原因的空白。

别名表本身也要有寿命。一张只增不减的映射表，五年后会有几千条记录，其中九成指向已报废对象，查询展开时把不必要的 ID 一起拉进来，`sum by` 的基数跟着涨。规则是：别名生效后保留一个查询窗口（30 天足够覆盖所有历史大盘和规则），到期归档进冷表，只留「旧名 → 新 ID」这一列。

还有一处容易漏的：别名只解决查询，不解决写入。改名当天的采集如果还在用旧名字发数据，映射表会把它归到旧 ID 上，于是新名字下面没有当天数据，旧名字下面多了一段不该有的点。改名要和采集配置的更新放在同一张变更单里，先后顺序是先改采集、再改台账、最后改别名表。

## 判据

下面三张表，各自写出外键方向与处理策略，再补一句「为什么不是另外两种」。

```text
T1  30 天原始指标的时序库，label 里带 device 与 ifName
T2  告警规则表，规则形如 device=~"tor-3f-.*"
T3  工单表，字段里存设备清单与端口清单
```

验收三条：

1. 三张表都能说出对象改名后要不要动、动的是数据还是查询
2. 给出一次具体的删除操作，列出受影响的表清单和每张表的处置动作
3. 说出你自己平台上哪张表把名字当成了关联键，改一处的成本是多少

::: details 参考

T1 走软删 + 别名。历史点无法重算，只能在查询层把旧名展开。改成重写历史，成本是 2.3 小时/300 台，而且每次改名都付一遍。

T2 走迁移，规则选择器换成稳定 ID。规则是判定逻辑，可以重建；它依赖名字只是实现细节。改成软删 + 别名，规则文本要跟着改，漏改就是静默。

T3 走冻结快照。工单是有法律与流程含义的记录，改了就失去证据价值。迁移成 ID 会让老单子上出现一个当时不存在的编号。

删除一次设备的完整影响：时序停写、规则标退役、工单加标记、拓扑解链路、采集任务停用、事件保留。六张表六种动作，少做一张就是一个悬空引用。

## 小结

改名断曲线，换板接错历史，报废设备训练出无视告警的习惯。三种错法一个来源：把名字当成了身份。

主数据的意思是别人存引用、不存副本。身份字段必须是机器给的、人改不动的，序列号是首选，主机名和 IP 都不合格。

引用方向只有六类，处理策略只有三种：能重算的迁移，不能重算的留别名，有流程含义的冻结快照。硬删从来不是选项。

下一课把这些规矩落成一张表：五层对象要哪些字段，设备从规划到报废怎么走，以及怎么用一条状态判断挡掉大部分假告警。
