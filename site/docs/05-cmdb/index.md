## 这一篇解决什么

前面五篇讲的都是数据：端口状态、探测结果、计数器、流记录。每条数据总得挂在某个东西上——一台设备、一个端口、一条链路。这些东西的名字、归属、上下线状态从哪来？CMDB。

CMDB 有问题，后面全错，而且错得隐蔽：曲线还在画，只是画在了错误的端口上；告警还在报，只是报的是一台三年前就报废的设备。

三种真实错法值得先看一眼：

- **设备改名**：主机名从 `tor-3f-02` 改成 `TOR-A3F-02`，采集器按名字存指标，历史曲线断成两截，告警规则找不到旧对象
- **端口重排**：换了块业务板，`ifIndex` 全变，按 `ifIndex` 建的主键把新端口的历史接到了旧端口上，运维看着一条「从未有过的流量曲线」查了两天
- **僵尸设备**：设备下架报废，台账没删。采集器每天轮询、每天超时、每天告警一次「设备失联」，值班的人学会了无视这条告警——最坏的后果不是多了一条噪声，是训练出了忽略告警的习惯

这一篇有两个结论值得单独记：

**链路是独立对象，不是端口的属性**。链路有自己的 ID、带宽、两端端口、聚合关系、SLA、故障历史。把它做成端口的两个外键，第一次遇到 LAG 就得重构。

**「拓扑」在平台里是两张图**：设备拓扑（LLDP / STP / 路由邻居）回答「交换机和交换机怎么连」，终端接入图（ARP / MAC 表 / DHCP 租约）回答「某个 IP 接在哪个交换机哪个口」。ARP 给不出设备间链路，混在一起做必然出错。

## 配套实验

- `labs/09-cmdb`：给一份刻意做脏的台账——重复登记、端口错挂、三台僵尸、两个幽灵——外加 LLDP 与 ARP 快照，输出三类差异清单。**不允许自动改写台账**
- `labs/10-topology`：拓扑融合与冲突裁决，syslog / Trap 的归一化与去重
- `labs/11-endpoint`：三套快照上的 IP → MAC → 交换机 → 端口联查，含三个陷阱

## 读完你应该能

- 说出平台的哪些表有外键指向 CMDB 对象，对象被删除或改名时这些表怎么处理
- 画出设备与链路的四层模型，并解释为什么 LAG 逼着你把链路做成独立对象
- 用 LLDP、STP、路由邻居、MAC 反推做四源融合，说清冲突时按什么取信
- 实现一次终端定位联查，并解释 MAC 漂移、聚合口只报逻辑口、ARP 已老化三种误判
- 写出一条「对账结果生成差异单、不自动改写台账」的规矩，并说服同事
