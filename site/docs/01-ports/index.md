## 这一篇解决什么

基础设施层的「通不通」，全部在设备和链路这一侧。前四课是端口：`adminStatus` 与 `operStatus` 各自的含义、抖动为什么比彻底 down 更难查、光模块在 down 之前有几周的信号、三条采集通路怎么选。后两课是设备本身：管理面可达性、一万台设备的存活判定。

这一篇的判据很硬：**能写出一棵 down 根因判定树**。判据写不出来，后面的告警分级、影响面分析、举证包全都建立在错误的归因上。

`ifAdminStatus=2`（人手工 shutdown）和 `ifOperStatus=2`（链路断了）在报表上都写「down」，含义差着一个工单类型——前者是变更，后者是故障。平台必须分开统计，否则每周的故障数里会混进一批割接。

**单向链路**是这一篇最麻烦的一类：本端显示 UP，对端早就 DOWN 了。检测方法只有一条——拿链路两端的状态做比对。所以端口必须先成对挂到链路上（第六部分），否则这个判断根本写不出来。这是「模型错了后面全错」的典型例子。

07 课的结论是一条工程规矩：**Trap 做快速发现，轮询做权威对账**。只用 Trap 会漏，只用轮询会慢，对账逻辑才是这一课真正的产出。

08 课要讲清一个平台设计后果：设备掉线会让它所有端口同时 down，告警系统不知情就会收到「一台设备 + 48 个端口」共 49 条。父告警压制子告警的规则源头就在这里。

## 配套实验

- `labs/01-portstate`：喂进录好的 `ifTable` 快照与 Trap 序列，实现六成因判定树，输出「这条端口为什么 down」以及归属（变更 / 硬件 / 配置 / 故障）。样本里混了三类陷阱：admin shutdown、单向链路、SNMP 代理重启造成的假抖动
- `labs/02-device-alive`：一万台设备的存活监测模拟器，含探测调度、去抖、探测侧故障识别与上下线事件；四类剧本（断电、重启、CPU 打满、探针整段失联）各自的误报代价写在 README 里

## 读完你应该能

- 拿到一个 down 的端口，按判据走完六种成因，说出归属是谁
- 判定 flapping 并解释它为什么比彻底 down 影响面更广，知道要拿 `sysUpTime` 剔掉代理重启造成的假变化
- 从光模块的五个参量里看出早期失效，并且知道要跟同型号横向比
- 解释「ping 不通」的六种可能，以及四步判据怎么分清设备死了、重启了、还是你过不去
- 给自己的规模算出探测点数与失联发现延迟，并说清 `N × T` 与设备重启窗口的关系
