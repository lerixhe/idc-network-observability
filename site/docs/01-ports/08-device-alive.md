## ping 不通，至少有六种意思

07 课把三条采集通路对完账，这一课把视角从单个端口抬到整台设备：它还在不在。

值班开盘第一件事就是这个。登上堡垒机，`ping 10.20.3.1`，不回。下一步做什么，取决于你信不信这个「不回」。它至少有六种来路。

| 可能 | 现场特征 | 谁的事 |
|---|---|---|
| 设备真挂了 | ICMP 与 SNMP 同时不通，`sysUpTime` 取不到，相邻设备也看不到它 | 硬件、机房 |
| 设备重启中 | 先不通，几十秒到几分钟后恢复，`sysUpTime` 只有几百秒 | 变更、硬件 |
| 管理面 CPU 打满，ICMP 被丢 | SSH 卡、SNMP 偶发超时；RTT 抖动大，业务高峰时丢得更凶 | 性能 |
| ACL 误封了探针网段 | 从别的位置 ping 得通，从探针这侧稳定不通，SNMP 也不通 | 配置 |
| 管理网络本身断了 | 同网段一批设备同时不回，业务侧毫无感觉 | 管理网 |
| ICMP 被设备限速 | ping 丢一半，SNMP 秒回；加大频率丢得更多 | 设备策略，不算故障 |

六行里只有第一行要打电话叫人。剩下五行，四行是「你过不去」，一行是「设备在动」。把它们统统报成「设备失联」，值班的人一周之内就学会无视这条告警——第 23 课那个僵尸设备的故事，成因之一就是这个。

给个数字记住代价。某机房 200 台设备，管理网的一台接入交换机重启 4 分钟，平台按「失联」上报，一次 200 条。设备的故障率一次只涨一台，这个数是告警系统的故障率。

最后一行（ICMP 限速）的判法要给个对照实验：固定发 20 个包，间隔从 1 秒压到 0.05 秒，看丢包率。丢包率随发送频率上去的，是限速；不随频率变的，是路径或设备真有问题。这个实验 30 秒能跑完，比争论谁对省事。

## 四步链：设备死了、重启了、还是你过不去

六种原因靠猜没用，按顺序走四步。

```text
① ICMP 不回
   ② SNMP Get sysUpTime.0（超时 2 秒，重试 1 次）
      ③ 拿到的 sysUpTime 是否归零（与上次采样比）
         ④ 相邻设备能否看到它（LLDP 邻居、路由邻居、同网段其他设备）
```

每一步的判据，以及它排除掉哪几行：

| 步 | 结果 | 结论 |
|---|---|---|
| ① | ICMP 通 | 管理面可达，存活一栏结束。慢、抖、丢包另算，进质量指标 |
| ② | SNMP 通、取到 `sysUpTime` | ICMP 被限速或被 ACL 挡。设备活着，改探针侧策略 |
| ② | SNMP 也不通 | 往下走，「设备死」与「你过不去」这时还没分开 |
| ③ | `sysUpTime` 比上次小 | 设备重启过。重启是事实，不一定算故障 |
| ③ | `sysUpTime` 取不到 | 判不了，走 ④ |
| ④ | 相邻设备看得到它 | 设备在网、在转发，问题出在你这条管理路径上 |
| ④ | 相邻设备也看不到它 | 设备真下线了，可以叫人 |

四步走完，「不通」被拆成三个可执行的结论：设备死了、设备重启了、你的管理路径断了。三句话三个人接：机房、变更、网络配置。

第 ④ 步有三类证据，置信度不一样，都别单独用：

| 证据 | 能证明 | 盲区 |
|---|---|---|
| LLDP 邻居（`lldpRemTable`） | 上游还能收到它发的 LLDP 帧 | 一代邻居 120 秒就过期，重启前后有窗口期；邻居没开 LLDP 等于没证据 |
| ARP 表、MAC 表 | 它最近发过包，二层还活着 | 表项老化几分钟，「刚才」不等于「现在」 |
| 路由邻居（OSPF/BGP） | 控制面还在跑 | 只看三层邻接，管理口挂了照样是邻居 |

三类都是间接证据。一条都没有，才敢判它下线；有一条在，只能说「转发面还在动」，管理路径的问题照样成立。

工程量全在 ③。`sysUpTime` 是 32 位整数，单位百分之一秒，约 497 天回绕一次（2^32 ÷ 100 ÷ 86400 ≈ 497.1）。判「归零」不能写成 `new < old`：回绕时 `new` 也会掉到很小。判据是按模 2^32 算增量 `Δ = (new - old) mod 2^32`——Δ 落在采样间隔附近（30 秒间隔取 Δ ≤ 3000）就是正常推进或刚好回绕；Δ 远大于采样间隔（比如超过 5 分钟对应的 30000）才判重启。第 18 课的计数器回绕算法在这里复用一次，还是同一个坑。

第二个坑是恢复顺序。设备重启完，内核先起来，ICMP 能回；SNMP agent 是用户态进程，还要再爬一阵。我见过这个间隔到 40 秒。② ③ 两步各有各的时间轴，判定要分别计时，不能拿「ICMP 通了」当成「SNMP 也该通」。

## 管理面和数据面是两张网

设备存活测的是「我能管到它」。它在不在转发，是另一件事。

这两件事在物理上就分开了。IDC 里一台交换机至少两张网：业务口接服务器和上行，管理口接管理网。管理网有自己的交换机、自己的路由、自己的 ACL、自己的 DHCP。两张网共用一台设备的电源和 CPU，其余一概不共用。

管理网本身有三种形态，出结论时要说清探的是哪一条，否则两个系统各报一个数：

- **带外管理口**：独立物理网口、独立交换机、独立 IP 段。设备断电，BMC 还能回话
- **带内管理 VLAN**：同一个业务口上的逻辑接口，配置错了就把自己关在门外，改错 VLAN 的经典后果
- **console 服务器**：串口，最后一条路，只给人用，不给平台用

第 03 课场面三在这里有完整因果：管理网的一台汇聚重启，几十台设备的管理 IP 一起不可达，告警齐响，业务侧一点没受——转发面走的是另一套设备和另一套链路。反过来也成立：业务网打满、转发面开始丢包，管理面的 ICMP 照样 0.2 ms 回你，管理面流量走低优先队列，与业务流量不抢同一条路。

由此得到两条口径，必须在表结构里分开，不许合成一个数：

- **设备可达率**：管理 IP 可达的时长 ÷ 统计窗口，分母扣掉计划内维护窗口
- **设备在网率**：CMDB 里状态为「在网」且被邻居看到的时长占比，与管理网无关

合成一个「设备可用率」，报表好看，事后没人解释得清：某月可达率 99.2%，业务侧零中断，那 0.8% 全在管理网上。第 36 课的「同一个词三种答案」，这是其中一种。

## 一台设备挂了，会引爆 49 条告警

平台设计上最硬的一条：**设备存活与端口状态分开报**。

一台 48 口交换机断电，四个源同时动静：ICMP 全丢、SNMP 超时、48 个端口的 `ifOperStatus` 采不到、下挂设备开始报服务不可达。规则要是写成「端口 down 报一条」，运维收到的不是 1 条，是 1 + 48 + N 条。

算三遍看规模：单台 48 口一次断电 49 条；一天 3 台设备重启 147 条；一次板卡重启带动 12 台 TOR，光端口层就 576 条。第 02 课那个 847 条的场面，一半是这么堆出来的。

还有一层时间上的麻烦：四个源到达平台的时间差几十秒。端口状态要等下一个轮询周期（60–300 秒），ICMP 三下就判死。父告警晚到，子告警先发，值班的人先看到 48 条端口 down，一分钟后才看到「设备失联」——那时候他已经开始一台台登设备了。判定要按时间窗回填：父事件成立后，回头看 5 分钟内同设备的子告警，把它们收进父事件。

三条规则：

1. **设备存活是父，端口 up/down 是子。** 父成立期间子不单独发通知，只在父的事件里挂成清单
2. **抑制单向。** 父压制子，子不压制父。反过来写，端口全 down 会盖掉「设备刚重启完」这个更值钱的结论
3. **父子关系靠对象模型，不靠时间窗。** 设备到端口是 CMDB 里的外键，第 24、25 课建的表就是这条规则的输入。没有外键，压制只能退化成「同一分钟、同一设备名前缀」这类模糊匹配，误伤和漏报一起来（第 38 课）

还有一个容易漏的分支：设备失联时，端口的最后一次状态是过期数据。平台把「采不到」当成「状态没变」，48 个口就永远停在最后一次的 up 上，业务断了，大盘全绿。硬规矩一条：**采集超时的端口状态标 unknown，不继承上次值**。`ifOperStatus` 本来就有 `unknown` 这个取值，多数实现只认 up/down，把它扔了。

## 换机复用 IP：台账污染的高发点

旧机下架，新机配同一个管理 IP 上线。平台按 IP 存数据，新设备的历史曲线就接在了旧设备后面。

三个标量足够识别，它们都在 `system` 组里，一次 Get 全拿到：

| 字段 | OID | 它标什么 |
|---|---|---|
| `sysUpTime` | `1.3.6.1.2.1.1.3.0` | 开机时长，百分之一秒 |
| `sysName` | `1.3.6.1.2.1.1.5.0` | 配置里的主机名 |
| `sysObjectID` | `1.3.6.1.2.1.1.2.0` | 厂商与型号 |

四种组合，四种处置：

| 现象 | 判断 |
|---|---|
| `sysUpTime` 归零，另两个不变 | 同一台设备重启：升级、断电、手动 reload |
| `sysUpTime` 归零，`sysName` 变了 | 换机，或改名重启。改名不必重启，所以大概率是换机 |
| `sysUpTime` 不归零，`sysObjectID` 变了 | 换设备必伴随重启，所以这一行指向固件或板卡升级，不指向换机 |
| 三个都不变，只有管理 MAC 变 | 换了主板或管理模块，还是那台机器 |

判据：**`sysUpTime` 归零，且 `sysName` 或 `sysObjectID` 与台账不符，发一条「疑似换机」事件，不自动改台账**。第 28 课的规矩在这里兑现：对账结果生成差异单，主数据不自动改写。

真正的身份是序列号（`entPhysicalSerialNum`）。主机名会改，IP 会复用，序列号不会。第 24 课建 CMDB 时定过这一条，这里它第一次真的被用上。

一次误判长这样：某机房一台 TOR 换了备件，IP 复用，主机名沿用旧名（图省事），型号也同款。平台按 IP 存指标，曲线平滑地接上了。三个月后做容量规划，发现这个端口「过去一年流量一直在涨」，涨的那一段是两台设备拼起来的。查了两天。

## 判据

给一组现场数据，按四步链走完，每步写一个判据和一句结论：

```text
10:14:02  ICMP 连发 5 个，全丢
10:14:30  SNMP Get sysUpTime.0，超时 2 秒 × 3 次，全失败
10:15:10  同网段 10.20.3.2、10.20.3.3 均可 ping 通，sysUpTime 为 4 天 2 小时、11 天
10:15:40  上游汇聚的 LLDP 邻居表里仍有 10.20.3.1 的条目，最后更新在 10:09
```

三个问题：

1. 这台设备死了吗？先写「能确定什么」，再写「不能确定什么」。
2. LLDP 那条记录能当「设备还活着」的证据用吗？（提示：一代邻居 120 秒过期，第 26 课）
3. 10:20 它恢复了，`sysUpTime` 读到 300 秒。四步链里哪一步会给出错误结论，错在哪里？

验收标准：问题 1 的答案里，「设备真挂了」与「管理路径断了」必须是两个分开的结论，各自给一个 5 分钟内能跑完的验证动作。问题 3 要答出「④ 在重启窗口内会把重启判成下线」。

## 小结

「ping 不通」有六种意思，四步链把它们压成三种结论。管理面与数据面是两张网，设备可达不证明它在转发。存活与端口状态必须分开报，否则一次断电换来 49 条告警，一次管理网抖动换来 200 条。`sysUpTime` 归零加 `sysName` 或 `sysObjectID` 变化，是识别换机复用 IP 最便宜的三个字段。

四步链在一台设备上够用。一万台就不够了：探测怎么调度、失败几次算失联、判定窗口多宽、上下线怎么变成事件，这些是工程账，下一课算。
